# One reply per message, model-written from what really happened (plan, 2026-11-01)

The owner, after the wrong-messages check: "Ok yes, but model written please."

## The problem
Several pieces each write their own sentence about one message, each seeing only its own part:
the page's first-answer line, each split part's reply, the per-part progress state, and the agent's
own summary. Each is right about its piece and can be wrong about the whole ("linking it in the
header was not done" while a sibling part had done it).

## After
1. **Facts first, gathered by code once every part has ended** (`requestView` ended): for the whole
   message, the site before vs after (files added / changed / removed, by name), rows and table
   rules changed, keys asked and still missing, what was published or left as draft, every part's
   ending (done, waiting on a question, paused for credits, stopped, failed and its reason), and
   the credits actually charged (ledger). Nothing from the request's wording counts as a fact.
2. **One model call writes the reply from those facts only**: the customer's message and the facts
   go in; one short reply comes out. Its instructions: say only what the facts show; name what was
   asked and not done, and why; never claim a change that is not in the facts; plain words, no file
   paths or developer notes.
3. **A check before it is shown**: every page, table and key the reply names must be in the facts;
   a reply that names something absent is not shown, and the facts' plain fallback sentence is.
4. **The parts stop speaking as conclusions**: while running, the task list shows progress only
   ("working", "waiting for your answer", "paused for credits"); the one reply is the conclusion.
   The page never shows a failure line once the server has taken the message.
5. **Cost**: one small model call per message (the customer's own builder model, low effort),
   charged by the tokens it uses, like every call.

## Order of work (each with tests that fail on the old code)
1. The facts: one function over the request's parts and the before/after site.
2. The writer call and its instructions; the check; the fallback.
3. Wire it at the request's end; the parts' replies become progress only.
4. The page: show the one reply; remove the per-part conclusion lines.
5. One live check on a test site (owner's approval, estimated 20-40 credits): a split message
   where one part's work is done by another, and one paused for credits.

## Decided by the owner (2026-11-01)
- Build it ("yes do it"), with the look shown in the mock-up (one task line, one reply, the key box after it).
- The writer is whatever builder model the customer has chosen in the chat.
- Every message gets the one reply (single-part ones too).
