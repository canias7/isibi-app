# The builder talks while it works: design, as built (2026-10-13)

**Status: built and tested offline on branch `new`, behind a new switch
(`PROGRESS_TALK`, off by default). Nothing is merged, deployed, built into an
image, switched on, pressed or spent.** The commits, test results and the one
consolidated live verification are in
`docs/history/2026-10-13-progress-talk.md`.

This document started as five options (2026-10-13, morning). The owner then
asked for them built as one batch, with corrections; this is the design as
built, with what it deliberately does not do.

## What the owner asked

> *"I want the builder to communicate naturally throughout the work across
> Build, Edit and Add-on: explain its initial approach, tell me what it is
> doing, share useful findings and decisions, ask questions when needed, and
> finish with a clear account of what actually happened. All ordinary
> conversational wording must be generated by the model … code should supply
> trustworthy facts and execution states, not canned sentences."*

And, among the corrections: no message quota and no narrating every file;
combine closely spaced events without losing findings, questions, failures
or completed work; an optional expandable explanation, never a promise to
expose everything the model thinks and never hidden reasoning; intended,
running, prepared, applied, published and verified kept apart, with "I
checked", "nothing else changed", "it looks right" and "it's live" each
needing its own evidence; reasons only where a recorded decision supports
them; parallel requests explained; server-side persistence with no
duplicates and nothing stale after the final reply; narration failure never
blocking or failing the work; platform-paid; measured.

## What it reuses (nothing new beside it)

Compared first with `claude/help-needed-ehlwlj` (38 commits ahead of `main`
at the time, a concurrent session working on final-reply evidence, canary
verdicts and a prepared Build-parallelism audit) and the older `claude/*`
branches (stale since September). None of them changes the progress writer,
its record or its UI, so this batch builds on `main`'s:

- **the record** (`jobs/<id>.progress.json`, etag-guarded, one per job);
- **the one writer per job** with its lease, its two tries, the job's row
  read before the call, before the commit and after it, and lines shown only
  once confirmed (`confirmLines`);
- **the recorder** with numbered, retried deliveries (no duplicates);
- **the two-minute sweep** for lost asks;
- **the task lines** (the model's first-person line for each task in each
  state);
- **the request's other parts** as context (`otherParts`);
- **the page's list** (`progressListHTML`), the poll reader
  (`EditPoll.progressLines`), the copy kept on a finished reply
  (`siteKeepJobProgress`);
- **the cost log** (`usageLogLine`) and its reader
  (`scripts/narration-usage.mjs`), which prices each call at the platform's
  own rates. Narration is never charged.

The concurrent session's files (`builder/content-evidence.mjs`,
`builder/site-requirements.mjs`, the add-on's content evidence in
`worker.js`, `scripts/canary-*`) are not touched. `builder/site-reply.mjs` is
touched only at the reply request (`replyRequest`, `writeReply`, one new
constant), away from the fact builders that session changes.

## The switch

`PROGRESS_TALK` = `on`, on top of `PROGRESS_REPLIES` (`talkOn`). It is read
once when a job's recorder is made, and a record opened with it keeps
`talk: true` for its whole life, so a job never changes writer half-way. It
is in `JOB_ENV_NAMES` (jobs in the container read it) and in the deploy
workflow's secrets with `|| 'off'`. Off, every record, call and answer is
exactly as before; the tests hold that byte for byte where it matters
(`OFF IS AS BEFORE`, the ordinary writer's instructions and context).

## The five options, as built

### 1. The initial approach

A first milestone, `start`, recorded as the job opens (`startFacts`), from
what is known then and nothing more:
- **Edit**: the kind of change the route sent it as (the wording, the look,
  the menu…) and the page when the route named one; then, as `next`, the
  steps an edit really runs (find the place, make the change, build, the
  automated browser check, publish).
- **Add-on**: an addition; then design, build, check, publish.
- **Build**: a new site at its address; then design, write, build, publish.
  Not again on the run that carries a build on.

All `decided` and `next`, never a result. The writer is told when it has not
spoken yet, and to begin with how it will go about the work; later
milestones (the edit's own plan of steps, the add-on's picked kinds) revise
it, and it is told to say how when the facts change the plan. **Nothing
waits for it**: the writer runs in the background, as before.

### 2. More moments, combined

New milestones only where a real result exists:
- **the checks a publish ran** (`checked`, in `recompileAndPublish`, after
  the add-on's repair seam settles the build that will ship and before
  anything is written): the site built; what the automated browser check
  opened and flagged; the style rules this change wrote, when that check
  was asked for;
- **the publish itself** (`published`, once `activate` answered ok);
- **a build's container turn** (`talkBuildStepFacts`): the site built, and
  the publish starting.

**Combining.** A conversational record asks for its writer
`PROGRESS_SETTLE_S` (3) seconds after a milestone, not at once; milestones
that land meanwhile find the ask already made, and the one call covers them
all (`batchFor`): every settled fact of every milestone — decisions, checks,
failures, things not done — and only the newest "now" and "next". No quota:
an edit that passes few moments says little, and no per-file milestone
exists. The job never waits for any of it.

### 3. Chattier updates, reasons only where recorded

The conversational writer (`TALK_SYSTEM`, `TALK_TOOL`, `talkRequest`) asks
for an update "as long as the news needs and no longer". A fact may carry a
**recorded reason** (`why`), shown to the model as "recorded reason: …";
the rule is a reason only where one is recorded. Recorded reasons today are
few and structural: a part's order in its request (`waitedFor`, from the
request's own `needs`). The other decisions the code makes do not record a
reason yet, so the model is given none for them — which is the point: no
"because" without one.

### 4. The explanation, folded — not a thought stream

The conversational call may return `explain`: a short account of the
approach and decisions so far, from the facts and their recorded reasons. It
is optional, stored with its line (only on a conversational record), handed
to readers only with the line's confirmation, carried by the poll, the
request view and a finished reply, and drawn under the lines as one section,
closed until opened, under the fixed label "More detail".

**What it is not.** No call asks a provider for its reasoning or for a
reasoning summary: the request carries only `model`, `max_tokens`, `tools`,
`tool_choice`, `system` and `messages` (`CALL` test). Whether the default
model (`grok-4.6`) or the Anthropic models offer such a feature was not
relied on, so nothing depends on it. The explanation is model-written prose
from facts, labelled as a summary, never presented as live thinking.

### 5. The final message

When the switch is on, the reply writer is told it follows a conversation
(`REPLY_TALK_RULES`): do not retell the updates; say what was done, which
checks ran, and what is not done or still open; a next step only when a fact
makes one useful; undo only where a fact gives it (the existing `u` facts
are added only where the operation supports one). For a queued Edit or
Add-on job, the checks and publish its record holds are added as `k` facts
(`jobChecksFor`), so the message can name the checks that really ran and no
others. A Build's reply and a request's combined reply are not given `k`
facts (see the limits).

## Truthful states

| Said | Needs |
|---|---|
| "I'll …" | a `next` fact (a plan) |
| "I'm …" | a `doing` fact (the newest milestone only) |
| "I've made / designed / worked out …" | `prepared` / `designed` / `decided` |
| "It's in your database" | `applied` |
| "I checked …" | a `checked` fact, and only as far as its text reaches |
| "It's published / live" | a `published` fact |
| "I couldn't …" | `notdone`, kept in every later update |

A `checked` fact is worded to its reach: "the site built without errors" is
not a look at the page; the browser check is "an automated check …, not a
look at the design"; a browser check that could not run is said as not done
(`notdone`), never as passed. "Something exists" is never said as "what you
asked for is met". A `published` fact means `activate` answered ok — the
live pointer moved and the site's script went up (one that could not serve
undoes itself) — **not** a fetch of the live address.

The model's own account of which state it described each fact as (`says`)
is checked, and a fact said in the wrong state, an id in the words or the
explanation, or a fact left out is asked for once more and otherwise
dropped. **The words themselves are not checked** (the owner rules out
keyword filters): a sentence that says "it's live" with a true account is
accepted, and is pinned so by a test (`LIMIT`). The instructions and the
final reply stand against it; no number of offline tests can show a model
never writes it.

## Parallel requests

Each job's updates are its own, on its own part. Its writer is told the
request's other parts as they stand, and on a conversational record what
each waits for and what this part waited for (`needs`, from the request's
plan), so a line can say what runs alongside and what must wait. The
request itself writes no progress line, only each part's task lines, so
there is no second narration to contradict the parts'. A part that stops to
ask closes its own record; independent parts go on (the request driver's
existing behaviour).

## Persistence, retries, ordering, failure

Unchanged machinery, now carrying the new fields: the record on the server,
lines kept with their explanation on a finished reply and re-read on any
device, numbered deliveries, one writer per job, a task delivered twice
making one call, a task arriving after the job ended making none, a line
committed after the end never shown. A narration call that fails is retried
once, then given up; the job's outcome, money and final reply are unchanged
(`NARRATION FAILING CHANGES NOTHING`).

## Cost, measured

Each conversational call is logged as before (attempts, fresh and cached
tokens, ms) and priced by `scripts/narration-usage.mjs`; nothing is charged.
Expected effect: one more milestone at the start, two or three more at the
publish, fewer calls than milestones because close ones are combined. A real
count is promised only after the live verification measures it.

## Limits, kept in view

1. **Prose is not verified.** See *Truthful states*.
2. **Few recorded reasons.** Only the request plan's order is recorded as a
   reason; picker, designer and router choices record none yet.
3. **No live read of the published page.** "Published" is the activation's
   own evidence; a fetch of the live address is not made.
4. **Build's final reply and a request's combined reply are not given the
   `k` facts.** A Build's reply already carries its own build facts
   (`buildFacts`); a request's reply covers its parts' replies.
5. **The old `renderNote` sentence** ("I had a look at the finished pages:
   …"), composed by code on `main` and used by final replies when the render
   check found something, reads as a visual review. It is in the file the
   concurrent session is changing (`builder/site-render.mjs`), so it is
   recorded here and in the backlog rather than changed in this batch.
6. **A browser check cut short** is said as cut short; which routes it did
   not reach is not listed.
7. **The 3-second wait** is a judgement, not a measurement; the live
   verification should read how many milestones each call covered.
8. **Supplied-model evidence only.** Every test answer is supplied; what a
   real model writes, how often, how long it takes and what it costs are
   unmeasured until the live verification.
