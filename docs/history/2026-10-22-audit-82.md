# Audit A03-4 (2026-10-22): the removal door's own look lanes under PARALLEL_WRITES

A03-4 in `docs/audits/2026-10-17-builder-audit.md`, on the owner's word ("if they're real, start"). Offline; nothing spent; not merged or deployed. Branch `audit-82`, from `codex-work-into-claude` (`a6564cf80`).

## Real

Re-confirmed today and reproduced through the real route (the request, the queue, the job runner, the edit route, the publish spine) with supplied model answers:

- `holdsConfig` (`builder/request-plan.mjs`) read only the route's layer (`look`, `logo`) and the router's targets (`site`, `theme`, `identity`). A `nav` or `picture` route with `remove` opens the removal door, whose picker can name look's own lanes (css, theme, description, the marks) beside the removal. Those lanes write the site config, but the part never took the site's turn at its start (`worker.js`, the job runner's `takeTurn` gated on `beside.holds`).
- Under `PARALLEL_WRITES` every request job runs with `beside`, even a one-part request, so the look step's `mayWriteConfig` threw `turn-lost` and its catch answered `error: "store"`, "That change couldn't be saved — try again." `store` is not an overlap code, so the request never re-ran the part.
- Reproduced: "Take Gallery out of the menu and change the site description…" routed `nav` + `remove`, picker `additional: ["description"]`: the menu published, the description step failed with that sentence, the part ended `partial`. With the switch off, both changes landed.

## The fix (two small changes)

1. **`holdsConfig` counts the removal door** (`nav` or `picture` with `remove: true`): such a part takes the turn at its start, as a look step does. The list is kept local (`DOOR_LAYER_NAMES`) because `site-ask.mjs` imports `request-plan.mjs`; a test keeps it equal to `DOOR_LAYERS`. `writesConfig` and `besideConflict` are unchanged: scheduling stays as it was, and the turn already orders two config writers.
2. **The look write's catch answers a lost turn as `turn-lost`** (an overlap code, `ours: true`, cost 0, "Another change in the same request took its turn to publish, so this one wasn't saved. Nothing of it was published."), so the request re-runs the part alone. Any other store failure keeps "couldn't be saved". The css correction's write (`turnStillMine` before `patchSiteConfig`) runs only after the look step's own write under the same turn; a loss there ends in the spine's own `turn-lost` and was left as it is.
