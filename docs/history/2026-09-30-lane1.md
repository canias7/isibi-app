## 1a. The data picker's deletion instructions

**What was wrong.** `DATA_TOOL`'s `changes` list said *"IF THE INSTRUCTION
CANNOT BE DONE BY CHANGING OR ADDING ROWS — it asks to DELETE one, or it is
about the look of the page rather than what is stored — return an empty
array"*. That was written before rows could be removed. `dcf269a4` gave each
item a `remove` field (*"True to DELETE the row with this id"*) and left the
sentence, so one request told the picker both to delete the row and to answer
nothing for a deletion. The tool's one line named changing and adding only.

**The change** (`builder/site-apply.mjs`):
- the list's sentence sends a deletion to `remove`;
- the empty array is kept for what cannot be done with rows (a request about

- the tool's one line names taking a row off;
- the `id` field names removal.

Adding a row is described exactly as before, and the router
(`builder/site-ask.mjs`'s instructions) is untouched, so the add-row routing
policy is unchanged.

**The existing pin revised.** `test/site-apply.test.mjs` required the list to
name DELETE as "the one thing this layer cannot do": it pinned the
contradiction. It now requires the list to send a deletion to `remove`.

**Tests** (`test/data-remove-wording.test.mjs`, the real
`POST /api/site/<slug>/edit` at layer `data`, the picker's answers supplied):

## 1b. Why a routing call failed

**What was wrong.** `routeMessage` wrapped building the request and sending it
in one bare `catch` and kept only `failed: true`. Run 70 answered `addon` and
`failed` in 0.4 s, and nothing could say why: the xAI account's balance was
empty, which the owner found by looking.

**The change.**
- **`builder/site-ask.mjs`**: the two steps fail separately. The answer
  carries `failure`, built by `routeFailure` from allow-lists only:
  - `kind`: `request` (the request could not be built), `config` (a key is
    not set), `provider` (the provider answered an error status), `timeout`
    (our clock), or `transport` (the send threw with no status);
  - `provider`: `xai` or `anthropic`, from the model the call was for;
  - `status`: an HTTP status, or null;
  - `type`: the provider's token, passed through the same shape check
    `upstreamKind` uses on the build path. Since `ce992066` it is a code
    from its provider's own finite table, or null (*The owner's review*,
    below);
  - `billing`: whether our account was refused (401/402/403, or the
    provider's own billing token);
  - `error`: the thrown error's class, from a fixed list, else `Error`.

  No message, detail, header, cause or request text is ever read into it. The
  fallback (`addon` with a site, `build` without), the null usage and the cost
  of 0 are unchanged.
- **`worker.js`**: `/api/site/route` hands in the build path's own
  `upstreamKind` as the provider reader, returns `failure` beside `failed`,
  and logs the same object.
- **The canary** (`scripts/canary-route.mjs`, `scripts/edit-canary.mjs`):
  `failureSaid` reads the object again by the same lists and prints it on the
  routing line, e.g. `FAILED (provider xai 403 insufficient_quota — refused on
  our account (billing or key))`. `routing.json` already keeps the route's
  whole answer, `failure` included.

**Tests** (`test/route-failure-reason.test.mjs`, the real
`POST /api/site/route`, the provider answered on the wire):
- run 70's shape: xAI 403 on an exhausted team → `provider xai 403
  insufficient_quota`, billing;
- Anthropic 529 overloaded, not billing;
- a provider token that is key-shaped, a sentence or markup → dropped;
- a network `TypeError` → `transport`; our `TimeoutError` → `timeout`;
- a key that is not set → `config`, and the provider is never called;
- an error whose class name carries text → reported as `Error`;
- a site name the digest cannot turn into text (`{toString: 1}`, reachable
  from the public body) → `request`, and no model is asked;
- with no site the fallback is still a build;
- a routed answer is billed as before and carries no `failure`;
- the module on its own: no reader, a reader that throws, a reader that
  answers junk, a status that is not an integer;
- the canary's line refuses what it cannot read.

**Secrets.** Both provider keys, a bearer, a Neon connection string with its
password, and the customer's own words were planted in every field a failure
carries. None reached the route's whole reply or the canary's line. Since
`d19652c4` the tests read the Worker's log as well (*The log lines*, below).

Also changed:
- `test/site-route-failure.test.mjs`: the browser stops on a failed answer
  that carries its reason exactly as it did without one.
- `test/edit-canary.test.mjs`: the routing line's wiring is guarded.

**Red check** (the new file on `19f6e480`, with only the new constants
stubbed so it imports): 10 of 12 failed, each on the missing `failure`. The
routed control and the canary's reader passed.

**What was wrong: four hops.**

   alone. That reader answers null for a blank reference unless some earlier
   build left the connection in KV, so the Data panel answered "no such site".
4. The Data panel said "No data tables yet." when its own read failed.

**The change.**
- **The list** decides through `backendState`, as the addon, the rules rung
  and the repair script already do:
  - `ready` and `incomplete` have a database;
  - `none` has not;
  - a project read that fails is `unreadable`, sent as `db: null`, never a
    no.

  scoped to the caller's uid and their own blank slugs, and selects `slug`

- **The browser** (`public/site-list.js`) keeps three answers, `true`,
  `false` and `null`, and the merge keeps `null`. The card

  real no.
- **Adoption** (`siteAdopt`) carries the server's yes onto the record the
  workspace reads, only a yes, and never takes one away.
- **The owner data routes** open the database through `ownerSiteConn`:
  - the fast reader first;
  - then the four-state reader, read-only. An incomplete link is resolved and

  - an unreadable reference throws, so the block answers its 500 ("Something

- **The Data panel** says "Couldn't load this site's tables just now." when
  its read fails, and "No data tables yet." only when the list was read and

## 1d. The router is told the owner's own table names

**What was missing.** The router's `data` clause says *"The tables it has are
named above"*, and the names came only from a browser that built or revised
the site. A fresh browser and the canary send `tables: []`. Run 74 routed a
price put-back to `text` with none named. That is a confirmed gap in what the
router is told, **not a proven cause**: B1 was routed `data` with no names at
all.

**The change** (`worker.js`, `/api/site/route`, `routeDigest` and
`routeTableNames`). When the digest names no tables, the route fills them in,
for a site the caller says exists (`hasSite: true`) under a well-formed slug:
- **ownership is verified first**, with `siteOwnerBySlug`, the uid reader the
  other owner routes use. It never reads `.uid` off the connection reader,
  the recorded trap. Nothing else is read for another owner's slug;
- the connection comes through `ownerSiteConn` (from 1c), so an incomplete
  link with an empty cache is resolved and proved, never healed;
- the names come from the catalog-first schema reader: identifier-shaped
  names only, no columns and no rows. An unknown schema names nothing;
- the whole lookup is bounded at **3 s**. Any failure routes exactly as
  before, blind. Nothing is written or provisioned;
- names the browser sent stand;
- the route reports `tablesFilled` when it filled them, so a run's evidence
  shows what the router was told.

**Tests** (`test/route-table-names.test.mjs`, the real `POST /api/site/route`,
reading the request the router is sent):
- a ready site is named. The site section is exactly the pages and the two
  table names;
- an incomplete link with an empty cache is named, and its connection proved;
- another owner's slug reads nothing past its owner;
- a missing slug, a path in the slug, upper case, an array, and a no-site
  message look nothing up;
- the browser's own names are kept;
- an empty database names nothing;
- five lookup failures route blind with nothing written: ownership, project
  row, probe, catalog, and stored schema;
- a table name that carries an instruction never reaches the router;
- a lookup that never answers is cut off at the bound (the test finished in
  about 3.6 s).

**Red check** (the new file on `b12dd43b`): the four cases that need the fill
failed. The five fail-open controls passed on both.

## The owner's review: two diagnostic gaps closed before deployment (`ce992066`)

The owner credited Lane 1's implementation and its CI, and found two gaps to
close before a deployment:

> *"PROVIDER_TOKEN is a character-pattern check, not an allow-list of known
> error codes. … routeTableNames now reaches the shared
> routeDeps.onBackfillError callback, which still logs raw e.message under
> "site route KV:"."*

### 1. A provider's code comes from a finite table

**What was wrong.** Any snake_case word in a provider's error body was named.
`private_token_probe` reached the reply, the Worker's log and the canary's
line. `upstreamKind` also read the type through `String()`, so
`["private_token_probe"]` became the word itself; `xaiErrorDetail` did the same
with xAI's code.

**The change.**
- `PROVIDER_CODES` in `builder/site-ask.mjs`, by provider:
  - Anthropic: its nine documented `error.type` values, from
    `invalid_request_error` (400) to `overloaded_error` (529);
  - xAI, which documents no codes in its error bodies: `insufficient_quota`,
    the one code the Worker itself classifies.
- `routeFailure` and the canary's `failureSaid` name a code only from its own
  provider's table (`providerCode`). An unknown code, a code that is not a
  string and another provider's code are dropped.
- `upstreamKind` (`worker.js`) and `xaiErrorDetail` (`builder/model-xai.mjs`)
  no longer coerce: a code that is not a string is no code.
- The provider, the status, the billing classification and the error's class
  are kept.

**Tests** (`test/route-failure-reason.test.mjs`, the real
`POST /api/site/route`):
- an unknown code from either provider is dropped, and appears in none of the
  reply, the log and the canary's line;
- a code that is not a string is dropped, with the status and billing kept:
  the probe or a documented code in an array, an object, a number, `true`,
  and xAI's `["insufficient_quota"]` on a 403;
- a code is named only under the provider that documents it;
- the module on its own and the canary's reader refuse the same inputs;
- **controls**: each of the nine documented Anthropic codes is named with
  its status, and billing is set for 401, 402 and 403 only; xAI's
  `insufficient_quota` is named.

### 2. The route cache's KV line names the operation and a class only

**What was wrong.** `routeDeps.onBackfillError` logged a KV error's message. A
KV error can carry the value it was writing, a connection string with its
password, and 1d made the routing call one of its callers.

**The change.**
- `lookupRoute` (`site-routing.mjs`) tells its callback which call failed:
  `read`, `write` or `delete`.
- The Worker logs `site route KV: <operation> <class>`. The class comes from
  the same fixed list as the table lookup's line, now one helper,
  `errorClassForLog`.
- The lookup itself is unchanged: a failed read falls back, and a failed write
  costs only latency.

**Tests** (`test/route-table-names.test.mjs`, the real `POST /api/site/route`).
Each case reads every line the Worker logs, the reply and the canary's own
routing line:
- a KV read that throws, with the connection string and a marker in its
  message, cause and fields, logs `site route KV: read TypeError`. The lookup
  falls back to Supabase, backfills and names the tables;
- a backfill that throws, quoting back the connection string it was writing,
  logs `site route KV: write Error`, and the names still arrive;
- a KV read that never answers is cut off by the 3 s bound, and routing goes
  on;
- **control**: a KV hit is used as before and logs nothing.

**The canary's line in the tests.** `test/fixtures/canary-line.mjs` takes the
canary's routing line from `scripts/edit-canary.mjs`'s source and evaluates
it on the route's real answer. The tests read what the canary would print,
not a copy of it.

**Red check** (the two test files on `3a728968`): exactly the eight new

**Sweeps**, each in its own worktree:
