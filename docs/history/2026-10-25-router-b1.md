# 2026-10-25 — router batch 1 (branch `router-b1`, not merged, not deployed)

From `origin/fix-row-hedge` (`6b0aaaa27` = main `a63451c3a` + the Lessons/hedging fix), on the owner's approval. It implements the router audit's plan steps 2–4 and its cache step (`docs/audits/2026-10-25-router-audit.md` on `origin/router-audit`, `fb1e5a312`). No model call, no live write, nothing spent.

## What changed

1. **No questions on a part (step 2).** A part's routing job is told questions are closed: the route passes `offerAsk: !rPart` beside `canAsk: rLive` (`worker.js`, the routing call), and `routeMessage` sends the "QUESTIONS … closed" block when `offerAsk` is false. `canAsk` still says a question can be kept, so a start-over question a part raises still waits (rebuild-scope (4)), and a stray `clarify` is still read and turned into the obvious choice by `partClarifyChoice`, kept as the safety net. A first attempt that passed `canAsk: false` broke both of those; it was replaced before commit.
2. **A site inventory (step 3).** `builder/route-inventory.mjs` (new, pure). Given what the route reads, it gives:
   - **each table with its columns.** `*` marks a column an entry must fill (NOT NULL, no default) and `=` one with a default, with the access label;
   - **each page's headings and kit sections,** whether it has a form, and the tables it reads and writes. These come from the data hooks it calls (`usePublicRows`, `useCreateRow`, …);
   - **the frame:** the menu's items, the header button, the footer's details, social links and small print. The menu editor's own readers (`navSlots`, `actionSlots`, `contactSlots`, `chromeListSlots`) read them.

   **How the route reads it.** `routeDigest` reads the stored pages once, for their addresses and the inventory. It also reads the stored spec (`ownerSiteConn` + `readStoredSpec`, as `readConverseContext` does). Both reads are for the verified owner only, each bounded in time, and each fails open: what could not be read is left out, and never said as none.

   **Size.** It is budgeted to 6,000 characters (about 1,500 tokens). When it runs over, the sections go first, then the lines are cut with "… (more not shown)". `askRequest` places it as a `SITE INVENTORY` block right after the digest, inside the user message. The tools and system are unchanged per site, so the cached prefix holds. The digest's 24-table cut is now 64 (`MAX_DIGEST_TABLES`). `builder/route-inventory.mjs` is added to the Dockerfile's worker COPY list, because `worker.js` imports it.
3. **One rule of each (step 4).** A site that exists is now sent its own compact `intent`, `alsoAsked`, `layer`, `page` and `remove` (`LIVE_INTENT` … `LIVE_REMOVE` in `builder/site-ask.mjs`). It also gets `LIVE_SYSTEM`: `SYSTEM` with its "pick the cheapest" site step replaced by a pointer to the one test. **A first build is sent `ASK_TOOL` and `SYSTEM` byte for byte**, as the owner asked on 2026-10-02.
   - **Edit/addon is one test, said once.** It is asked of the thing itself and answered from the inventory. A working feature on an existing page is an addon only when the inventory doesn't show it. In that case the page is the target and the form is a `new-component`, never a list entry.
   - **There is one tie-break.** The inventory decides first. If it can't, ask where a question may be asked. Where questions are closed, answer `addon`. Cost never decides.
   - **A removal has one owner, by what holds it.** A whole page is `page` + `remove`, and a stored row is `data`. A frame item or the logo is `nav`/`logo` + `remove`. Anything else on a page that stays is `look`. `picture` no longer claims removals.
   - **The several-changes rule is said once,** closing `layer`; it also carries look's reach.
   - **A new menu link, footer link, contact detail or header button is now `edit` + `nav`** (the frame step), as the owner directed for this batch, not `addon`. New words and new photographs on a page stay `addon`.
   - **`targets`:** "A form, section or table the site inventory already shows is never new-".
   - **`layerLine`** (the lane picker's copy of the router's words) reads the live tool now.
4. **Cache pin.** xAI's docs (docs.x.ai, *Prompt caching → Maximizing cache hits*, read 2026-10-25) say that on the **Chat Completions** API the `x-grok-conv-id` header routes calls with the same id to one server; `prompt_cache_key` is the Responses API's body field. The transport already turns a request's `cacheKey` into that header (`toXaiRequest` → `prompt_cache_key` → `xaiHeaders`). The routing call fell back to the tool-name key (`gofarther-route_message`, one key for every site). It now sends `cacheKey: "route-<slug>"` (header `gofarther-route-<slug>`). `anthropicWire` strips it. The connection was not migrated.

## Prompt size

Measured with `askRequest` for a five-page, two-table site, with no inventory:

| | before | after |
|---|---|---|
| The live rules (`intent` + `layer` + `alsoAsked` + `page` + `remove`) | 25,272 chars | 11,059 chars (44%) |
| Tool schema | 38,332 | 23,925 |
| System | 7,121 | 6,592 |
| Total request | 45,978 chars, about 11,500 tokens | 31,042 chars, about 7,800 tokens |

The inventory adds up to 6,000 characters (about 1,500 tokens) per site. A typical small site adds a few hundred to about 2,000 characters. The first build's tool is unchanged (33,344 chars).
