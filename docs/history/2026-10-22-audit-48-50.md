## A29-1: turning a rule off stays off

- **Finding.** The rules step wrote a clear as `t[k] = null` and replied
  "cleared sms" / "now off". The engine reads null as "not mentioned": the
  fill before the DDL (`fillFromStored`) and the late `_meta` merge in
  `applySiteSchema` both copied the stored `confirm`, `sms` and `webhooks`
  back. The reply said off; the site kept emailing, texting and sending.
- **Fix.** A removal is said, not implied: `cleared: [...]` on the table
  (fields `confirm`, `sms`, `webhooks` only, `CLEARED_FIELDS`).
  - `builder/site-rules.mjs` `mergeRules` adds the field to `cleared` when it
    clears it, and takes it out when a change sets it again.
  - `site-schema.mjs`: `normalizeSchema` keeps `cleared`; `fillFromStored`
    and the late merge skip a cleared field; `_meta` is written through
    `withoutCleared`, so the marker is never stored (the field is stored
    null).
  - `site-draft.mjs` `mergeSpec` (so `combineHeld`, `specOverlay` and
    `publishPlan`): a later held entry for the same table that gives the
    field no value keeps the removal, so Publish applies it.
  - The reply's "cleared" is unchanged and now true.
- **Tests.** `test/rules-clear-engine.test.mjs` (4 cases, through the real
  engine with the database stubbed at the network): all three cleared and
  none stored; the control (a silent re-declaration keeps the rules; one
  cleared keeps the others); the fill; the held path to Publish. Red check:
  4 of 4 fail on the old code.

## A29-3: a changed no-duplicates / one-per-customer rule reaches the database

- **Finding.** The unique index was named by position
  (`ux_<table>_g_0`, `_u_0`) and created `IF NOT EXISTS`; nothing dropped
  one. A changed rule reused the name, Postgres skipped it, and the reply
  said changed.
- **Fix** (`site-schema.mjs`, `mkIndexes`). The name is a digest of the
  index's columns and WHERE (`ux_<table>_<g|u>_<7 chars>`). After every group
  of that kind went in, the table's indexes are listed (`pg_indexes`) and the
  platform's older ones of that kind that are no longer declared are dropped
  (`isPlatformUniqueName`: a position or a 7-character digest after the
  prefix; the slug, case-insensitive and owner indexes never match). A group
  refused (existing duplicates) drops nothing: the old rule stands and the
  refusal is in `refusedRules`. A failed listing or drop is reported there
  too.
- **Not one transaction.** The engine sends one statement per call; instead
  the order makes it safe: the new index is created first, and the old is
  dropped only once it is in. For a moment both stand (stricter, never
  looser).
- **Once per existing site.** A site's first apply after this creates its
  unchanged index again under the digest name and drops the position name.
- **Tests.** `test/rules-unique-replace.test.mjs` (4 cases): a widened rule
  makes a new name and drops the old one after it, the slug and owner indexes
  kept; a refused index drops nothing and is reported; the same name every
  apply for an unchanged rule; the name matcher. Red check (with the new
  export removed from the import): UX 1 fails on the old code; UX 2 and 3
  are guards and pass on both.

## A29-4: a rule the database refused is not reported as changed

- **Finding.** The rules route's apply discarded `applySiteSchema`'s
  `refusedRules`, so a unique Postgres refused was replied "changed".
- **Fix.** `worker.js`'s rules apply returns `{ refusedRules }`;
  `runRulesEdit` takes each refused `unique`, `oncePerUser` or `noOverlap`
  out of `applied` and says it in the reply ("the database refused that
  rule, usually because entries already there break it", `db-refused`). An
  apply answering `true` reads as before.
- **Limit.** On the held path (draft-first) the DDL runs at Publish, whose
  result is still not carried to the owner (the audit's worker.js:13056
  half); kept for the Publish findings.
- **Tests.** `test/rules-db-refused.test.mjs` (3 cases). Red check: 2 of 3
  fail on the old code (the control passes on both).
