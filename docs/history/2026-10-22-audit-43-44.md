# Audit findings A27-1 and A27-2 (2026-10-22)

Two menu findings from `docs/audits/2026-10-17-builder-audit.md`, both
re-verified as still real today, one commit each. Offline; nothing spent, no
deploy, nothing pushed to `main`. The page guards (A21-1, A21-2) are another
helper's and were not touched.

## A27-1 — a menu edit deleted phone, email, file and anchor links

- **Finding.** The menu editor answers the whole menu back. `readNav` checked
  every restated item as if it were new (`hrefProblem`) and dropped the ones
  that failed: an existing `tel:` or `mailto:` (`not-a-path`), an upload such
  as `/u/menu.pdf` (`no-such-page`), a bare `#anchor` on a multi-page site
  (`page-local`). `menuChange` then read them as left out and `menuApply`
  deleted them from every page, and the reply said "I left out …".
- **Fix** (`builder/site-nav.mjs`). `readNav(reply, routes, shown)` takes the
  addresses the editor was shown; one of those is kept as it was, whatever its
  scheme. `runNavEdit` passes `menuUnion(slots)`'s addresses. Only a new
  address faces the new-item checks, and an item the answer leaves out is
  still removed.
- **Tests** (`test/menu-kept-items.test.mjs`, 4 cases through `runNavEdit`
  and `readNav`): a reorder keeps `tel:`, `mailto:`, an upload and a bare
  anchor on all three pages, with no "left out"; a rename of the anchor in
  place; a requested removal of the phone link still removes it; a new
  `tel:` and a new unknown path are still refused, and the reader with
  nothing shown refuses the same shapes as before.
- **Red check.** All 4 fail on the old code.

## A27-2 — a band-built home page: unreadable button, unreachable menu

- **Finding.** A one-page first build split into bands writes the home page
  through `pageShell`, which wrote the button with `JSON.stringify`
  (`action={{"label":…,"href":…}}`). `literalProp` matched only unquoted
  keys, so the menu step saw "(no words) -> (no link)" and a wording change
  had to make up the link. `chromeFor` writes no `links` for one page, and
  `applyAdditions` never gave a page with no menu one, so a page added later
  reached every menu but the home page's. `chromeFor`'s items also carried
  `to`, where the kit's `NavLink` reads `href`.
- **Fix.**
  - `builder/site-nav.mjs`: `literalProp` accepts a quoted key (`"label":`
    or `'label':`), which also covers menus written that way.
  - `builder/page-bands.mjs`: `pageShell` writes plain object literals with
    unquoted keys (`jsLiteral`), as the kit's pages do.
  - `worker.js`: `chromeFor` writes `href`, not `to`.
  - `builder/site-nav.mjs`: when a menu item is added, a `SiteChrome` or
    `AppChrome` header in the addition's scope with no `links` prop (and no
    spread), on a site where other pages have a menu, is given the site's
    menu (`seedMenus`: the union of the other menus, without a link to the
    page itself), and then gains the new item like any other menu. A site
    with no menu anywhere is still given none. The seeded page counts as
    `added`, not `had`, in the addition's report.
- **Tests** (`test/band-home-menu.test.mjs`, 6 cases): the shell's button is
  read with its words and link; quoted-key buttons and menus are read; a
  wording change keeps the link (control); an added page reaches the home
  header, with no self-link, reported as added; a site with no menus is
  given none (control); `chromeFor` writes `href`. One existing guard in
  `test/page-bands.test.mjs` pinned the old quoted spelling of the shell's
  `action` and now asserts the unquoted one.
- **Red check.** 4 of 6 fail on the old code; the 2 controls pass on both.
