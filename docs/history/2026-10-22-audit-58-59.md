## A33-1 — any edit after an SEO-tab description save put the old description back (`5ea9a1757`)

- **Checked again on today's code: real.** The SEO tab (`POST /api/site/<slug>/seo`)
  writes the description into the config's look and the live sidecar, with no
  new version. Every edit and add-on reads its source through
  `loadSiteSourceForEdit` → `ensureEditableState`, whose config merge compared
  the config's repair fields with the version's staged `state/config.json`
  and wrote the version's look back when they differed. The edit then composed
  its head from that config. Reproduced through the real SEO route followed by
  `ensureEditableState` (log: `config put back to <version>`).
- **Fix.** `keepPanelDescription(want, cur, liveText)` (`site-meta.mjs`),
  applied inside `mergeConfig` before the comparison: the current description
  is kept when it is the one the live head serves (what the tab wrote). A
  description the live head does not serve, such as a job's config write whose
  publish never came, is still put back, as the repair intends. An unreadable
  live head keeps nothing.
- **Tests** (`test/audit-58-59.test.mjs`): the real SEO route then the check
  (the config keeps the new description, the theme intact, the live head
  unchanged); the control (a config ahead of a live head that does not serve
  it is still put back); the rule; the wiring.
- **Red check.** With `worker.js` at `fdf73825a`, the real-route case and the
  wiring case fail; the control and the rule pass.

## A33-2 — draft-first Publish overwrote panel head changes and later address changes (`37f2adfa3`)

- **(a) The panel half: already fixed by A11-2** (`528c33cfc`,
  `carryPanelFields`). Batch 3 had shown it only with the rule and a wiring
  guard; it is now **driven through the real Publish route**: draft revision
  staged with the old head, then the real SEO POST and a verification pair on
  the live head, then `GET /draft` and `POST /publish`. The pointer moves to
  the draft version, and the live head keeps the new description and the
  verification pair, with the version's own fields live. This case passes on
  `fdf73825a` unchanged. Not re-fixed.
- **(b) The address half: real.** A revision's sidecar takes its `origin` from
  the public name when it is staged (`publicUrlFor`, which does not apply held
  renames). Publish overrode it only for a rename inside the published range
  (`heldRange` starts at `draft.applied`), and A11-2 keeps "the address is
  always the version's". So a rename published from an earlier revision went
  back to the old address when a later revision staged before it was
  published. Reproduced through the real Publish route with the live head's
  origin moved after the draft was staged.
- **Fix.** `carryPanelFields(..., { origin })` carries the live origin when
  asked; `runPublication` asks (`{ origin: !rename }`) only when no rename is
  in the range, so a rename in range still sets its own address. Restore is
  unchanged: its old address is A33-5, a separate finding.
- **Tests**: the real Publish case, the rule (carried only when asked, never
  from an empty or unreadable live origin), the wiring.
- **Red check.** With `worker.js` at `5ea9a1757`, the real Publish case and the
  wiring case fail.
- **Spelling guard re-anchored**, property unchanged: `test/audit-batch-3.test.mjs`
  B3-5 now accepts the extra `{ origin: !rename }` argument.
