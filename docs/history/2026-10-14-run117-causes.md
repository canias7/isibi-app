## 2. Causes — verified

**V1. A first build runs as a container job, and the job's env did not
carry the parallel doors.**
- **The runner takes builds.** Since 2026-09-14 (`34e68d92`,
  `JOB_RUNNER_EVERYONE` defaulting to `on` in `deploy.yml`) the build
  consumer fires each queued build into the site's container
  (`fireContainerJob(..., { kind: "build" })`, worker.js).
- **The job's env is a fixed list.** It is `jobSecrets(env)`:
  `JOB_ENV_NAMES` in `builder/edit-job.mjs`. That list carried
  `IMAGE_PURCHASES`, `MODEL_REPLIES` and `PROGRESS_REPLIES`, but none of
  `DESIGN_SPLIT_*`, `DESIGN_GRAPH_*` or `BAND_SPLIT_*`.
- **So the job reads every door shut.** `runSiteBuild`, running in the job,
  asks `designGraphFor` / `designSplitFor` / `bandSplitFor` of that env, and
  each answers false whatever the account. The Worker's runtime route asks
  the Worker's env, so it answered `design: true, graph: true`. Run 115's
  rehearsal read that and called the mode on.
- **Reproduced offline through the real route** (`PR 2`). With the job env
  as it was, the build designs in one call and records `bands:sync` —
  run 117's trace exactly.
- **And the Worker's own env takes the graph** (`PR 6`, and the probe in
  this round). With the flags present, the same route makes 16 design calls
  and records `graph: 16`.
- **The timeline matches.** The last first build with a graph design was
  `repairbench-1` on 09-13. From 10-04 (`the-hot-plate`) every first build is
  single-call and `bands:sync`.

**V2. In the job, the band split could never run, even with its door open.**
- The container env's queue is a refusal (`refusingQueue` in
  `builder/container-env.mjs`), so `canFire` is false.
  `bandRefusal({ canFire: false })` answers `sync` before the door is even
  asked, and the page is written in one call.
- The job has no fifteen-minute clock. The container's own build service
  already runs a list of requests at once on `/model/start` and keeps the
  answers for `/model/result`. Nothing on the job path used it.

**V3. A build sent with its own name was never listed, so a lost answer
could not be found.**
- `liveBuildStart` listed a build only when it carried no slug. The route
  itself counts a named slug with no site as a first build (`firstBuild`).
  The press names its slug, so run 117 left no marker.
- When Cloudflare reset the press's request at about 285 s (status 0, the
  route's own documented limit), nothing could find job `b6360027…`.

**V4. The press dropped the network error and judged a running build.**
- `postLong` kept `why: "ECONNRESET"`, but `runBuildCheck` stored only the
  status.
- With no job it skipped every poll and read the source, the trace and the
  ledger at once: "pages: []", "done false", "no job to attribute charges
  to".
- Red check: the old `runBuildCheck`, driven on the lost-connection
  scenario, keeps `{status: 0, job: ""}`, makes 0 polls and cannot
  attribute charges.

## 3. Legitimately sequential, not defects

- **Dependent work stays in order**: the design before the database, the
  pages after the design, the compile after the pages. `PR 1` asserts every
  design call precedes the first page call.
- **A thin plan** (one band) is one call with the door open: `bands:thin`
  (`PR 4`).
- **Doors shut for the account** give one design call (`bands:door` on the
  page) (`PR 4`).
- **A fan-out the container will not start**, or a job it no longer knows,
  falls back to the one call (`bands:nofanout`) and still writes the page
  (`PR 5`).
- **On the Worker** (no local service, no queue) the page stays the one call
  it always was (`PR 6`).

## 4. Hypotheses — not verified

- **H1.** That run 117's job ran in the container was not observed directly:
  there is no container log. It follows from V1: the runner was on for
  everyone, and the only env in which this route takes neither door with the
  account named is one without the names. It also fits the 09-13/10-04 split.
- **H2.** Whether 16 design agents and a band fan-out inside one container
  fit its memory and socket bounds live: offline the fan-out is
  `MAX_MODEL_FANOUT` (8) at a time. Not measured live.
- **H3.** Whether the parallel build is faster live than run 117's 7.7
  minutes. Earlier Worker-side graph builds took 160–393 s for the design
  alone, so a saving is not assumed.
- **H4.** That `design-recovery` 129,004 ms is the design call's own time.
  It is the time since the previous mark; the design mark carries `ms: 0`.

## 5. Fixes (general, not tailored to any site)

1. **The doors travel with the job.** `JOB_ENV_NAMES` adds
   `DESIGN_SPLIT_CANARY`/`_EVERYONE`, `DESIGN_GRAPH_CANARY`/`_EVERYONE` and
   `BAND_SPLIT_CANARY`/`_EVERYONE`. `PR 3` derives the rule from the doors:
   every door answers the same on `jobSecrets(env)` as on `env`, for canary
   and everyone, on and off.
2. **A container-local fan-out** (`containerPagesFanLocal`, worker.js).
   - In a job (`SITE_BUILD_CONTAINER.local`) with no fire, a list of band
     requests goes to `/model/start` and is polled on `/model/result` where
     the job stands. One request stays synchronous.
   - A start that does not land, or a job the container no longer knows, is
     the existing `noFanoutError()` fallback. The wait is bounded by the
     calls' own cap per round of 8.
   - `bandRefusal` and the band door read `canSplit` (the fire, or the local
     fan-out).
3. **The runtime route reports the job's view** (`jobDesign`, `jobGraph`,
   `jobBands`, `jobBandsEveryone`, booleans like every field on the route).
   The press's `buildFlagsVerdict` judges a mode by the job's view while the
   runner takes builds, and names the Worker's view beside it when the two
   differ (`PR 14`).
4. **Every build send is listed, with the caller's attempt key.**
   - The marker and the listing carry `attempt` (a caller-made random key,
     read strictly by `isAttempt`).
   - A named send is listed but claims no chat. An unnamed browser build
     claims its chat exactly as before (`PR 7`, `PR 8`).
5. **The press reconciles by its own attempt** (`attemptMatch`,
   `traceAttribution`, `runBuildCheck`).
   - The original answer is kept as it came, error included.
   - With no job, the fresh session finds exactly one listed build carrying
     this send's key and follows it to its end. It never takes the latest
     for the slug and never sends again; none or two matches is no job
     (`PR 9`, `PR 10`).
   - The trace is taken only when it falls inside the job's own row's life.
   - Charges are attributed by the job's ref, as before; another attempt's
     rows count as other.
6. **A free judge of one finished build** (`judgeBuild`, mode
   `judge-no-images` with a `job` box on *build as owner*).
   - It reads the stored source, the bound trace, the order, the overlap and
     the job's own ledger rows.
   - It sends nothing and charges nothing. It is the owner's way to read
     run 117's source without minting a credential here (`PR 12`, `PR 13`).

**Production acceptance.** The queued request still waits for the result
(`awaitJobResult`, up to 16 minutes), and Cloudflare still resets it at
about 285 s. The work survives that (the queue), as it always did; what was
lost was the caller's way back to its job. That is fixed by the listing of
every send and the attempt key, not by changing the answer's timing. The
browser's unnamed builds were already listed by chat and are unchanged.
