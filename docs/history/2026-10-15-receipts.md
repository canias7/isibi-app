## 1. A completion receipt is history, not proof the file still exists

**What Codex reproduced.** `handleMediaStatus` and `handleMediaComplete`
returned a finished session's saved file without looking at the object, so the
page answered `reused: true` for a file deleted after it was uploaded.

**What happens now (`site-media.mjs`).**
- **The object is read as it is now.** Every answer that would hand a finished
  upload's file back first reads the object (`whereNow`): a repeated
  `complete`, `status`, and an abort after the finish. There are four outcomes:
  - **here**: the object exists and still carries this upload's id (`up`). The
    file is answered, as before.
  - **missing**: deleted, or moved by a build. `status` says `removed`. A
    repeated `complete` answers `410 removed`, with no file.
  - **other**: the address holds another upload's bytes, a replacement.
    `status` says `replaced`. A repeated `complete` answers `409 replaced`. The
    original's receipt never hands out the replacement's address as the
    original.
  - **unknown**: storage cannot be read. The answer is `503 unreadable`, never
    done and never removed.
- **A repeated `complete` never writes.** It does not close an upload again, so
  it cannot bring back a deleted file or write over a newer replacement.
- **A replacement whose file was deleted while it was being sent** is not
  closed: closing it would recreate the deleted file. It is given up (`410
  removed`) and its reservation released.
- **A part sent after the finish** is refused without the file attached.

**What the page does now (`public/site-media.js`, `chat.js`).**
- `removed` and `replaced` mean the record is dropped and the file is sent
  again as a new file, at its own new address and with its own bytes. It is
  never reused, and the replacement's bytes are never taken for the original.
- `503 unreadable` is "not confirmed yet": no reuse and no re-send until it can
  be checked.
- A chip being re-checked says "deleted from your library" or "replaced in your
  library" when the file was removed or replaced.

## 2. The ledger's repeated state

**What Codex reproduced.**
- The R2 double had set every etag to `md5(bytes)` plus a counter and called
  that R2's behaviour. Cloudflare's own Miniflare uses a content MD5 for
  ordinary writes and a separately generated `version`.
- With real etags, an existing empty ledger can return to identical bytes:
  1. Admission A reads the empty ledger and zero usage, then pauses before its
     conditional write.
  2. B reserves 60 bytes, finishes its file, and releases its reservation. The
     ledger is back to the same empty JSON, with the same etag.
  3. A's stale etag matches again, and A admits another 60 bytes under a
     100-byte, one-file limit.

**What happens now.**
- **Every ledger write is a new revision.** The record (`v: 2`) carries a
  revision that only grows (`rev`) and the id of the write (`w`). No two writes
  are the same bytes, so an etag read once is never matched again, and a stale
  reading of usage can never be written over a newer ledger. An old-shape
  ledger (`{ v: 1, held }`) reads as revision 0.
- **The double now gives R2's etags, no stronger:**
  - an ordinary write's etag is the MD5 of its bytes, and the same bytes written
    again carry the same etag;
  - each write gets its own `version`;
  - a part's etag is its MD5;
  - a finished multipart upload's etag is the MD5 of its parts' MD5s and their
    count (nothing relies on this form).
- **`hooks.beforePut`** holds a request between its read and its conditional
  write, which is how the exact interleaving is tested.

  gives R2's documented etags. Real R2 under real concurrency is not run.

  file still exists just before it closes; a delete landing between that check

  kept separate, and suggested as its own task.
