# Audit G6 — Turnstile and public RPC writes, 2026-10-22

Branch `audit-g6`, from `origin/addon-partial-2` (`841cc65c5`). Offline only:
nothing paid, no model call, no live write.

## The finding

From A30-2 in `docs/audits/2026-10-17-builder-audit.md` ("Writes through
`data/rpc/<fn>` also skip the gate, because the table name read off the path is
`rpc`"), left open by `docs/history/2026-10-22-audit-53.md` ("Not changed (kept
separate): `data/rpc/<fn>` writes still skip the gate").

## Re-verified against the code: real

- `proxySiteService` (`worker.js`) runs `turnstileGate` on every `data` POST,
  RPC included.
- `turnstileGate` reads the table as `path.split("/")[0]`. For
  `rpc/<fn>` that is `rpc`, no declared table has that name, so
  `def` is null and the gate returns without verifying. The non-object branch
  added for A30-2 does the same.
- The request then reaches PostgREST. Every non-`internal` declared function is
  `GRANT EXECUTE … TO anonymous` and `SECURITY DEFINER` (`functionSql`,
  `site-rls.mjs`), so it runs as the owner and bypasses RLS. A declared function
  whose body inserts into a `collect` table is therefore a public write with no
  spam check on a site where Turnstile is on.
- Ordinary inserts are covered: a POST to `data/<collect table>` is verified
  (and since audit 53, must be one JSON object).

## Why it was not closed here

Gating the RPC path "the same way inserts are covered" breaks the reads that
sites legitimately make on it, and the Worker cannot tell a read from a write:

- **Every RPC is a POST, reads included.** The kit's `useRpc` (a read),
  `useClaimedRow` (the claim-link read), `useCancelClaim`, `useAmendClaim` and
  `useRpcAction` all POST to `data/rpc/<fn>`
  (`builder/lovable/template/src/lib/rows.ts`).
- **None of them sends a Turnstile token.** Only the row-insert path calls
  `challenged()`; the widget sits on the `collect` form. Requiring a token on
  `rpc/*` when the secret is set would refuse every RPC on every protected site,
  including "manage your booking" links and slot counts.
- **There is nothing to classify by.** The stored spec keeps
  `{name, args, returns, internal, language}` with no body and no volatility,
  and `functionSql` emits every function as the default `VOLATILE`. Reading the
  body for `INSERT`/`UPDATE`/`DELETE` would be a keyword rule (refused by the
  working rules) and misses a function that calls another.

So any fix needs a decision, which is the owner's:

1. **Declare it.** Add a field to a declared function (e.g. `public: "write"`,
   or reuse the access word of the table it writes), have `normalizeSchema` keep
   it, and have `turnstileGate` verify `rpc/<fn>` when the function is marked a
   write and the site has a secret; the kit's `useRpcAction` sends the token as
   the insert path does. Reads stay ungated. Needs the addon cleaner and the
   builder prompts to set it, and old specs default to ungated.
2. **Emit volatility.** Have `functionSql` mark read functions `STABLE`, and
   have the kit call reads with GET (PostgREST runs GET read-only); then gate
   every RPC POST on protected sites. Changes every existing site's calls.
3. **Accept it**: a write function exists only where the model declared one,
   and claim functions already require a secret token. Record and leave.
