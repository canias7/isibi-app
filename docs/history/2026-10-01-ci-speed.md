## 2. What was cut, and why each cut is safe

**Sections.** The file's 298 top-level statements after the preamble were
analysed for which names each one reads, with scope resolution (an inner
`const broken` shadows an outer one; the first, naive pass over-counted and
found 16 cut points instead of 46). Two spans cannot be cut, because one
variable runs through them: `rounder` (statements 81–129, 294 s) and the logo
cluster (154–288, 268 s). Each section's time was taken from the CI log by
mapping every check line to its statement.

The 27 sections are blocks `if (SECTION("name", shard)) { … }` around the
original lines, **not re-indented**: the diff to the harness adds lines and
changes one (the port, now `SITE_BUILD_PORT`, default 8123). No check, message
or condition changed.

**Names.** A section is a block, so one that read another's `const` would
throw. `test/site-build-shards.test.mjs` resolves every name in the 27
sections with TypeScript's own binder: 4,219 references, none reaching into
another section, none writing or mutating a variable outside every section
(no section assigns `passed`, pushes into a shared list, or the like). The
reader is proved alive first: each kind of coupling is planted in a small
source of the same shape and must be named.

**State.** Names are not the only coupling: a check can rely on what an
earlier BUILD left in the sandbox or the service. Read for in the file, three:

- *"the previous build's extra route is gone"* relies on the builds that
  wrote `menu.tsx` (`unusable-style`) and the rebuilds after them
  (`refusals`);
- *"a build that sends no logo carries none"* relies on the one earlier build
  that HAD a logo (`two-page`), and
- *"a build that names no language keeps the one the template had"* on the
  same build, which sent `pt-BR`.

Each names what it relies on (`{ needs: [...] }`), shares its shard, and
refuses to run unless that section ran first in the same process. Without it,
in a fresh shard, the leak checks would pass over nothing.

**Order.** The stopping check (SIGTERM under a hold) ends the service, so it
stays the last section of the file and so of its shard.

## 3. The workflow

`site build` runs seven jobs at once, each on its own runner, then a gate:

- **kit and generator checks**: page-gen and publish-pages tests,
  kit-typecheck, kit-render, contrast-cases, kit-a11y, kit-effects, kit-paint;
- **theme checks**: theme-seam, theme-render and its screenshots;
- **published-site checks**: site-routing, site-runtime;
- **site-build.mjs, shard 1–4 of 4**: the harness with `SITE_BUILD_SHARD`, its
  own build service, sandbox and port; each writes a report of what it ran,
  check by check, and uploads it even when it fails;
- **all checks** (`scripts/site-build-gate.mjs`): runs unless the run was
  cancelled, and is green only when every job above succeeded and every
  section the harness declares ran exactly once, in the shard it names, on
  this commit, from this harness file, complete, with at least one check and
  none failed. Anything else is red and named: a skipped or cancelled job, a
  missing or second report, a report from another commit or another harness,
  a whole-file or hand-picked run passed off as a shard, a section run twice,
  nowhere or in the wrong shard. It writes the table to the run's summary page.

Within each job the checks keep their old order and the rule that each runs
even when an earlier one failed. The npm cache is kept in every job, on the
same key. A push to a branch cancels that branch's older `site build` and
`unit tests` runs still in progress; no other workflow cancels anything (a
guard holds it to those two). `deploy.yml`, the image predictor and the
image's reuse are untouched: the image is `c051f625db27b5b7` from the same
189 inputs before and after this change.

**The trigger keeps every path it had**, `worker.js` and the image's other
inputs included. It gains what the jobs import from `test/` and nothing
named: the shared site server (`test/integration/lib/`), the theme and
page-gen fixtures and their data, `test/publish-pages.test.mjs`, and the
gate. Found when the gate began to fingerprint the inputs; a guard now walks
the import graph of every script the jobs run.

## 4. Evidence that matches the commit being merged

The gate prints `site build inputs <hash> (<n> files)`: a sha256 over the
path and content of every tracked file the trigger names. The same number for
any commit:

    node scripts/site-build-gate.mjs fingerprint <rev>

So before a merge, `all checks` is evidence for the candidate when it ran on
the candidate itself, or when the candidate's fingerprint equals the one the
gate printed (the commits between touched nothing these checks read, such as
documents). Measured: `2188f706`, `85f8702b` and `e0787733` (two documents
commits on top) all print `013d6f9775c3ab8f` over the old trigger.

## 6. During corrections, and before a merge

- **Each push**: `unit tests` (the whole unit suite, about 2½ minutes) and,
  when the push touches its inputs, `site build`, whose jobs report as they
  finish. A newer push cancels the older runs.
- **While correcting**, locally: the focused unit tests, and the sections of
  the harness the change touches, e.g.
  `SITE_BUILD_SECTIONS=job-door,job-stop,job-build node test/integration/site-build.mjs`
  for the job runtime in the image, or one shard with `SITE_BUILD_SHARD=n`.
  A `SITE_BUILD_SECTIONS` run is never evidence: the gate takes shard reports
  only, and CI never sets it.
- **Before a merge**: `unit tests` green on the candidate, and `all checks`
  green on it, or on an earlier commit with the same inputs fingerprint.
