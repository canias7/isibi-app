## Full-text search (`_fts`) in the draft preview

**Not added: it needs a design decision.** The kit's search box
(`pgQuery` in `builder/lovable/template/src/lib/rows.ts`) sends
`_fts=fts.<q>`; the `fts` column is a generated
`to_tsvector('english', …)` queried through `to_tsquery`. Unlike
`like`/`ilike` (added earlier today,
`docs/history/2026-10-22-preview-search-reload.md`), its result cannot be
reproduced exactly over the merged rows in the Worker: stemming, the
English stop-word list and the parser's own tokens (hyphenated words, URLs,
numbers) decide what matches. Any approximation would sometimes show a
held row the database would not, or hide one it would. So `_fts` on a table
with held changes stays answered 422 (an honest refusal), and on an
untouched table it already passes through to the live data service.

The options for the owner:

1. **Ask Postgres itself** (exact): for each held insert or update, evaluate
   `to_tsvector('english', <the row's text columns>) @@ to_tsquery('english', $q)`
   with a read-only query on the site's own database (no table write), and
   keep the held rows it answers true for. Costs one extra database call
   per preview search on a touched table and needs the generated column's
   expression read from the schema.
2. **Approximate in the Worker** (a stemmer and stop list): cheap, but
   wrong at the edges; not recommended for a preview the owner judges
   before publishing.
3. **Keep the refusal** (today): honest, but the search box on a touched
   table shows an error until Publish.
