## 1. The served-section reader (fixed)

**Defect.** `servedLines` (`scripts/canary-requests.mjs`) stripped tags with
`<[^>]+>`. That ends a tag at the first `>`, even inside a quoted attribute.

The opened accordion's button carries Tailwind's
`[&[data-state=open]>svg]:rotate-180` in its class. So
`svg]:rotate-180 text-start" data-radix-collection-item="">` leaked into the
question's line, the one added section read as two, and a right page failed
"exactly one section".

**Fix.** One tag pattern, `<\/?[A-Za-z](?:"[^"]*"|'[^']*'|[^'">])*>`, used
for the block breaks and the tag strip alike. Comments and declarations are
removed by the same pattern. A tag now ends only at a `>` outside its quoted
values. Visible text keeps its `>` and `<` (escaped as `&gt;`/`&lt;` in
served HTML, and a bare `>` in text passes through).

**Tests** (`test/canary-served-attrs.test.mjs`, 4 cases):
- **ATTR 1**: run 141's saved evidence gives one section, "When is the list
  updated? Every Monday morning.", and every check passes.
- **ATTR 2**: no attribute text in any line of either saved page.
- **ATTR 3**: quoted `>` in double- and single-quoted attributes, on block
  and inline tags; visible `>`/`<` kept; comments gone.
- **ATTR 4**: controls on the same evidence. A wrong answer (Friday for
  Monday), a missing answer, and a second stating section still fail.

**Red check**: ATTR 1–3 fail on the old reader, and the control ATTR 4
passes there.

**Sweep**: 5 of 5 mutants killed, and the comment control survived. A sixth
mutant (dropping a separate comment strip) survived. That strip was
redundant, since the tag pattern already removes comments, so it was taken
out rather than kept untested.

**Not changed (kept separate)**: `visible` in `scripts/canary-additions.mjs`
and the other helper strippers (`addon-sweep`, `gap-sweep`, `lane-sweep`,
`edit-canary`) still use `<[^>]+>`. Recorded in the backlog.

## 2. Why job 996afba7 replayed 1 answer and asked 3 again

### How reuse is decided (read from the code)

There is no staleness test, no site-version check and no per-file hash. A
recorded answer is replayed only when the new call's request has the same
SHA-256 fingerprint as the recorded one:
- the fingerprint is `requestHash` (`builder/prepared.mjs`): model, system,
  messages, tools, tool choice and sampling fields;
- each recorded answer is used at most once (`replayer().wrap`);
- an answer with a verdict is never staged or replayed (`readPrepared`): cut
  off, or refused by its step's own validation (`rejected:<step>:<reason>`,
  VA 0–5).

The earlier backlog note ("judged stale after the Gallery publish") described
a mechanism that does not exist.

## 3. Verifying task isolation without assuming the router's order

**Why run 141 could not show it, and what a scoped Add-on already
guarantees.**
- A scoped Add-on's writer is shown only its own pages. In run 141's shape it
  could not have rewritten `/gallery` whatever the markings said.
- The markings matter where the Add-on is shown the other part's target:
  - the same page;
  - an unscoped or widened writer;
  - the picker's and designers' reading of the message.

**The prepared check: `acc-isolation-page`** (canary scenario; not pressed,
not in the balance opt-in).
- *The request*: on the Bake List,
  - a questions section ("Can I leave the list?" → "Yes, reply STOP to any
    note."),
  - and an edit that **appends** " — sent every Friday" to the heading "Join
    the weekly bake list".
- *Why it works in either order*:
  - both parts are on the same page, so the Add-on's writer is shown that
    heading whichever part runs first, with the edit's words marked as
    another part's;
  - an append is not idempotent, so a stray application shows:

| Which part runs first | What a stray application leaves |
|---|---|
| the edit | the phrase twice |
| the Add-on | the phrase twice, or the edit part with nothing to do |

**The verdict, `isolationVerdict`** (`scripts/canary-requests.mjs`), read from
evidence the press already saves. It passes only when all of these hold:
- the request was split into one `text` part and one `addon` part;
- the text part's own job applied the change, with `changed` naming the
  phrase and `applied ≥ 1`, read off its final poll;
- the served page carries the phrase exactly once;
- the phrase stands straight after the heading.

Any other split is **not exercised**. It becomes a failed, named check plus
an "unverified" line, never a pass and never a breach. The order is recorded,
never judged.

**What remains router-dependent**: whether it splits at all. If it batches
both into one Add-on, isolation is not exercised and the press says so.

**Cost estimate**: 12–26 credits (routing 2–3, the heading 1–3, the Add-on
7–15, its judgment about 1); run 141 cost 16.

**Tests** (`test/canary-isolation.test.mjs`, 8 cases):
- either order passes;
- twice fails;
- the edit part finding nothing to do fails;
- an unexercised split is never ok;
- missing evidence is never a pass;
- the check is wired into the press verdict;
- the scenario agrees with itself.

**Sweep**: 7 of 7 verdict mutants killed. Two of them first survived and
were killed by two added cases: applied 0 with a matching `changed`, and
words between the heading and the phrase. The comment control survived.

## 4. The minimal evidence that the model received the markings

Model inputs are not kept. `edit_traces` holds events, and a preparation keeps
only each request's fingerprint. So no run, past or future, can show what a
step's model saw.

**The smallest sufficient record**: one trace event per model call of a
request part, written where the markings are added (`withPart`, through
`clarifyTransport` and `clarifyCall` in `builder/clarify.mjs`). It would
carry:
- the call's name (`pick_adds`, `add:<kind>`, `judge`, `pages`, a text or
  data step);
- the number of `⟦ANOTHER PART: …⟧` spans it carried;
- whether the isolation rule sentence was present;
- the number of other-part spans found in the request **outside** a marking
  (must be 0);
- whether the call was replayed or asked.

That is integers and a name, with no prompt text. A replayed call still forms
its request, so the job records it either way.

**For the preparation side**: the same counts on the preparation record's
entries, or preparation traces written to `edit_traces` (they are not today).

**Not implemented**: it is product code, useful only once deployed.
