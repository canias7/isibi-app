# 2026-10-22 — decide-3a: a held add-on schema tried on a Neon branch (A04-3, option A)

Branch `decide-3a`, from `origin/combine-groups` (`36671236e`). Offline only:
nothing paid, no model call, no live write, no secret read.

## What changed

- `builder/addon-rehearse.mjs` (new, pure, every network step injected):
  `addonDryRunOn` (`ADDON_DRY_RUN`, on unless `off`), `rehearseHeldSchema`
  (sweep stale rehearsal branches, create a branch off the site's branch, get
  its connection for the site's database and role (read from the site's own
  connection string), apply the spec with `applySiteSchema`, delete the branch
  in a `finally`, time it), and `heldFromRehearsal` (what is held and what is
  answered).
- `site-db.mjs`: `createRehearsalBranch` (POST `/projects/{id}/branches`
  with a `read_write` endpoint, name `rehearse-<ms>`, then `waitForProject`;
  a failure after the create carries `branchId`), `rehearsalConn`,
  `deleteRehearsalBranch` (404 = gone), `staleRehearsalBranches` (older than
  15 minutes, never the default branch, at most 3).
- `worker.js`: `backendWriter(env, slug, { rehearse })`; when holding and
  asked, the schema is rehearsed before `hold.add`. **Only the add-on asks**
  (`aWriter`); every other writer is unchanged. The trace gets a `dryrun`
  mark (`ok` / `refused` / `skipped`, with `why`, `ms`, `deleted`, `swept`,
  counts).
- `builder/edit-job.mjs`: `ADDON_DRY_RUN` in `JOB_ENV_NAMES`. The container
  already holds `NEON_API_KEY` and provisions from there, and the project row is
  read through `siteNeonProject` (the gateway admits `site_project` GET by
  slug), so the rehearsal runs wherever the add-on runs.
- `deploy.yml`: `ADDON_DRY_RUN: ${{ secrets.ADDON_DRY_RUN || 'on' }}`, and the
  name in the secrets list.

## What the result does

- A function the copy refused: taken out of `made.functions`, named in
  `made.functionErrors`, removed from the held spec with every held job on it.
  The add-on's existing code then names it, blocks its jobs by name
  (`aBlocked` → `jobErrors`) and keeps them out of the held jobs op, so the
  reply never says "made" for it.
- A Postgres refusal of the whole apply (a table): thrown before anything is
  held, into the add-on's existing apply-failure path (`{ ok: false }`,
  refunded), as on a site that is not yet published. That path's wording
  ("ours") is today's, not changed here.
- Rules the copy refused ride on `made.refusedRules` (the existing reply
  reads them).
- Not run (switch off, no key, no project row (legacy per-account
  projects), project unreadable, branch create failed, copy unreachable):
  exactly today's hold, with the reason in the trace.

## Orphaned branches

Deleted in a `finally`; a half-made branch from a create that failed to settle
is deleted too. A delete that did not land is removed by **the next rehearsal
on the same project** (new bounded sweep, at most 3 a time, older than 15
minutes). A site that never gets another add-on keeps its orphan: no tick
sweeps them. Neon's branch expiry (`expires_at`) was not used, since it could not be
checked offline. If Neon refused the field, every create would fail, and the
feature would quietly fall back for everyone.
