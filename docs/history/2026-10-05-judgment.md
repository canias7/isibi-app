## 2. The split, on the owner's line

| | who | what |
|---|---|---|
| provenance | code | the quoted words are in what they wrote (`groundRequirements`, unchanged) |
| meaning | the model | whether the requirement follows from those words, and which designed or existing thing carries it out (`judge_requirements`) |
| execution | code | every thing the judgment names must be one it was shown, and must really have been applied or already be there, with the part of a table that does the work |

**No word list, no site exception, no rule about what a kind of thing can
do.** Code compares ids it printed itself, verdicts against their own
constants, and a table's parts against the table as stored.

## 3. What changed

### The judgment (`builder/site-add.mjs`)

- **One small call** (`runJudge`, `judge_requirements`), on the add step's
  own model (`.quick`), through the same transport as every designer (so it
  is shown the customer's answers to earlier questions, and the job's clock
  reaches it). Its rules and tool are cached.
- **It is shown**: what they asked; every requirement the designers kept,
  one JSON line each (its need, basis, quoted words, status, the step that
  wrote it, its own reference); and every thing this request designed or the
  site already has, each under an id the code wrote (`judgeItems`).
- **It answers, per requirement**: `follows` — `asked`, `needed` (what they
  asked cannot work without it), `optional` (it would go well, but what they
  asked works without it) or `unrelated`; `carried` — `yes` (with `by`, the
  ids of what does the work), `no` or `unsure`; and a one-line `reason`. It
  may ask a question instead, when a choice only the customer can make
  changes what gets built — never about an optional extra.
- **Its rules say, in words, what a quote is not** ("A real quote does not
  make the requirement theirs") **and what a thing that only keeps
  information does not do** ("a table that stores email addresses sends
  nobody an email"). When torn between `needed` and `optional`, it answers
  `optional`.

### What a table does (`tableParts`, `builder/site-add.mjs`)

A table's working parts are their own ids, read off the table as stored, one
reader for the applied facts, the existing facts and what the judgment is
shown:
- `notify` — the owner is emailed about each new row: a `collect` table a
  visitor may still write to (`shouldNotify` sends it from that POST);
- `confirm` / `sms` — the person who added the row is emailed / texted:
  only where `normalizeSchema` kept the declaration (`normalizeConfirm`,
  `normalizeSms`);
- `webhooks`, `payment` — another system told; a card payment.

So `table:signups` and `table:signups:confirm` are different things, and
"this table exists" is never "this table emails somebody".

### The checks (`builder/site-requirements.mjs`)

- **`readVerdicts`**: a verdict about an id it was not shown, a repeated
  one, one missing `follows` or `carried`, and a thing it names that it was
  never shown are dropped **and counted** (`verdictsInvalid`), never
  repaired. A `yes` naming nothing checkable reads `unsure`.
- **`applyVerdicts`**: meaning is judged once; what carries it out at the
  end. An `optional` requirement leaves the list and is offered as a
  suggestion — unless what it names already does it, when "nothing was made
  for it" would be false, so it is only recorded. An `unrelated` one leaves
  the list and is recorded (`setAside`). One with no verdict stays,
  `unjudged`.
- **`requirementOutcomes` with `judged: true`** (the route always passes it;
  every other caller reads exactly what it always read):
  - **unjudged → never told** (recorded with `unjudged: true`, counted on its
    own);
  - **`carried: yes`** → the named things are looked up in what was applied
    and what the site already has (`carriersReading`), in the order the
    unjudged reading decides in: a named thing that failed → `blocked`; the
    owning step failed over a thing not there → `failed`/`blocked`; not there
    → `missing`; **the table there without the part that does the work →
    `missing`** ("the signups table does not do this"); nobody could look →
    `unknown`; all there → `unverified` / `configured`, as before;
  - **`carried: no`** → `missing` ("Still to do"), unless the owning step
    failed;
  - **`carried: unsure`** → the designer's own reference, read as before, but
    **it can no longer buy "I've set that up"**: a positive state is capped
    to `unknown` (`capped: true`). That cap is the owner's rule in code: a
    referenced thing being there is not the behaviour.

### The route (`worker.js`)

- **Before a hand-off**: the requirements about to be handed to the next step
  are judged first (meaning only — nothing has been designed for them), so an
  extra is never handed on to be built. What has no verdict is not handed.
- **After the last designer**, before anything is applied or charged: every
  requirement is judged with everything designed in view. A judgment that
  fails stops the addition as a designer's failed call does (`aDown`, cost
  0); one that asks is the addition's question (cost 0, nothing applied).
- **A designer's refusal** judges first, so its cover note tells only what
  follows from their words.
- **The cover note, the record and the trace mark** all read with
  `judged: true`; the record keeps `setAside` and `verdictsInvalid`; the mark
  counts `unjudged` and `setAside`.
- **Billed with the designers' calls** (`aDesignUsage`).
- **The judgment is shown what a requirement names explicitly, even when no
  designer planned it** (said to be in neither list), because it runs before
  the page writer: run 53's shape, a page the writer published that no
  designer declared, would otherwise be unnameable. Whether it is really
  there is read afterwards, as for every id.

## 7. Limits, stated

- **Nothing here is shown live.** The judgment is one more model call on a
  paid path; it has run only against supplied answers.
- **The judgment's quality is the model's.** Code checks that what it names
  was shown and really ran, and that a table has the part; it cannot check
  meaning. A model that calls an invented email `needed` and names the
  table's own `confirm` part, which the designer really added, would still
  read "I've set that up" — the part exists. What the old path could not do,
  this one does: a table that merely exists no longer counts.
- **It is shown the design, not the result.** The last judgment runs before
  the pages are written; a page no designer planned is nameable only when a
  requirement names it explicitly.
- **A designer that builds an extra anyway is not undone.** The judgment
  decides what is handed on and what is reported; a part a designer put into
  its own answer for an extra it also declared is built. An `optional` one
  is then recorded, not offered.
- **Cost**: one more small call per add-on that declares requirements, and
  one more before each hand-off. Estimated from token counts, not measured:
  about +1 credit on a typical add-on with the default model (`grok-4.6`),
  up to +3–4 for a large request with a hand-off.
- **The route harness shares one stored-schema cache between cases** (every
  slug has the same database connection, and `readSiteSchema` caches by it),
  so a case can start from an earlier case's applied schema. Found here (a
  JUDGE 10 sub-case read the previous case's confirmation); the new file
  clears the key per case; the harness-wide fix is a backlog item.
