## What it does

- **#12, browser errors as data.** `render-check.mjs` now keeps, for each
  route, every uncaught exception (`pageerror`), unhandled rejection (an init
  script logs one in a marked form, and Chromium's own `Uncaught (in promise)`
  is recognised too) and console error, as `{ kind, message, source }`. The
  source is `file:line:col` from the stack or the console location, or null.
  `site-render.mjs` (`runtimeErrorsOf`) dedupes by route, kind and message,
  merges a rejection that was also reported as an exception into one entry,
  caps the list (5 per route, 20 in all, 300 characters a message), counts the
  rest (`runtimeMore`) and carries it as `report.runtimeErrors`. A clean report
  is byte-identical. The observer's own console line never reaches
  `consoleErrors`, so the findings are unchanged.
- **#11, one compile repair before salvage.** In `publishPages`, when a
  compile fails in a way salvage can answer (`salvageable`), the pages the
  error cites that this build wrote (at most 3) go to the build's pages model
  through `runTweak` with `COMPILE_REPAIR_RULES`. Each gets its source, the
  bundler's exact error, tsc's lines for that file, and the cited lines. The
  container now also returns `typeErrors` beside a failed vite build
  (`build-server.mjs`). A fix that compiles replaces the build and the stored
  source. One that doesn't compile, or a refusal, leaves `built` and `pages`
  untouched, and salvage runs exactly as before. There is one try and no loop.
  The usage goes into `repairUsage`, so the single `pageCredits` call prices it
  on the build's ref. `out.compileRepair` records what was tried, fixed,
  refused or skipped, the named causes, and the failed recompile's stage.
- **The runtime half reuses the existing repair pass** (`repairPages`, the
  `repair: quickSend(env)` dep). Under the switch, its instruction also carries
  the route's `runtimeErrors` and the named cause (`runtimeLines`). It still
  uses the quick model, as before; only the compile repair uses the pages model.
- **#13.** `namedCause` turns the known forms into the real cause: a missing
  export, an unresolved module (vite or TS2307), TS2305, a duplicate
  identifier, an undefined name, a read off undefined, a hook outside its
  provider, a route-file transform error whose fault is the SyntaxError inside
  it, and a real path problem (ENOENT, invalid route path). Anything it doesn't
  recognise answers null, so the model gets only the raw error and no guess.
  `failureSignature` (path plus the message without line numbers, directories
  or hashes) is recorded per page per build in one `tried` set, shared by the
  compile and render repairs. A recorded signature is never sent again
  (`skipped: same-error`).
- **Progress.** `compile-fixing` gives "Fixing a page that didn't build…".
  `compile-fixed` gives "Fixed it", or "Couldn't fix it, so it's a placeholder
  for now" (it says placeholder only when salvage really stubbed the page,
  otherwise "Couldn't fix it."). Both are mapped to `publish` in
  `build-budget.mjs`.

## The switch

`BUILD_REPAIR` defaults to off and is read like `VISUAL_REVIEW`. Any
affirmative word turns it on. When it is off, the Worker supplies no
`compileRepair` dep. With no dep, no compile repair runs, the render repair's
request is byte-identical to before, and nothing changes. The one exception is
the container's extra `typeErrors` field on a failed vite build, which nothing
reads unless the switch is on. That change rolls the container image.
