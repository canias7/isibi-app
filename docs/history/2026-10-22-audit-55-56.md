# Audit findings A31-2 and A31-3 (2026-10-22)

QR code findings from `docs/audits/2026-10-17-builder-audit.md`, re-checked against `codex-work-into-claude` and fixed on `audit-55-56`, one commit each. Offline; nothing spent, nothing deployed.

## A31-2: text above U+00FF cut to its low byte (real)

- **Re-check.** `qrSvg` called `qr.addData(read.text)`; `qrcode-generator`'s byte mode pushes `charCodeAt(i) & 0xff` and has no UTF-8 option or ECI. `qrEncodes` built its reference the same way, so a cut drawing passed. Shown by the red tests: the Łąka wifi code, `Кафе`, `中文` and `Joe’s` drew the same matrix as their low-byte strings on the old code.
- **Fix** (`19250f5c4`). `qrBytes(text)` (`builder/site-qr.mjs`) turns the text into its UTF-8 bytes, one per character, and `qrSvg` adds those. The byte-mode length is the byte count. No ECI header: the library cannot write one, and scanners detect UTF-8. `qrEncodes` builds its reference from percent-encoding (`unescape(encodeURIComponent())`), not from `qrBytes`, so the two cannot share a loss. `readQrText` refuses a lone surrogate ("a broken character"), which has no UTF-8 form. `scripts/lane-sweep.mjs`'s matcher reads UTF-8 too. ASCII drawings are unchanged. A Latin-1 accent such as é now draws as UTF-8, so its matrix differs from the old one.
- **Tests.** `test/qr-utf8.test.mjs`, 9 cases: é, Chinese, emoji, Polish wifi and a curly apostrophe each match a reference built from Node's `Buffer` UTF-8 bytes; above-U+00FF text differs from its low byte; `qrEncodes` refuses a cut drawing; ASCII unchanged; a lone surrogate refused. **Red check**: 8 of 9 fail on the old code.
- **Container.** `builder/site-qr-list.mjs` is imported by `build-server.mjs`, so the image rolls on the next deploy.

## A31-3: a revise replaced the whole code list (real)

- **Re-check.** The revise design call still gets `currentStateNote`, which says "to change one, name it in `qr`". The build route merged with `mergeLook(priorLook, designed, body, { instructed: !!editState })`. On that path the designed value comes first, and `keepsValue('qr')` is just "non-empty", so a one-entry answer became the whole list. The red test "without the fold" shows it: `[ring, wifi]` plus a wifi-only answer gave `[wifi]`.
- **Fix** (`729d56b08`). `foldQr(stored, designed)` (`builder/site-qr-list.mjs`) replaces each named code in place, appends a new name, keeps every code it does not name, and stays within `MAX_QRS`. A `qr` with no usable code comes back as it was sent, so the merge's absent-field rule still keeps the stored list. `worker.js`'s revise merge folds `designed.qr` this way when `editState` is set. The add-on (`foldAdds`) and the edit lane (`patchQr`) were already per code and are unchanged. Not changed here: whether a revise may create a new code (the audit's `ADD_ONLY_FIELDS` remark), and removing figures for a dropped code (nothing drops one now).
- **Tests.** `test/qr-revise-fold.test.mjs`, 9 cases: the note's wording, the defect without the fold, changing the second code or the first, a new name appended, absent, empty or unusable answers kept, the legacy single code, the cap, and a source guard that the route merges `qrFolded`. Shown at module and source level. The test does not drive the build route. **Red check**: 7 of 9 fail on the old code.
