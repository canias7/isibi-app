## A26-1 — a revise whose stored look cannot be read stops, refunded (`7894defa8`)

- **Finding.** In the full revise (`POST /api/site/react-revise`), the read of
  the site's config was wrapped in a catch that logged `look read failed:` and
  carried on with `priorLook = null`. `mergeLook(null, designed, …)` then had
  no owner's mark to keep, and `patchSiteConfig(env, slug, db, { look })`
  wrote the merged look over the stored one. Since 2026-09-07 the uploaded
  logo and tab icon live inside the look (`{form:"image"}`), so one storage
  blip during a revise deleted them for good. The comment that justified the
  swallow ("can never be worse") stopped being true when the marks moved.
- **Fix** (`worker.js`). A failed read is cannot-tell: the revise stops
  before anything is written, gives back what it took (`refundFields()`), and
  answers 503 `look-unreadable`, `ours: true`, with
  `REVISE_LOOK_UNREADABLE_MSG`. The same shape as the revise's unreadable
  schema (`REVISE_DB_UNREADABLE_MSG`) and the edit spine. An absent config
  still reads as `ok` (nothing stored), so a first build is unaffected (the
  read is inside the revise gate).
- **Test** (`test/revise-look-unreadable.test.mjs`, driven through the real
  route, every model answer supplied). The config's second read (the look's)
  is refused once; the write's own read after it succeeds, as a passing blip
  would. Asserts the stored logo and tab icon afterwards, then the 503, the
  writer never called, one reversal, cost 0. Control: a readable config keeps
  both marks and reaches the writer.
- **Red check.** On the parent the stored logo read `null` after the revise
  ("the uploaded logo was written over: null"); 1 fail, the control passes.
- **Guards updated.** `test/credit-debit.test.mjs` counts the refusals that
  reverse through the ledger (11 → 12, and 12 → 13 calls);
  `test/wiring.test.mjs` re-anchored to `console.error("look read failed:"`
  (the catch is now a block).

## A23-2 — a model call cut after the headers settles (`f994b522e`)

- **Finding.** `builder/long-post.mjs` settled only on the response's `end`,
  the request's `error` or the abort signal. A peer that closes cleanly after
  the headers (mid-body) emits none of those; and the request's `close`
  cleared the idle timer and removed the abort listener. The promise never
  settled, its own timeout could not reach it, and the site's container
  waited behind it (about an hour, per the audit).
- **Fix** (inside `long-post.mjs`'s own settle logic only; which hops use it
  is finding 40's, untouched). The response's `aborted`, `error` and `close`
  reject, when the body is not complete, with a `ConnectionCutError` carrying
  `wire` (headers time and characters). Every settlement goes through one
  `resolve`/`reject` pair that disarms the idle timer and the abort listener;
  the request's `close` disarms nothing. `settled` still guards every path,
  so nothing settles twice.
- **Test** (`test/long-post-cut.test.mjs`, a real local server: headers, one
  chunk, a clean close). Three cases (no signal; a signal 60 s out; an idle
  timer 60 s out) must reject within 3 s as `ConnectionCutError` with
  `wire.headersMs >= 0` and `wire.chars > 0`. Control: a whole answer
  resolves once with its body.
- **Red check.** On the parent all three cut cases stay pending ("the call
  never settled"); the control passes.
- **Related files.** The six test files that import `long-post.mjs` plus the
  new one: 101 / 101.
- **Not changed, noted.** `retryHere` (`build-call.mjs`) reads a status-less
  error as "no request was made", so a cut call may now be asked once more,
  as an RST (`ECONNRESET`) already was. That reading is A23-3, kept separate.
