## A04-5: a QR or 3D addition beside another part always lost its first run

- **Re-verified, real.** An add-on holds the site's turn from its start only
  when its targets name the config (`writesConfig`). A QR code or 3D scene is
  targeted as a page or component, but stored in the look (`aLookPatch`), and
  `turnStillMine` answers false for a job with no turn, so the addition always
  refused `turn-lost` ("another change in the same request took its turn")
  and was re-run alone, repeating its model calls; with a database already
  made it was not re-run and the sentence was false.
- **Fix** (`worker.js`, before the add-on's look store): a job beside others
  that does not hold the turn takes it there (`takeTurn`), marks itself a
  holder (`beside.holds`, so its publish keeps the config it stores), and puts
  the config level with the live site first (`ensureEditableState`), as a
  holder does at its start. A turn it cannot get is said as its own reason
  (`turn-refused`, `turn-timeout`, `turn-unreadable`, or `turn` after the
  wait), with a sentence that does not blame another change; a turn truly
  lost still answers `turn-lost` as before. A state check that fails answers
  `read`, saying the database was made when it was.
- **Guard**: `test/addon-look-beside.test.mjs` ALB1. A QR addition (targets
  `component:qr`) runs beside a text part that stays open until the addition
  has answered. Red on the old code (`turn-lost`), green after: the first run
  lands, it runs once, both parts done.
- **Sweep** 4 of 4 killed (the take removed, the gate off, the gate inverted,
  the state check always refusing); comment-only control survived. Related
  files (`addon-beside`, `addon-look-beside`, `addon-failure-outcome`):
  32 / 32.
- **Not changed**: the overlap re-run still does not proceed when a database
  was made (`leftOf` = partial). With this fix the case that reached it no
  longer fails, so it is left as it is.

## The live `no-job-fn`: a job naming a function nobody declared

- **Why it could happen.** Each add-on kind is its own model call; `job`
  runs after `function`. The route hands the job designer `jobFns` (stored
  internal functions plus the ones the function designer declared a step
  earlier), and `siteNote` prints them ("The functions a scheduled job may
  run are: …"). But the job rule (`builder/site-add.mjs`, `ADDS.job.add.yours`)
  said the function could be "one the site lists, or one you are declaring in
  this same change with `internal: true`", and the job tool has no field to
  declare a function. A designer that read the request ("count the sign-ups
  weekly") could name the counting function it expected, whether or not the
  function designer wrote one (not picked, refused by its cleaner, or named
  differently), and `cleanAdd` refused it `no-job-fn`.
- **Small fix made**: the rule now says the name must already be on the list
  of functions a job may run (which includes those declared a step earlier),
  that no printed list means none, that it cannot declare one here, and that
  when none fits it designs no job and lists the missing function as an
  unsupported requirement. Guard `test/addon-job-fn.test.mjs` (AJF1 red on the
  old wording, AJF2 the list is printed); sweep 4 of 4 killed, control
  survived; `site-add*` and `addon-*`: 810 / 810.
- **Options left for the owner** (a design decision, not made): (a) let the
  job tool declare its function with the job (one call writes both, so the
  name always exists); (b) when the picker picks `job`, tell the function
  designer the job's need ("a weekly job will call an internal function that
  …") so it writes one; (c) when a job's function is missing, re-ask the
  function designer once for it before refusing. The wording fix lowers the
  chance; only (a)–(c) make it impossible or recoverable.
