### 7.5 Found while reading the evidence (recorded in the backlog, not changed)

1. **The preview frame is reloaded on every reading of a running request.**
   - **The code**: the page reads a running request about every 8.6 s once
     its back-off reaches the 8 s ceiling. Every reading ends in
     `renderSites()` (`siteRequestShow`), and that rewrites the whole
     workspace through `innerHTML`, preview `<iframe>` included
     (`renderSiteWorkspace`), so a new frame loads the preview.
   - **The load record**: during message 2's two minutes the reopened tab
     requested the same `?v=11` 17 times, each within about 15 ms of one of
     the page's own readings, plus once at the send and once at the routing
     answer. None followed the canary's own reads of the request, which run
     inside the page about every 3.6 s and draw nothing
     (`requestViewInPage`).
   - **What a customer sees**: the preview blanking and reloading every few
     seconds while a request runs, which is inferred from the code and the
     record, not seen in a screenshot.
   - **Since when**: reading on every poll came with the request flow; the
     canary kept no load record before this press.
   - **Already recorded, and seen here**: the first tab's first look moved
     the preview nine times in under a second, once per earlier finished
     job, a limit already recorded in `2026-10-05-reconcile.md` §5.
2. **A page that one add-on both changed and put back is reported both
   ways.**
   - **The answer**: the add-on lists `visit.tsx` as `reverted` (its page
     step had changed the Visit page, which its part did not name, and the
     merge in `builder/site-addon.mjs` put that change back). It also lists
     it as `changed`, because the code then added the menu link there.
   - **The reply**: message 1's said "I added a Bake List page, and updated
     the home, Order, Visit, … pages" and then "The Visit page was left as it
     was; nothing there needed to change for this."
   - **The cause**: `reverted` is taken at the merge, before the menu-link
     step changes the same page, and the reply's facts state it as they
     come (`builder/site-reply.mjs`).
3. **The add-on can declare a requirement the customer did not state.**
   - **What it declared**: its requirement note named "The person who joins
     gets an email confirming they are on the list". Message 1 asked only for
     a page where people join by leaving their name and email.
   - **What it built**: a table and a page, and nothing that sends mail.
   - **The reply**: "I can't confirm from here … that they then get an email
     confirming they're on the list", which can read as though such an email
     was set up.
   - **The source**: `requirementNote` reads the requirements the add-on's
     own planner declared. Not traced further.
4. **The canary's preview checks cannot judge a closed-tab message's
   refresh when the first tab moves its own preview after the send.**
   - **What happened**: the baseline is the address read before the send
     (`?v=0`). Within two seconds of message 1's send, the first tab's own
     first look at earlier requests moved the stored address to `?v=9`, and
     the reopened tab opened there.
   - **Why it matters**: "given a newer address" and "loaded the newer
     address" would have passed with no reconcile at all in the reopened tab.
   - **Where the evidence is instead**: the load record (§7.2), read by the
     session, not the checks.
   - **The fix it needs**: a reopened tab's baseline should be the address
     that tab opened at.
   - **A related limit**: the reopened page's own page list is also read from
     the server when the tab opens (`siteRoutesFetch`), so for pages that
     check shows the list is right, not which path made it right.
