## 1. What was built

- **The `row` kind** (`builder/site-add.mjs`), a tenth add-on kind (`MAX_ADDS`
  10, `LIST_ADDS` gains it, `MAX_ADD_ROWS` 12):
  - its tool answers a list of `{ table, values }`; its rule says one entry
    per item named and not one more, never `id` or `created_at`, never a list
    visitors send in, and nothing else about the site moves;
  - the picker's instructions gained one sentence: one more entry in a list
    the site already stores is a `row`, never a second `table`, never a
    `component` or `page` drawn by hand;
  - `rowTables(spec)`: the stored tables whose access is the DISPLAY preset
    (`resolveAccess` against `ACCESS_PRESETS.display`, the data step's own
    condition), with their declared columns; `rowBrief` tells the designer
    exactly those lists;
  - `cleanAdd`'s `row` case checks each entry against the site's OWN schema,
    never the answer's: a list it stores, a display list, its declared
    columns only (the shared `rowValues`), `id` and `created_at` dropped;
    each refusal named (`no-row-table`, `row-no-table`, `row-not-list`,
    `row-no-values`), one bad entry never throwing the good ones away;
  - `rowsInsert`: every entry with the data step's own `insertStatement`,
    `RETURNING *`, and — when the request has a key — a `_meta` row keyed by
    it, all in one statement; `readSavedRows` and `readRowMarker` read back
    exactly what the database stored (its id, its defaults), or `null`.
- **The shared insert** (`builder/site-rows.mjs`, a leaf with no imports):
  `rowValues` (the data step's value rule, moved out of `readDataChanges`)
  and `insertStatement` (the data step's INSERT, moved out of `worker.js`).
  Both doors import it; the data step's statement is byte for byte the one it
  always wrote (a test holds the old expression against the new). The one
  place it is stricter: a double quote in a table name is dropped, as it
  already was in a column name; a stored schema cannot hold one
  (`SAFE_IDENT`).
- **The route** (`worker.js`, the add-on route):
  - **before the picker**, on a site with a display list, the request's key
    is read from `_meta`; found, the run answers what was saved (`repeat`),
    with no model call and no second charge. A missing `_meta` (42P01) reads
    as nothing saved; any other read failure stops at no cost (`no-meta`);
  - **a `row` alone**: the row designer is called once (with `rowBrief`), its
    answer cleaned, the charge reserved under a job before anything is
    written (a refused reserve answers `unbilled`), the one statement run,
    and the reply built from what came back: `{ ok, kinds: ["row"], rows:
    [{table, id, label, row}], added: [], …, cost }`. No page call, no
    compile, no publish;
  - **a unique key's refusal** (23505): `_meta`'s means another run of this
    request saved first, so its saved entries are read back and answered as a
    repeat; the list's own means a duplicate entry, said to the customer
    (`row-duplicate`). Any other write failure is `row-write`, at no cost —
    under a job the consumer refunds the reserve because the reply did not
    ship;
  - **inline**, the charge is collected after a write that landed, as the
    pageless add-ons' is;
  - **a `row` beside other kinds** is set aside and named (`row-alone`, in
    `notAdded`), and the rest runs exactly as before; beside a kind that hops
    to an edit rung on its own (a photograph alone), the message is refused
    whole at no cost, so the entry cannot vanish on the hop;
  - the charge closure (`aCharge`, `aCharges`) moved above the picker, its
    body unchanged, because the row step is its first caller now.
- **The data step** imports `insertStatement` and `rowValues`; nothing else in
  it changed.
- **The browser** (`public/chat.js`, `addonReplyText`): one clause per saved
  entry, from the reply's `rows` — *added “Rye & Caraway” to loaves (entry
  12)* — up to six, then *and N more*. Inline, so the sweep's composer
  (`scripts/addon-sweep.mjs`, which runs the real function) needs no new
  helper.
- **The container image**: `builder/site-rows.mjs` added to the Dockerfile's
  worker-tree COPY line (`worker.js` imports it). The image rolls on merge.
- **The canary** (`scripts/canary-addon.mjs`, `scripts/edit-canary.mjs`):
  with the route box `intent=addon` and the router answering `addon`, the add
  answer is posted to `/api/site/<slug>/addon` exactly as `siteAddon` posts
  it (instruction, a fresh retry key, the zone, what was held back), watched,
  composed by the add route's own composer, read after (an entry-only
  addition must leave every page at the before-read's version), and passed
  only on an `ok` answer, the line saying what was saved. Without the box
  saying `intent=addon`, an `addon` answer is refused as before; a box
  expecting an addition and an `edit` answer is refused by the route check;
  an answer that is neither is refused at the gate, naming the add-on step.
- **The sweep harness** (`scripts/addon-sweep.mjs`): a `row` case that runs
  only when typed by name, never under `all`, because it writes a real
  entry (`.github/workflows/lane-sweep.yml`'s form description says so).

## 4. The Postgres probe (local Postgres 16, no live database)

The statement `rowsInsert` builds (from the real module, not a copy), run
through `PREPARE` with no parameter types — Postgres infers each one from
where it stands, as it does for the driver's untyped parameters — on a
`loaves` table of the engine's shape (`id integer GENERATED BY DEFAULT AS
IDENTITY`, `created_at timestamptz DEFAULT now()`) that had 11 rows inserted
and ids 7–11 deleted, with `_meta (k TEXT PRIMARY KEY, v TEXT)`:

1. **Two entries in one statement**: the parameters inferred as `{text,
   numeric, text, text, numeric, text, text, text, numeric}`; saved as **id
   12 and id 13**, not 7 — the sequence's position, not `max(id) + 1` —
   with the database's own `created_at`; `RETURNING *` handed back each row
   as stored; the `_meta` key holds both rows and `cost: 2`.
2. **The same statement again** (a replay of the same request): `ERROR:
   duplicate key value violates unique constraint "_meta_pkey"`, and the
   table still holds 8 rows — the second run saved nothing.
3. **"£5.00" for the numeric column**: `ERROR: invalid input syntax for type
   numeric: "£5.00"` (22P02), 8 rows, 1 key — nothing saved, no key left.
4. **A unique column** (`loaves_name_key`) refusing a second "Rye &
   Caraway": 23505 on `loaves_name_key`, 8 rows, 1 key.
5. **No `_meta` table**: `ERROR: relation "_meta" does not exist` (42P01),
   8 rows.

Each outcome is what `test/fixtures/rows-db.mjs` models.
