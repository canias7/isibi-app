# Decide 1a: full-text search in the draft preview, judged by the site's database (2026-10-22)

The owner chose option A from `docs/history/2026-10-22-audit-g5.md`: the site's
own database judges the held rows. On `decide-1a`, branched from
`origin/combine-groups` (`36671236e`). Offline. Nothing was spent and nothing
was deployed.

## What changed

- **`servePreview` (`worker.js`)**: when a touched table's read carries a
  full-text filter (`col=fts|plfts|phfts|wfts[(config)].<q>`), `ftsFilterOf`
  takes it out and `previewFtsRows` works out which of the draft's rows match:
  - **Live rows the draft leaves alone**: the data service is asked
    `?select=id&<col>=<the same filter>`, so the live site's own answer decides.
  - **Held rows** (new rows, and live rows the draft changes, judged by their
    new values): one catalog read gets the search column's generated
    expression (`pg_get_expr` on `pg_attrdef`, `attgenerated = 's'`) and its
    table. Then one judging query runs:
    `SELECT v.ordinality FROM jsonb_populate_recordset(NULL::<rel>, $1::jsonb) WITH ORDINALITY AS v WHERE (<expr>) @@ <fn>(…)`.
    The rows, the config and the query text are passed as parameters. The
    expression and the table name come from the catalog, never from the
    request.
  - **A row the draft deletes** is already gone from the overlay, so it stays
    hidden even when the live filter returns it.
  - Every other part of the query (`order`, `limit`, the other filters) is
    then answered by `applyRowQuery`, as before.
- **The operators follow PostgREST**: `fts` → `to_tsquery`, `plfts` →
  `plainto_tsquery`, `phfts` → `phraseto_tsquery`, `wfts` →
  `websearch_to_tsquery`. With `(config)`, the call is `fn($2::regconfig, $3)`.
  Without one, it is the one-argument form, which uses the database's default
  configuration, as PostgREST does.
- **Read-only**: there is no separate read-only role. The preview reaches the
  database through the site's owner connection (`siteBackendBySlug`). The new
  `sqlReadOnly` (`site-db.mjs`) sends each statement as a Neon read-only
  transaction (`Neon-Batch-Read-Only: true`), and Postgres refuses any write
  inside one. The test reads that header on the wire.
- **Refused (422, never guessed)**:
  - more than one full-text filter;
  - a column or config that is not a plain name;
  - an empty query;
  - no generated column in the catalog;
  - held rows on a table the live database does not have yet;
  - the data service or the database failing;
  - an answer that cannot be read.

## Cost

Each preview search on a touched table with held rows now costs one extra
data-service read and **two** small read-only SQL statements: the catalog read
and the judgement. The catalog read is needed because the column's expression
(which columns, and any weights) lives in the database. A search with no held
rows in the list runs no SQL.

## Tests

- **`test/draft-first.test.mjs` DFB16**, through the real Worker and the real
  Neon driver, with no network:
  - a held new row that matches appears, and one that does not is absent;
  - a live row deleted in the draft stays hidden although the live filter
    returns it;
  - a changed row is judged by its new value: it appears where the live data
    did not match, and is absent where the live data matched;
  - both SQL statements are sent read-only;
  - the four operators and two configs map to the right function and
    parameters;
  - a malicious query leaves the SQL text unchanged and goes in as a
    parameter;
  - a config that is not a name is refused before any SQL is sent;
  - an unreachable database, or an unreachable data service, gives 422.
- **DFB14** keeps its `_fts` → 422 case. Its stub answers no catalog read,
  which is the cannot-judge path.
- **Red check**: DFB16 fails on `combine-groups`' product files (0 of 1).
- **Sweep**: 6 of 6 mutants killed, and the comment-only control survived.
  - the `plfts` function swapped;
  - `readOnly: false`;
  - held rows always kept;
  - changed rows not treated as held;
  - the config form dropped;
  - a failure answering the unjudged rows.
- **Related files** (`draft-first`, `preview-*`, `*held*`): 174 of 174.
- **Full suite**: see the commit's report.

## Left open

- **Not run against a real Postgres.** The catalog query, `jsonb_populate_recordset`
  over the table's row type and the `ordinality` column are standard Postgres,
  but the test checks them only through a stub.
- **A held row whose values are not valid for the table's column types** (for
  example, text in an integer column) makes the judging query fail, so the
  search answers 422.
- **A search column that is not generated** (a plain `tsvector`, or `text @@`)
  is refused.
