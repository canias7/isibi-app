## A04-3

**Fixed (the Publish half, the owner's rule of 2026-09-14):** the publication's
`schema` step now reads the stored function names before it applies the held
spec, and keeps the `functionErrors` the apply answers. A function the site did
not already have that failed to create is stored on the journal (`deadFns`), so
a stop between the steps keeps it; the `jobs` step leaves every held job on such
a function unregistered and records each in `skipped` (stage `jobs`, with "the
function it runs, X, could not be created"), which the Publish answer already
returns. A failed replacement of an existing function drops nothing (the old
body still runs), and an unreadable prior list drops nothing (cannot-tell never
takes a job off). Helpers `deadNewFunctions` and `jobsWithoutDead` in
`site-draft.mjs`.

**Left, an owner decision:** checking the held DDL *before* holding, so the
add-on's own reply is honest at save time, and applying the full schema before
the switch. `applySiteSchema` is many separate statements over HTTP, not one
transaction, so a rolled-back rehearsal means restructuring the schema engine or
using a Neon branch (cost and time per add-on); applying before the switch
changes the publication's phase contract (functions and DDL reaching the live
database while the old version still serves). The add-on reply under
draft-first still lists every designed function and job as made until one of
those is chosen.

## A06-5

The Edit page rung overlays the draft's held changes on its schema
(`specOverlay(eSpec, view.ops)`) before the writer and `lintPages`; a draft that
cannot be read stops with `page/spec-unreadable` (backend `draft`), as the data
step does. The revise Build, when its writer is holding, overlays the draft on
the stored spec before `withStoredSpec`; an unreadable draft stops the revise,
refunded, through the existing `backend-unreadable` answer.
