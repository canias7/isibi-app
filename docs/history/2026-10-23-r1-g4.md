# Audit round 1, group 4: containers and jobs, recovery, compile, preparations (2026-10-23)

Branch `r1-g4`, from `origin/main`. Fourteen findings of the builder audit
(`docs/audits/2026-10-17-builder-audit.md`), each checked again against
today's code. Offline only: nothing paid, no model calls, no live writes. Not
merged or deployed.

Seven are fixed, two were already fixed, one was partly fixed and needs the
owner for the rest, and four need an owner decision. Each fix has a guard test
that fails on the old code (the red check), a small mutation sweep with a
comment-only control that survived, and the affected test files run.

`builder/long-post.mjs` now keeps the abort listener until the call settles
(`disarm`) and rejects a cut after the headers as `ConnectionCutError`

3. Option 2, then move every fired-job file onto it.

## #108 A08-6: a draining or full container makes a fire fail for good. Needs the owner; comments fixed

Real: `fireOutcome` (`builder/edit-job.mjs`) asks a 503 three times, 2 s
apart, and reads a 429 as final, while a draining container answers 503 for
up to 13 minutes. The stale build-server comments, which said a 503 or a 429
was "the Worker's inline path", now say what really happens
(`builder/build-server.mjs`, comments only). The fix changes how long a
customer waits and how a claimed row is handed back to the queue, so it is
the owner's call:

1. **Defer `stopping` and 429 like a busy site** (release the claim and
   re-send the queue message a minute out, bounded by the 13-minute drain).
   Recommended.
2. Retry in place longer, up to about a minute, then fail as now.
3. Keep failing fast and say "try again in a few minutes" in the reply.

## #109 A08-7: nothing ties a launch to an image. Needs the owner

Real: the launch carries only `v: 2`, and nothing compares images. Options:

1. **Record the image on the job's run mark** (the runner already knows

2. Stamp the expected image into the Worker at deploy, refuse a mismatch with

3. Leave it, and keep the 15–20 minute wait rule for owner-driven tests.

## #143 A17-3: a held add-on row refunded as "not saved". Fixed

- **Re-verified, real.** `reconcileEditJob`'s row path read only the live
  database's `_meta` key, which held rows never write, then closed it and
  refunded, telling the customer to ask again. At Publish the held row went
  live anyway.
- **Fix** (`worker.js` `reconcileEditJob`; `draftVerdict` exported from
  `builder/site-reconcile.mjs`): the row path first reads the facts the page
  path reads (`reconcileFacts`) and asks `draftVerdict`. A revision of this
  job in the draft record, with its journal, is kept `draft-saved`, and the
  live key is never closed. A record that cannot be read, or a revision that
  cannot be proven, stays unknown. With no draft naming the job, the key
  decides as before.
- **Guard**: `test/addon-row.test.mjs`, "A17-3 A ROW HELD IN THE DRAFT…". The
  draft record comes from the real `saveDraftRecord`, with a held revision
  naming the job. Kept, with no `_meta` read or write and `p_committed: true`.
  Control: a row job that the draft does not name is still `closed-now`.
- **Red check**: with the draft branch disabled, the case fails (`refunded`).
- **Sweep** 4 of 4 killed (draft read skipped, wrong job id, the draft path
  always taken, the journal check inverted); the control survived.
- **Not changed**: the owner's dry read (`/api/site/reconcile`) still reads the
  key alone. It closes nothing and moves no money.

## #144 A17-5: the platform rebuild under DRAFT_FIRST only saves drafts. Needs the owner

Real: `verdictFor` (`site-rebuild.mjs`) counts `ok: true, draft: true` as
`done/republished` and forgets the queue row. Whether a platform security
rebuild may go live without the owner's Publish is a product decision:

1. **The rebuild recompiles the live version and publishes it live** when the
   site has no unpublished draft, and saves a draft otherwise, reporting the
   draft-only count. Recommended: a security patch reaches live sites.
2. Keep drafts, but `verdictFor` keeps the row as "saved as draft, needs
   Publish" (a new state) and reports the count, never "rebuilt".
3. Refuse platform rebuilds while DRAFT_FIRST is on.

## #156 A22-4: salvage called a part this build wrote "a file the build didn't write". Fixed

- **Re-verified, real** (`salvagePlan` built `known` from pages only).
- **Fix** (`builder/publish-pages.mjs`): `salvagePlan` takes the build's parts.
  A cited `-parts/<name>.tsx` that this build wrote is stubbed as a part
  (`partStub`, a default export that draws nothing, so the import stays
  valid). A part that a page the site already serves imports is `kept`
  (refused wholesale, as for that page). Not knowing what is live is refused
  as before. `foreign` is now kept for files the build did not write. The
  caller swaps the stub into the parts it compiles, keeps it only when the
  recompile works, and reports `salvage.stubbedParts` and `salvagedParts`.
- **Guards**: `test/publish-pages.test.mjs`, two "A22-4" cases: the plan
  (stubbed, kept when a live page imports it, refused when not told what is
  live, foreign when not written by the build), and a first build whose one
  band fails to bundle ships with that band stubbed, with the stub what the
  recompile is handed.
- **Red check**: not passing the parts makes the build case fail (the
  placeholder).
- **Sweep** 6 of 6 killed; the control survived.
- **Left out**: the customer's note (`salvageNote`) names stubbed pages only. A
  stubbed band is a missing section and is not mentioned yet. The wording is
  the owner's to choose.

## #157 A22-5: a check cut by its budget replaced the landmark map. Fixed (the stored side)

- **Fix** (`worker.js` `saveLandmarks`, both callers): when the render report

- **Guard**: `test/edit-path.test.mjs`, "A22-5…", driven through the edit

- **Red check**: without `partial` passed on the spine, the case fails.
- **Sweep** 5 of 5 killed; the control survived.
- **Not changed** (capture side): landmarks and texts are still captured at
  desktop after the phone pass, the CSS correction round still reads the cut
  run's own map, and the build's caller is covered by the same code but not
  driven by a test.

  signature).

## #159 A24-2: a refused checkpoint read retried for a day. Fixed

- **Re-verified, real**: the gateway admits only the job's own `jobs/` keys,
  and `readHeldIn` read the 403 as `unreadable`, so the part recovered for 24
  hours.
- **Fix**: `readHeldIn` (`worker.js`) answers a 403 `GatewayError` as
  `refused` at once. `recoverHeld` (`builder/request.mjs`) reads `refused` as
  the Worker would read the same record: missing. So it is lost without a
  copy, and run again with one.
- **Guard**: `test/requirement-checkpoint.test.mjs` CK 7c: the checkpoint is
  deleted, and the job's own fallback read gets a 403 after its staged read
  (the Worker's staging is not refused). The part fails at once
  (`checkpoint-unread`), nothing is judged and nothing applied. The fixture's
  `failGet` takes an optional error.
- **Red checks**: either half removed fails the case.
- **Sweep**: the 401 mutant was killed. "Refused is lost even with a copy"
  survived, because no case drives a refusal with a copy on the request. That
  branch is untested.

## #160 A24-3: a preparation with no parser paid for a rewrite. Fixed

- **Re-verified, real**: in the Worker, `tweakParser()` is null, so a
  component-bearing page's tweak is `needs-parts/no-parser`, and the
  preparation fell through to the page writer.
- **Fix** (`worker.js`, the page step): a preparation stops at that answer
  (`prepStop`), and the job replays the tweak where the parser loads.
  `standInTweakParser` (`builder/site-tweak.mjs`, tests only) lets a case give
  the preparation the Worker's null.
- **Guard**: `test/parallel-prep-paths.test.mjs`, "A24-3…": the Visit page
  renders a site component, and the parser is null for the preparation only.
  No page writer is asked, and the job applies the tweak with the component
  kept.
- **Red check**: without the stop, the case fails (the page writer is asked).
- **Sweep**: the wrong reason was killed. Two survived, with reasons: "the stop
  for jobs too" (a job has a parser, so the condition never holds there), and
  "the stand-in ignored" (with the real parser the preparation's tweak works,
  which also passes; the red check shows the null path is the one the case
  exercises).

## #161 A24-4: records under `jobs/prepared/` were never deleted. Fixed

- **Re-verified, real.**
- **Fix**: `retentionPrefixes` (`builder/job-retention.mjs`) adds
  `jobs/prepared/<nibble>`, so a job's staged answers, use record, kept replies
  and checkpoints go after seven days, like every other `jobs/` object (a part
  waits a day at most). `deleteSiteFor` (`worker.js`) reads each request
  record's job ids before the record goes and deletes those five keys per job.
- **Guards**: `test/job-retention.test.mjs` (three prefixes listed; a new case:
  all five keys of one job go in one full rotation once seven days old, never
  before) and `test/request-flow.test.mjs` E4b (a finished request, then
  `DELETE /api/site/<slug>`: its jobs' records are gone, and a neighbour's
  stays).
- **Red checks**: the prefix removed fails two retention cases, and the job
  deletes removed fails E4b.
- **Sweep** 6 of 6 killed across the two; both controls survived.
