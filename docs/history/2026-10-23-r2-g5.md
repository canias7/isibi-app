## A23-3: a provider's error sent down an open stream

**The problem.** A provider can open a stream and then send an error on it,
for example `insufficient_quota`. That error has no HTTP status. Three places
read it as "no request was made":

- `retryHere` (the Worker's hop and the resume);
- `patientCall`, which asked twice more;
- `routeFailure`, which reported it as `transport` with `billing:false`.

**The fix.** Such an error is now named `StreamError`. The name crosses the
container's failure shape as `kind`. `retryHere` and `patientCall` refuse it,
as they refuse a status. `routeFailure` reads its envelope through `classify`,
so an exhausted account is reported as billing.

**Kept as it was.** A stream merely cut short keeps its plain `Error` and is
still asked again. That was an earlier recorded choice: `build-call.test.mjs`,
"a stream cut mid-generation throws with NO status — the shape that refires".

**Tests and checks.**
- Tests: `test/stream-error-retry.test.mjs` (SE1–SE4).
- Red check: 3 of 4 fail on the old code.
- Sweep: 5 of 5 mutants killed; the control survived.

## S3-2: the data and rules lanes never honoured a Stop

**The problem.** Neither lane publishes, so the edit route's pre-publish gate
never ran for them. A job whose cancel had been asked still reserved, wrote
and finalized.

**The fix.** `applyStop(job)` is asked after the reserve and before the first
write. It renews the lease once, so a cancel set while the job was queued is
read now, and then asks the job's own `gate`. If the answer is stop, the lane
answers through `editStopped`, which refunds.

**Tests and checks.**
- Tests: in `test/edit-list-sort.test.mjs`, a queued data edit with a cancel
  asked writes no row, answers `cancelled` and is refunded; the control
  reaches its write. The rules lane is covered by the re-anchored source
  guard in `test/edit-reserve-refused.test.mjs`.
- Re-anchored: one landmark in `test/edit-rules-backend.test.mjs`.
- Red check: the cancel case fails on the old code.
- Sweep: 4 of 4 mutants killed (the beat, the gate's answer, and each lane's
  stop line); the control survived.

## A35-5: a side question read as an answer

**The problem.** A reply with `answered:true` and intent `ask` closed the
waiting question. For a request part, the part was then marked done without
its work being done.

**The fix.** In `routeMessage`, while a question is waiting, that pairing is
now read as `answered:false`: a side question. The reply is given and the
question keeps waiting.

## A35-3 (and part of A35-4): a dead part's question left in the slot

**The problem.** After a Stop, or when a part expired, its question stayed
pending for a day. The next message was taken as its answer: it was routed
and charged, with nothing to resume. Every other request's question also
queued behind it.

**The fix.** Each request advance (`offerRequestQuestions`) now closes, as
`cancelled`, a slot question whose part has ended. An answer to it is then
refused before routing (`stale-question`), at no cost.

**What it does not close.** A question is closed only once its part is in
`PART_TERMINAL`, never while the part waits or runs. Three legitimate states
put a question in the slot ahead of its part's record:

- an answer whose resume did not save waits on the same question again;
- a follow-up is written over the question in the slot (`replaceAsk`);
- a running part's job stores its own question before its part is told it
  waits.

**Tests and checks.**
- Test: A35-3 in `test/request-flow.test.mjs`. A part waits, the request is
  stopped, the slot question becomes `cancelled`, and the answer is refused
  with no routing call and no charge.
- Red check: fails on the old code.
- Sweep: 3 of 3 mutants killed; the control survived. A belt in the
  ended-request path was dropped because its mutant survived (it was
  untested).

## A35-4: re-offered and stale questions

**A cancel whose request read failed.** One thrown read ended the loop, and
the reply still said "cancelled". Now a failed read is tried again, up to 6
times. If the part could not be ended, the route answers
`503 { ok:false, error:"unread" }`, so the page says the question is still
open. Tests: C4b in `test/request-flow.test.mjs`, with 1 failed read and with
6. Sweep: 3 of 3 mutants killed; the control survived.

**An answer to a question the part has moved on from.** A stale copy could sit
in the slot while the part waited on its next question. `resumeRequestPart`
now treats the part as gone when the part waits on a different question id.
The part is never resumed with words meant for the other question. Test: C4c.
Red check: fails on the old code. Sweep: 3 of 3 mutants killed; the control
survived.

**Narrowed, not closed.** An advance can re-offer a question just after its
answer closed it and before the part's resume saved. The stale copy is now
closed once the resumed part ends (see A35-3), not after a day. While the part
runs again, the copy can still sit in the slot. Telling it apart from a
running job's own fresh question needs a closing time on the slot record (the
audit's "grace period" option). That was not added.

## A35-2: a replaced question never came back on the same page

**The problem.** A message typed beside a part's question card replaced the
question (`superseded`). The server offers the question again while its part
still waits. The page never made a question live twice (`siteReqAsked`), so
the request said "waiting for your answer" with no card until a reload.

**The fix.** When the route says the message replaced a part's question
(`d.ask.answered === false`), the page lets that id go. A later reading then
makes the question live again. There is no visual change: the existing card
is drawn again, so no screenshot was taken.

**Tests and checks.**
- Test: PLACE 11 in `test/request-reply-placement.test.mjs`. It uses the
  page's own functions and the real Worker: the card comes off, the server
  offers the question again, and the card is live again.
- Re-anchored: one guard in `test/conversation.test.mjs` (the clear is now a
  block).
- Red check: fails on the old code.
- Sweep: 3 of 3 mutants killed; the control survived.

## S6-4: two container jobs of one request, overlapping, through the gateway

**DH7** in `test/draft-handoff.test.mjs` combines what DH6 and PPM2 each
covered only in part:

- the site lock production runs (`beside`);
- each fired job started without waiting for the other;
- every storage call through the Worker's gateway (`{ worker, wire }`);
- `MODEL_REPLIES` on and `IMAGE_PURCHASES` off.

It asserts that:

- the two jobs' model calls overlap in time;
- both jobs ask the gateway for the publish turn, and it is taken there;
- nothing is refused;
- there are two draft revisions, and the live pointer, script and price are
  unchanged.

Under the applied lock (`beside: false`) it fails. The full file passed 3 runs
of 3.

**One reading from building it.** The row job sometimes finds the turn held
and saves its held change without taking the turn. Both revisions still land.
So the test requires each job to ask for the turn, not to take it.

in the backlog (build_debit.sql). The options:

1. Apply `supabase/proposed/build_debit.sql`, so container builds bill the

**S3-4: an approved rewrite stopped mid-build runs to its end and is charged.**
This is already in the backlog. Whether a stop mid-build should give back the
model work already spent is a cost decision. The options:

1. The build's beat records `cancel`, and the next stage (design, generation,
   publish) refuses through the budget-stop path. That path reverses all the
   build's refs, so the platform absorbs the model work already done.
   **Recommended**: it matches what a Stop means everywhere else.
2. The same stage gate, but keep the debits already settled (the deposit for
   the design) and reverse only what was not started.
3. Keep running to the end, and change the request card to say "the rewrite
   was already underway and finished", so the Stop is not claimed.
